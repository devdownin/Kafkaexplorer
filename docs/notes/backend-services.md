# Backend services — design notes

Extracted from `CLAUDE.md` (it had grown to 505 KB, loaded into every session).
This is the *why* behind the odd-looking choices in `service/`: almost every one is a
fix, and the paragraph beside it is the defect it closes. Read the entry for a class
before changing it.

## Backend layers

```
web/          REST controllers (one per domain: Query, Topic, Audit, Lineage, etc.)
service/      Business logic — FlinkSqlService is the core engine
config/       Spring configuration (Kafka, Flink, Explorer settings, CORS)
domain/       DTOs — implemented as Java Records
parser/       JSON, XML, and Avro (via Confluent Schema Registry) schema inference
```

**Key services:**
- `FlinkSqlService` — executes SQL against Kafka topics using embedded Flink `LocalEnvironment`; per-request table registration ensures isolation
  - **The embedded runtime is told which classpath its jobs run on** (`FlinkConfig.applyJobClasspath`). A job submitted to the local MiniCluster carries no user jars, and Flink reads "no jars *and* no classpath" as "this job needs nothing of its own": `BlobLibraryCacheManager` then hands the JobManager `ClassLoader.getSystemClassLoader()` to deserialize the job graph with. That is the right default on a real cluster, where Flink sits on the system classpath, and it is wrong in **every packaged form of this application** — inside a Spring Boot jar (`java -jar`, or the extracted layers behind `JarLauncher`, which is what both runtime images run) the dependencies live in `BOOT-INF/lib` and are reachable only through Boot's own loader, so the first operator came back as `ClassNotFoundException: org.apache.flink.table.runtime.operators.CodeGenOperatorFactory` and the job never started. What reached the log was `FlinkException: Failed to execute job '…'`, stack trace included, once per SELECT — and at boot, since the warmup probe is a SELECT. Nothing about it read as what it was: every SELECT was classified as an *engine* failure and fell back to the direct Kafka reader, so rows kept arriving from a reader that supports neither JOIN nor subqueries, the circuit breaker then disabled the planner for the rest of the process after three, and `CREATE TABLE` / `INSERT INTO`, which have no fallback, simply failed. The whole Flink half of the application was dead in the shipped artefact while the suite stayed green — it runs on a plain classpath, where the application loader *is* the system loader. Naming a non-empty `pipeline.classpaths` is what makes Flink build a real user-code class loader instead of taking that shortcut, and the parent it gives that loader is the one that loaded Flink, i.e. ours. It is paired with **parent-first** resolution and that is not decoration: Flink's default is child-first, which over our own URLs would load a second copy of every class outside the always-parent-first patterns (our UDFs among them) and yield `ClassCastException` between two versions of one type. On a plain classpath the method writes nothing — there is nothing to correct. `ci.yml`'s `release-image` job asserts both halves (no `Failed to execute job`, and the warmup reporting success), because it is the only place in CI that runs the engine the way it is shipped.
  - **SELECT execution**: when `explorer.flink-select-enabled` is true (default), SELECT runs through the real Flink planner via `executeViaFlinkPlanner()` and normally reports `engine=FLINK`, falling back to `kafkaDirectSelect()` only on a planner failure. The historical `FlinkRelMetadataQuery` NPE (`metadataHandlerProvider`, reproduced on Flink 1.18/1.20/2.0) that once forced every SELECT through the direct reader is **fixed**: `FlinkRuntimeCoordinator.ensureFlinkMetadataProvider()` pre-seeds Calcite's `RelMetadataQueryBase.THREAD_PROVIDERS` ThreadLocal with Flink's provider (Flink 2.x leaves it unset before the VolcanoPlanner's cost pass). A process-lifetime circuit breaker (`FLINK_SELECT_FAILURE_THRESHOLD` = 3) still guards against any residual planner failure so it does not add a failed attempt to every query (timeouts don't count toward it). `CREATE TABLE` / `EXPLAIN` always go through Flink. Engine used is reported in `QueryResult.engine()` (`FLINK` vs `KAFKA_DIRECT`).
  - **A named read mode does not change what a windowed query means** (`SqlStatements.hasWindowTableCall`). `readMode` routes a single-table read to the direct reader, and `MetricService.isSingleTableRead` is the predicate deciding whether that reader can answer the shape honestly. It answered **true** on `TABLE(HOP(…))` — measured — so the editor's **Latest** selector, which names a read mode, sent a windowed query to the direct reader *with no planner failure anywhere*. The same `HOP` then came back as adjacent buckets approximated as `TUMBLE`, where **Earliest** went through Flink and got real overlapping windows: a selector supposed to choose only which end of the topic to read was changing what the query means, and returning a plausible wrong answer rather than a refusal — the worse of the two directions. A window is not a shape that reader can answer honestly, so the predicate now says so, which is a correction to its own contract rather than a change of policy; the caller then goes to the planner and **says the mode was not applied**, through the `unhonouredReadMode` branch that already existed for exactly this. The rule is shared rather than restated, and that is what turned up the second half: it lived in two copies inside `FlinkSqlService` that **did not name the same functions** — the one extracting the source table knows `CUMULATE`, the one deciding to route to the window handler did not. A cumulative window reaching the direct reader was therefore not approximated but treated as an ordinary aggregate, so **the window vanished without a word**, where its three neighbours at least came back with the warning saying they had been approximated. The `warnings` a windowed direct read builds are still dropped on a topic that does not resolve — deliberately, since that result carries an error instead and the UI renders warnings only beside a successful one.
  - **A CTAS is classified by Flink's parser, not by a regular expression** (`parserSaysCreateTableAsSelect`). The lexical test blanks single-quoted literals and **not backtick-quoted identifiers**, so it refused perfectly ordinary DDL: measured, ``CREATE TABLE `weird as select` (id STRING) WITH (…)`` and ``CREATE TABLE t (`col as select` STRING) …`` were both classified as CTAS and refused — with a message explaining how to split into `CREATE TABLE` then `INSERT INTO`, about a `CREATE TABLE` that had nothing to split. That is the false positive that matters, on the only DDL this application accepts. `CreateTableASOperation` does not get it wrong, and this repository replaces the lexical with the parser for exactly that reason — `LineageService.parseWithFlink` is the precedent, guards included, and they are reused here: the parser is consulted only when it exists (a bare `TableEnvironment`, as in some tests, exposes none), the access goes through the runtime's read lock like every other, and **a failure falls back to the lexical test**, which fails closed. A CTAS whose source does not exist does not parse — the regex catches it and the refusal stands. It returns `null` for "could not ask", never an invented verdict.
  - **A query that updates its answer says so, row by row** (`ChangelogInfo`, `describeChangelog`). An aggregation, an outer join or a scalar subquery does not return rows: it returns a *changelog*. Measured on three input rows, `SELECT COUNT(*)` returns **five** (`+I(1)`, `-U(1)`, `+U(2)`, `-U(2)`, `+U(3)`), a `FULL OUTER JOIN` of 3 x 2 returns seven, a scalar subquery seven. `Row.getKind()` was read — logged at DEBUG for the first row — and then thrown away, so the grid presented the corrections as results and an operator reading a `COUNT(*)` saw five rows and had to guess that only the last one counted. `MetricService` had already learnt that lesson ("the value is the last numeric row"); the editor never had. The kind now travels with the row under the reserved key `__row_kind`, **never as a column**: `columns` comes from the resolved schema and is what the grid, the sort and the export read, so an entry there would make a property of the row pass for a value of the result — the same rule as the `__`-prefixed columns of `MetricService`. It is written only when there is something to say, an insert being the ordinary case. The marker was chosen over folding the changelog server-side because folding decides *for* the caller which row counts, where the marker returns exactly what the engine emitted and says what each row is. **The row cap counts the corrections**, and that is the heaviest consequence: a changelog can fill the cap with intermediate states and be cut off *just before* the only row that mattered. The cap is deliberately not loosened — returning more rows than the caller asked for, or picking the surviving row for them, is precisely what the marker avoids — so what changes is that the result **says** it: one warning names how many of the rows are corrections, a second, separate one says the cap cut the changelog before it settled. Two sentences and not one, because "these rows correct each other" and "the correction is cut short" are different facts and only the second changes how the last row on screen reads. Both travel in `warnings` as well as in the record: the grid is not the only reader, and an export, a screenshot or a direct API call have only the text.
  - **`SHOW` and `DESCRIBE` are answered, not refused** (`isIntrospectionStatement`). They are pure reads, and they are what an operator arriving from a SQL client types first — refused with "Only SELECT, EXPLAIN and CREATE TABLE statements are allowed", which reads as a security restriction on two statements that cannot write anything. The application already held the answer behind another door (`/api/query/init` lists the tables, `/api/query/schema/{table}` returns the columns), so the refusal was not protecting data, it was hiding the same data. The `SHOW` forms are a **closed list** and everything else stays refused, which is the whole of the guard: the whitelist classifies on the first word, so admitting "anything beginning with SHOW" would admit whatever the next Flink version puts behind that keyword — `USE`, `SET` and `LOAD MODULE` change the session's state, `ALTER` and `DROP` write. `DESCRIBE` needs no list, every form of it describing an object. Two things travel with the permission. **`SHOW CREATE TABLE` is masked**, because what it returns is DDL — Kafka client properties, so the SSL passwords and the `sasl.jaas.config` secret — which is the rule every other DDL exit here already followed and this path had never needed. And **`DESCRIBE <topic>` auto-registers its table** (`describedObject`): without it the most natural first gesture answered "unknown table" about a topic that is plainly there, and registering it meant going away to run a SELECT and coming back. Both go through the runtime's **read** lock rather than the mutation one — taking the write lock to list tables would serialise the most banal gesture of the editor behind whatever query is running.
  - **Only an engine failure falls back.** `SqlErrorClassifier` splits a planner failure into `USER_ERROR` (parse error, unknown table/column, type mismatch, restricted statement) and `ENGINE_ERROR`; `rejectIfUserError()` returns the planner's own message for the former instead of retrying on the direct reader. Falling back on a bad query is worse than useless — the direct reader only regex-matches the table name out of `FROM`, so `SELECT id, FROM orders` or a misspelled column came back as *rows*, and the planner's precise complaint (with its line and column) was discarded. User errors also don't count toward the circuit breaker, or three typos would disable the Flink planner for the rest of the process. One exception, carried by `AutoRegResult.deferToDirect()`: when a topic exists but schema inference returned nothing, registration is deliberately skipped, so the planner's "not found" is our doing and must still fall back.
  - **A SELECT that names no table never falls back either**, and when it cannot run, the reason it reports is the *engine's*. The direct reader begins by regex-matching a name out of `FROM`, so on `SELECT 1 + 1` it can only answer `Cannot parse table name from SQL` — its own complaint, about a statement it was never meant to run — and that is what was handed to the caller *in place of* the planner's real message, which sat one WARN line above. It is the line the startup warmup probe printed for months while the actual cause (a job that could not be submitted at all) went unread, and the same substitution reached the API. `extractPrimaryTable() == null` now ends the query with `engineFailure` when the planner tried and failed, and with `plannerUnavailableMessage()` when it was never consulted — the latter distinguishing an operator's `explorer.flink-select-enabled=false` from the circuit breaker having tripped, two states that read identically from outside. Same rule as the CTE branch above: a refusal that names the cause beats a different engine's opinion of a query it cannot run.
  - **The circuit breaker says so, on the queries it affects.** `flinkSelectDisabled` was written in one place and read in one place and surfaced nowhere, so once it latched — for the lifetime of the process — every later SELECT came back as `engine: KAFKA_DIRECT`, without JOIN or subquery support, with nothing saying the degradation had become permanent. A fallen-back result now carries `plannerUnavailableMessage()` in `QueryResult.warnings()`, which the editor already renders above the grid, and `isFlinkSelectDisabled()` exposes the latch. The latch itself is unchanged and still needs a restart to clear: that is deliberate where the cause is a Flink version defect, and is worth revisiting now that an *environmental* fault has been seen to trip it.
  - **No step of a query waits without a deadline** (`FlinkRuntimeCoordinator`). Only the *row fetch* was bounded — the step that comes after validation, table registration and job submission, none of which had any deadline at all: `lock.lock()` and `future.get()` both wait for ever, and the runtime is one fair read/write lock plus a single mutation thread, so one operation that stopped making progress took every later query with it. What the user saw was a Run button spinning with no result and no error, which is what a status bar must never do. `runRead`/`runMutation` now take a wait budget (`DEFAULT_WAIT_MS` = 30 s; the SELECT path passes `max(5 s, query timeout)`) and raise `FlinkRuntimeBusyException` when it expires — classified as an **engine** failure, so a SELECT still falls back to the direct reader rather than being returned to the user as an invalid statement. The message names the operation that gave up **and the one holding the runtime, with its thread and how long it has held it**; a wait beyond 2 s is a WARN for the same reason (it was DEBUG, i.e. invisible on an ordinary install, which is exactly the line that explains a query that never comes back). A timed-out mutation is cancelled, so it cannot run later behind its caller's back. The frontend carries a matching ceiling — `axios` has no default timeout, so a server that never answers left `executing` true for ever.
  - **Cancelling a synchronous run** needs the id up front: `QueryRequest.queryId` is client-supplied, because a server-generated id only reaches the caller in the response, by which point the query is over. `FlinkSqlService.resolveQueryId()` accepts it only when it matches `[A-Za-z0-9_-]{8,64}` (it becomes a job-store key and appears in logs) and mints a UUID otherwise. `POST /api/query/cancel/{queryId}` then reaches the live `JobClient` and **reports whether it found one** (`CancelOutcome`), because the UI also aborts the HTTP request — the part that is guaranteed regardless of engine — while a `KAFKA_DIRECT` scan has no Flink job to cancel and finishes its in-flight fetch server-side. Returning `void` behind a 200 meant Stop announced a cancellation in the case where nothing had been cancelled.
  - `SqlErrorClassifier.explain()` flattens a throwable's cause chain into one never-blank message (Flink wraps the useful Calcite text — including the line/column — inside a generic outer exception). It replaced bare `e.getMessage()` on the error paths: that is `null` for a `NullPointerException`, which nulled out `QueryResult.error()` and made the UI report a crash as a successful run of zero rows.
  - **And the plan dump is taken off before the message is shown or cut** (`SqlErrorClassifier.readable()`). Calcite reports a planning refusal as `Error while applying rule <Rule>(…), args [<the whole rel tree>]: <the actual sentence>`, so the useful half is *last* — which is also the half `MAX_EXPLAIN_CHARS` removes first on a wide table. `readable()` keeps whatever wrapped the rule failure (Flink's own "Cannot generate a valid execution plan" is a sentence, unlike the tree), keeps the rule name in parentheses because that is what one greps the Flink log for, and drops the tree. It is applied inside `explain()` before the truncation, and again at the two places where a planner message reaches a user — the rejection message and the fallback caveat — since those also receive error *strings* that never passed through `explain()`. Classification still reads the full text: this is presentation, not logic.
  - `kafkaDirectSelect()` (fallback engine) supports aggregate functions (COUNT/SUM/AVG/MAX/MIN with optional GROUP BY) computed in-process over fetched Kafka messages. SQL must alias the result column (e.g. `COUNT(*) AS metric_value`). COUNT values are returned as `long` (integral), other aggregates as `double`.
  - For aggregate queries, up to 100 000 messages are fetched (earliest-offset). Plain projections fetch `limit + 20`; when a `WHERE` clause is present the scan widens to `max(5000, limit×100)` capped at 100 000 (the row loop still stops at `limit` matches).
  - **WHERE filtering**: simple `col = 'value'` conditions. Anything else — `>`, `LIKE`, `IN`, `OR`, `NOT` — never matches the extraction pattern, so it used to be dropped silently and the rows came back unfiltered. `unsupportedWhereFragments()` now reports what was ignored in `QueryResult.warnings()`; keep that wiring when touching the direct engine, a search that lies is worse than one that refuses. Column names keep their original case and support dot-notation nested paths (resolved via `getNestedValue`, with a case-insensitive top-level fallback). Values compare case-insensitively.
  - XML payloads are parsed through `SecureXml.documentBuilder()` — one hardened, per-thread `DocumentBuilder`, reset before it is handed back. Never build a `DocumentBuilderFactory` per message, and never write the hardening a sixth time: `SecureXml` is the only place in the tree that configures an XML parser (`documentBuilder` / `documentBuilderFactory` / `inputFactory` / `xpath`), because the same eight-line block had been copied into five classes and had already drifted — `FEATURE_SECURE_PROCESSING` was set in one of them, `setNamespaceAware(false)` in one, and `XmlSchemaInferrer` built its factory per call. XXE hardening has to hold at *every* entry point, so five copies meant five chances for the next one to be written with seven of the eight lines. A feature the parser implementation does not recognise now throws rather than being swallowed: a hardening that silently did not apply is the one failure mode worse than a missing one.
  - **Window functions**: `TABLE(TUMBLE(TABLE <name>, DESCRIPTOR(<time_col>), INTERVAL '<n>' MINUTE|HOUR|SECOND|DAY))` is supported via `kafkaWindowSelect()` — buckets messages by timestamp and computes aggregates per window. Time column resolution: message field (ISO-8601 or epoch) → Kafka record timestamp (fallback). `HOP`, `CUMULATE` and `SESSION` (with or without `PARTITION BY`) parse too but are **approximated as TUMBLE** of the same width — for the two-interval forms the width is the *last* interval (HOP's size, CUMULATE's max), not the slide — and the approximation is reported in `QueryResult.warnings()`. They used to reach this method and die on a TUMBLE-only regex with "Cannot parse TUMBLE syntax". Flink accepts singular and plural unit names alike (`MINUTE`/`MINUTES`), so both are matched.
  - **Every lexical pass reads outside the string literals** (`SqlStatements.outsideLiterals`, one scanner). A regex over the raw statement does not know where a literal starts, so it finds its keywords inside one — and none of those cases returns an error, they return a *different query* than the one that was written. Four were live. `WHERE note = 'voir -- plus bas'` lost everything after the quote's contents when comments were stripped, so what reached the planner was truncated and its syntax error was reported as the user's. `WHERE msg = 'CROSS JOIN'` was refused by the guard, which is how a guard teaches people to work around it. `WHERE note = 'select * from autre'` made `extractPrimaryTable` read *autre* as the source, so the direct reader looked for that topic and auto-registration created a table for it if one existed. And `WHERE note = 'limit 1'` cut the page to one row. The scanner blanks the **contents** of single-quoted literals and backtick identifiers, keeps the delimiters (so a pattern citing them still works) and **preserves every position** — which is what lets a caller find its boundaries on the blanked text and then slice the original when it needs the literal's value, as `extractSimpleWhere` and `unsupportedWhereFragments` now do. It replaces the private literal-blanker that `isCreateTableAsSelect` already carried: the technique was in the tree, it was just not shared. Comment stripping folds into the same pass — one scan, block and line together, hints kept — so `--` inside a literal is a value and `--` inside a block comment is a comment, which the two-pass version got right only by accident.
  - **A column qualified by its table's alias resolves, and comes back under its bare name.** `SELECT o.state FROM demo_orders o WHERE o.state = 'SHIPPED'` is ordinary SQL, and this reader answered **zero rows** to it: the condition carried the key `o.state`, looked up whole and then segment by segment in an object `o` that does not exist, so every row was rejected — an empty grid on a correct query, which is the plausible wrong answer this codebase keeps removing. The projection had the same defect one column over, returning a column of nulls. `tableQualifiers` reads the table name and its alias (with or without `AS`, and a keyword following the table is not an alias), `withoutQualifier` strips the prefix **only** when it is one of those — a nested `customer.name` is not a qualification — and `resolveColumn` tries the written path first, so a flattened XML key that really is called `o.state` still wins. It is applied to the WHERE, the projection, the GROUP BY key and the aggregates (`SUM(o.amount)` read through a raw map access and came back null). The output name is the bare one, because that is what the planner produces and two engines that name the same column differently break everything that reads a result by name — including this application's own metric templates.
  - **A projection that stopped on its scan ceiling says what it read.** The aggregate branch already did (`AGGREGATE_SCAN_CAPPED`) and this one did not, which is where the silence costs most: a `WHERE` that matches nothing in the slice read comes back as an empty grid, indistinguishable from "no record matches" — and on a topic older than the ceiling that is the wrong answer by construction, every time. The caveat fires on exactly what is known — the read stopped on its own cap (`records.size() >= fetch`) and the page is not full — and names the count, the topic, which end it entered by (`describeScanEnd`, deliberately not `MetricService`'s sentence of the same shape: there `null` means that module's default, here it means what `fetchForDirectRead` really does with it) and the two ways out.
  - **A window over a Kafka topic is handed to the direct reader by name, before the planner is consulted.** Not a preference — a Kafka source is unbounded, so it never finishes, so the last window never closes, and the collection loop only returns at the row cap or at the budget. A windowed query producing fewer rows than the cap (the ordinary case: `SELECT window_start, COUNT(*)` over a day of traffic in five-minute buckets) could therefore only spend its ten seconds and fall back here, discarding the rows it had already collected on the way. The fallback was the outcome, not the exception, so the wait bought nothing. Three guards, each closing one way of returning wrong rows. **The shape**: `MetricService.namesOneSourceOnly` — the structural half of `isSingleTableRead`, shared rather than copied — refuses a window joined to another table or opened over a subquery, which that reader would answer by reading the first table and ignoring the rest in silence. **The table**: it has to be a topic *this application* registered; a definition an operator typed stays with the planner, since its own options (a bounded scan, a watermark) may be exactly what lets the planner answer, and `FlinkTableStore` is what tells the two apart. **The hint**: a statement carrying its own `OPTIONS(…)` says what it wants of the source — `scan.bounded.mode` being precisely what makes it end — so it goes to the planner as asked (`SqlStatements.carriesAnOptionsHint`, one definition shared with `MetricService.injectScanHint`). The result carries a note rather than a fallback caveat, because nothing failed: it names the reader, its 100 000-record cap, and the table declaration that moves the query to the planner. It also means the read mode is honoured — `latest-offset` and `earliest-offset` now answer through the same engine, which is the inconsistency `isSingleTableRead` was refusing windows to avoid.
  - **A window the planner refuses for want of a time attribute is the table's shape, not a breakdown.** A column carrying timestamps only becomes a *time attribute* when a `WATERMARK` is declared on it, and until `DdlGeneratorService` declared one (below) no generated table had any — so `TABLE(TUMBLE(TABLE t, DESCRIPTOR(event_time), …))`, which is verbatim what the editor's Window Assistant writes and what the Help page teaches, was rejected at planning time on every topic in the cluster: *The window function requires the timecol is a time attribute type, but is TIMESTAMP(3)*. Read as an engine failure, that refusal did three wrong things at once. It reached the editor as `warnings` in the planner's raw form — `Error while applying rule StreamPhysicalWindowTableFunctionRule(…), args [rel#27876:…]` — four hundred characters of planner state in front of the one sentence that says anything, behind a caveat about JOINs and subqueries the query never used. It counted toward the circuit breaker, so three windowed queries in a row (the most natural thing to do in that assistant) took the Flink planner out for **every** query of the process for ten minutes. And it named neither the column nor the fix. Since the routing above takes every window over a topic away from the planner, what is left here is the hand-written table and the statement that bounds its own scan — but there the refusal still had to stop being read as a breakdown. `windowNeedsATimeAttribute()` recognises it before `rejectIfUserError` — gated on the statement really being a window call, which is what lets the wording match be broad — resets the failure counter and writes the caveat itself: which column, that it needs a watermark, what the `WATERMARK FOR` clause looks like, and the planner's own sentence past `SqlErrorClassifier.readable()`. **The fallback itself stays**, and that is the reason this is not a `USER_ERROR`: `kafkaWindowSelect` genuinely computes the window, resolving the column out of the message payload — which is the commonest shape here, a window over a payload timestamp on which no watermark can be declared from an inferred schema — so refusing would remove a capability that works. An `OVER` window is the opposite case and *is* classified as a user error: the direct reader has no `OVER` at all, so falling back there would return rows that silently ignore it.
  - **`extractPrimaryTable()` drives auto-registration**, not a bare `FROM` match: `FROM TABLE(TUMBLE(TABLE orders, …))` yields the keyword `TABLE`, so a windowed query never registered its topic and the planner's "Object 'orders' not found" was indistinguishable from a typo — which, once user errors stopped falling back, broke windowed reads on unregistered topics outright. The window call is consulted first because it carries the real name.
  - **SQL comments**: `--` line comments and `/* */` block comments are stripped before any keyword checks. A query beginning with a comment line is valid.
  - **Common table expressions** run: `SqlStatements.withoutLeadingCte()` strips a leading `WITH … AS ( … )` chain before every keyword check (whitelist, SELECT branch, auto-registration, job-mode split), because all of them are `startsWith` and a CTE therefore came back as "Only SELECT, EXPLAIN and CREATE TABLE statements are allowed" — a message that reads as a security restriction rather than a gap in the guard. It **fails closed**: an unrecognised shape is returned unchanged and stays refused. Auto-registration had to follow (it bailed on anything not starting with SELECT, so a CTE would have cleared the whitelist only to hit "Object not found"), and a CTE **never falls back to the direct reader** — that reader regex-matches a name out of `FROM` and would return rows that silently ignore the `WITH` clause.
- `FlinkWarmupService` — runs **one throw-away query after startup** so a user's first query does not pay for the planner waking up. The cost was measured, not assumed, against the embedded runtime: the first SELECT of a process takes **~5.5 s** where a warm one takes ~1.2 s, and that ~4 s is one-off (Calcite class loading, Janino codegen of the metadata handlers, the first job graph). Without it, the Run button spins for five seconds once per deployment — on the gesture that forms an operator's first impression. Three choices are load-bearing. The probe is a **table-less `SELECT 1`**: an `EXPLAIN` was measured too and only gets the first query to ~3.0 s, because the cost is in code generation and the job lifecycle rather than in parsing, while a full query gets it to ~1.6 s — essentially warm. It carries **no table** so there is nothing to register, nothing to drop, no dependency on a reachable broker at boot, and no probe view left in the catalogue for the schema browser to show (Flink also distinguishes `DROP VIEW` from `DROP TEMPORARY VIEW`, so a view-based probe leaks unless that is respected — one more reason not to create one). And it runs **after `ApplicationReadyEvent` on a daemon thread**, because boot time here is deliberately short and a warmup that delayed readiness would trade a defect for a worse one. The accepted cost: a SELECT takes the runtime's shared read lock, so a user query needing a table *registration* in the first seconds can queue behind the probe — bounded by the coordinator's own wait budget, and it is the very query that would otherwise have paid the 4 s itself. Everything is best-effort: a failed probe is logged and forgotten, never able to affect startup. Off with `explorer.flink-warmup-enabled: false`. **And what it proves is narrower than it was credited with.** `SELECT 1` is table-less, runs at parallelism 1 and needs one slot, so it establishes that a job graph deserializes behind `JarLauncher` — real, and the reason `release-image` keeps asserting it — and *nothing* about reading a topic. Two defects lived here for months underneath a probe reporting success at every boot: a generated table option this connector refuses (never validated at `CREATE TABLE`, only when a source or sink is built, so a probe with no table can never provoke it) and a job asking for more slots than the embedded cluster owns (one slot is always free). Both degraded every SELECT to the direct reader in silence. The assertion that catches them belongs where a broker and seeded topics already exist — `ci.yml`'s `docker` job posts a plain SELECT on a demo topic and requires `engine: FLINK`, on the engine rather than on latency, since a gate that flakes is a gate people learn to ignore. **`getHeldJobs()` sweeps the registry**, which it did not before: a finished query stayed in `heldJobs` until something swept it, and the three callers of that method are the ones that *act* on the answer — `POST /api/config` counts them to refuse a cluster repoint with 409, the lineage graph draws a node per job, and the KPI suggestions derive a pipeline edge from each. A query the user ran and watched finish went on refusing their next config save until some other screen happened to call the sibling that swept. It stayed invisible because the Dashboard polled that sibling every 30 s, so an open browser hid it — which is why it surfaced only when a warmup probe ran with no browser open at all. The sibling has since gone with the Dashboard's job table, which makes `getHeldJobs()` the only sweeper there is. - `KafkaAdminService` — Kafka AdminClient wrapper for metadata and topic ops. `getEarliestRecords` / `getRecentRecords` share one `drain()` loop whose termination is driven by the **end offsets**, never by an empty poll: a fresh consumer's first poll very often returns nothing while metadata resolves, and both methods used to treat that as "topic exhausted" — the audit then judged a topic on a handful of records and reported a confident zero. **What it compares against those end offsets is a cursor of its own** (`hasUnreadOffsets(partitions, endOffsets, nextOffsets)`, pure — it asks the consumer nothing), seeded from the offsets the caller seeked to and advanced only by records the loop was actually handed. It used to be `consumer.position(tp)`, which is not a consumption watermark but the client's *fetch* position: the consumer prefetches in the background across every assigned partition and advances it as responses are buffered rather than as records are returned — measured on `KafkaSnapshotReader`, which had the same comparison, one poll delivered two records while `position()` reported the log end for all eighteen partitions. A single-partition read masks it, which is how it survived here; both callers assign **every** partition of the topic, and that is how the audit samples one — duplicate detection, poison detection, format inference and schema inference all read through this method — so a topic with enough partitions truncated the sample and the audit reported a confident number about records it never saw. Both call sites therefore *state* where they seeked rather than letting the loop ask: `getEarliestRecords` seeks the beginning offsets explicitly instead of through `seekToBeginning`, so the map it hands `drain()` is the one it applied, and the timestamp branch of `getRecentRecords` seeks a partition whose records all predate the instant asked for to its **end offset** — a number `drain()` can compare — instead of a `seekToEnd` whose result would have to be read back. **When that end offset is itself missing there is no number, and none is invented**: the fallback was `getOrDefault(tp, 0L)`, which on the one branch whose whole purpose is "read nothing from here" says the exact opposite — seek to the beginning and return the entire partition, every record of it older than the filter. Such a partition is now seeked to its end the lazy way and left out of the cursor map, so it carries no bookkeeping entry rather than a wrong one. `KafkaSnapshotReader.seekToTimestamp` had the identical line and the identical fix, with `auto.offset.reset: earliest` in that mode making a skipped seek land in the same wrong place. The **LATEST_N branch of `getRecentRecords` had the same default and a different symptom**: "the last N records" is measured backwards from the end, so with `endOffset` defaulting to 0 the clamp `max(beginning, 0 − n)` collapsed to the beginning and a partition whose end could not be read answered a question about the *newest* records with its oldest ones — a wrong answer where the other was a missing one. It contributes nothing now, on the same rule. A cap of 3 consecutive empty polls and a 20 s budget remain as safety nets against a slow broker. `getClusterDetails()` also reports the KRaft controller quorum (`describeMetadataQuorum`: leader, epoch, high watermark, voters/observers with lag) under `kraftQuorum`, and all client groups (`listGroups`, Kafka 4 admin API — types CLASSIC / CONSUMER (KIP-848) / SHARE (KIP-932) / STREAMS with state) under `groups` — each absent when the broker doesn't support the API, and the Cluster page hides the section accordingly. `getTopicConsumers(topic, maxGroups)` (`GET /api/topic/{name}/consumers`) reports **who reads a topic and how far behind they are** — the one thing a Kafka UI is asked for that this app had no answer to, since `listGroups` gave a name, a type and a state and nothing else. Four admin calls **in this order**: list the groups, describe them (members and assignments), read their committed offsets *restricted to this topic's partitions*, and only **then** the log end offsets — reading the ends last means a consumer committing between the two calls can only make the lag look larger, so a negative lag that survives is a real one (an offset reset past the end, a topic recreated under the same name) and is reported rather than clamped. **A partition with no committed offset carries `null`, never 0**: "caught up at the beginning" is the opposite of "nobody is reading this partition", and `partitionsWithoutCommit` counts them separately from `totalLag`. SHARE groups (KIP-932) are excluded — their state lives in the share-group coordinator, not in `__consumer_offsets`, so listing them would only manufacture "0 lag" rows. **The application's own groups are excluded too, and the response says how many** (`ExplorerConsumerGroups`): every internal reader assigns and seeks explicitly and never reads a committed offset, yet seven of them left `enable.auto.commit` at its default — **true** — so each metadata read, timestamp scan and sample fetch committed offsets under a fresh random group id and left a consumer group behind for `offsets.retention.minutes`. The Dashboard polls every 30 s and drives two of those readers, so an idle browser tab manufactured a few thousand phantom groups a day; each then had committed offsets, no member and a live topic behind it — the exact shape `ConsumerGroupLag.health()` grades `STALLED` and `AuditService` reports as a **critical** finding. The app was inventing critical findings about its own leftovers, while crowding the real groups out of a panel capped at 200. **The prefix those internal groups carry is configurable** (`explorer.consumer-group-prefix`, default `kafka-explorer-`): the ids are visible on the user's cluster — in `kafka-consumer-groups.sh`, in someone's monitoring, under whatever naming convention an organisation applies — so a deployment that must call them `acme.kse.` can. Three rules keep it from becoming the defect it exists beside. It renames **only** what this application creates for its own reads, never a group of the user's pipelines and never the `flink_table_*` id of generated DDL, which is copied into jobs this application does not run. An absent, empty or unusable value falls back to the default with a WARN naming the property (`resolvePrefix`), because an empty prefix is not a shorter name — it is internal readers that no longer look like ours, which the audit then reports as third-party consumers stalled on a backlog — and a value with no trailing separator gets one, since `myapp` would otherwise yield `myappmetadata-<uuid>`. And **the default stays recognised whatever the property is set to**: adopting a prefix must not disown the groups the previous configuration left on the cluster, an unrecognised leftover of ours being exactly what `health()` grades STALLED and the audit reports as critical. It is applied from `ExplorerConfig`'s `@PostConstruct` rather than a listener of its own, because `MetricService` and `FieldMappingStore` both open a consumer while restoring state at boot and both inject that bean — so it is constructed before either of them exists, and no consumer can be named while the prefix is still unset. `ExplorerConsumerGroups.configure()` also sets **`allow.auto.create.topics=false`**, which is the same rule one level down: that setting defaults to *true*, so asking a consumer about a topic that does not exist — a `partitionsFor` on a name typed into the search box, a subscribe to a topic deleted since the catalogue was cached — **creates** it, with one partition and the broker's defaults, on the cluster under exploration. This application makes exactly two deliberate writes to a user's cluster (`InternalTopicProvisioner`, `ExplorerGroupCleanupService`), both opt-out and both loud; a read inventing a topic is neither. It is also what lets the record fetchers take their partition list off the consumer instead of paying for a separate `describeTopics`. `ExplorerConsumerGroups.configure()` is the only way an internal consumer is named — `KafkaSnapshotReader` was still setting the id in one method and the no-commit rule in another, which is correct until someone edits one of them — and it sets the group id and `enable.auto.commit=false` together so the two cannot drift apart; `isExplorerGroup()` also recognises the six historical naming schemes, so groups an older build already left on a cluster are not mistaken for third-party consumers, and `flink_table_*` — the group id `DdlGeneratorService` writes into every generated Flink table, which is a group this application asks Flink to use on the user's cluster and which nothing had ever counted as its own. **That last one is ours by origin but not ours to delete**, which is why `isOwnReaderGroup()` exists beside it: every id the narrower predicate matches was minted by a `KafkaConsumer` inside this JVM, so nothing else can be using it, whereas the DDL is published *to be copied* into the user's own Flink jobs — an idle `flink_table_*` group may be their stopped production job rather than our leftover. `ExplorerGroupCleanupService` filters on the narrow one; excluding a group from "who consumes this topic" and deleting it off someone's cluster are not the same question, and answering both with one predicate would have broken the rule that cleanup states for itself. That DDL now pins `properties.enable.auto.commit = 'false'` besides: the connector only commits on a checkpoint, which a bounded local SELECT never takes, but a committed offset under a memberless group is exactly the phantom-critical shape above. **One unreadable group costs one row, not the answer**: both admin calls are awaited per group (`describedGroups()`, `partitionsToOffsetAndMetadata(group)`) rather than through `.all()`, which fails as soon as any single group does — that used to cost the members and assignments of all two hundred, and membership is what separates STALLED from BEHIND. A group whose offsets cannot be read becomes a `ConsumerGroupLag.failed(...)` row (health UNKNOWN), never a silent drop: "could not be read" and "does not read this topic" are different answers. Only when *no* group answers does the call still report `unavailable`. **The cap cuts by relevance, not alphabet** (`isDormant`): groups with members are read first, EMPTY/DEAD ones last — the old alphabetical cut admitted its own flaw in its warning ("a group past that point would not appear here even if it were the one lagging"), and it is the same defect the Stream Flow trace was fixed for. Bounded by `explorer.consumer-group-max-groups` (200), and the response carries `groupsExamined` / `groupsEligible` / `groupsInCluster` / `truncated` / `available` / `warnings`, because an empty list must not read as "nobody consumes this topic" when it means "we read two hundred of three thousand groups". **`groupsEligible` is the honest denominator** — groups left after the share and explorer exclusions, before the cap; the panel used to divide a post-exclusion numerator by the cluster's raw total and announce "all 3 of the cluster's groups read" on a cluster of fifty. **`available` is the one thing the counts cannot express**: a failed read and a cluster with no group both come back as zero of zero, so the panel rendered "The cluster has no client group at all" above "No consumer group reads this topic" — two confident claims about a question that was never asked — and the Prometheus exporter could not tell whether to keep a gauge's last value or drop it. **Membership that was never read is `membersKnown: false`, not zero members**: a group whose `describeConsumerGroups` failed still has its lag (the offsets are a separate call) but arrived with no assignments, and `health()` graded that STALLED — "nothing is draining it", concluded from a call that never answered, which the audit then reported as **critical**. `describeConsumerGroups` is silent for a STREAMS group in particular, so a healthy Kafka Streams application was reported as an abandoned backlog on every topic it reads; STALLED now requires `membersKnown`. Rows whose lag could not be read sort **first**, not among the caught-up ones their zero would otherwise place them with. The cache key carries `maxGroups` alongside the topic. **`groupSnapshot(maxGroups, restrictTo)` is the same read, taken once**: the audit called `getTopicConsumers` per topic, and each call re-listed every group of the cluster, re-described up to two hundred and re-read their offsets — on three hundred topics that is three hundred `ListGroups` and sixty thousand `OffsetFetch` round trips for an answer that does not vary by topic, with the 30 s cache (keyed per topic) expiring many times over during the run. `getTopicConsumers(topic, snapshot)` derives one topic's view from it, reading only that topic's end offsets, and still reading them **last**. The single-topic path still restricts its offset fetch to that topic's partitions, which is why `resolvePartitions` runs *before* the snapshot is taken — resolving them afterwards leaves nothing to restrict it with, and one topic's question fetched every group's offsets on every topic (`restrictsTheOffsetFetchToTheTopicItWasAskedAbout` pins it, since nothing in the structure of the code enforces it). **A failed read is not cached** (`unless = "!#result.available()"`): a brief coordinator blip otherwise froze the failure for half a minute, and the panel's Refresh button — the one gesture that exists to retry — replayed the cached error instead of asking again. `pingDetail()` is the reachability probe **with its reason** (`ping()` is the boolean shorthand kept for callers that only need the flag): a bare boolean meant every caller could report "offline" and none could say whether the broker was down, the bootstrap address wrong, or the client unauthorised. `setAdminClientForTest()` is the test seam (`KafkaAdminServiceConsumerLagTest` drives a mocked AdminClient).
`getTopicActivity(topics, windowMs, buckets, maxLookups)` (`GET /api/dashboard/activity`) is **what each topic produced over a window, bucket by bucket** — the sparkline in the dashboard's topics table, and the one question this app could not answer without opening a consumer per row. It is built from `listOffsets` alone: one request per bucket boundary covering every partition of every topic asked for, **all issued before any is awaited**, and consecutive offsets subtracted. Nothing reads a record, nothing joins a group, and the wall clock is one round trip's latency rather than sixty. What it therefore counts is **offsets produced, not records present** — a transaction marker takes one, and a record later compacted away still counts, because it was produced; that is the right answer to "was this topic busy" and the wrong one to "how many records are in there", which is `getTopicsSize`'s question. The window is **aligned on the bucket width and ends at the last completed bucket**, so two polls inside one bucket describe the same boundaries — which is what makes the curve stop wobbling as the clock moves, makes the read cacheable at all, and keeps the final point from being a half-filled bucket that reads as a collapse in traffic. Three things are stated rather than assumed, all of them the same rule the consumer-lag work was done for — a measurement that could not be taken must not come back as a zero, because on a curve a zero *is* an answer. **`coveredFromMs`** is the instant from which the series is complete: retention deletes the oldest records and a boundary older than the log's first surviving record resolves to that record, so the buckets before it would read as a quiet night; non-null means the earlier counts are floors, and the browser greys that stretch instead of drawing it. **`partitionsMeasured` against `partitionsTotal`** says the same about a partition that did not answer — each partition is awaited on its own future rather than through `.all()`, so one silent partition costs its contribution and not the topic's whole curve. And a topic where *nothing* could be read comes back `available: false` with its reason, never a row of zeros. Bounded twice, because a curve per row is affordable only if it scales with what is displayed: `explorer.activity-max-topics` (the dashboard asks for the rows it shows) and `explorer.activity-max-lookups` — partitions × boundaries, the real unit of work, since a sixty-partition topic costs sixty times a single-partition one — with whatever a budget cut **named** in the response's warnings, an absent curve otherwise reading as a topic that produced nothing. Cached 30 s like the rest, and **a failed read is not cached** (`unless = "!#result.available()"`): the dashboard's refresh is the gesture that exists to retry.

**A question the broker can answer from metadata is never answered by reading records.** That rule was already followed by `getTopicActivity`, which is why the sparkline costs a burst of `listOffsets` and no consumer, and it was followed by nothing else — three of this service's reads opened a `KafkaConsumer` and pulled record batches to extract numbers the offset index already holds. **`getTopicsLastMessageTimestamps` was the expensive one**, and it is the dashboard's "Last Message" column, so it ran for *every topic of the cluster* on every poll past the 30 s cache: it assigned every non-empty partition of every topic, seeked each to `end - 1` and polled until each had answered — to keep one `long` apiece. A fetch does not return one record, it returns the batch that record sits in, up to `max.partition.fetch.bytes` (1 MiB by default) **per partition**, so a three-partition cluster of three hundred topics dragged the tail of nine hundred partitions across the network to render a column of relative dates. `ListOffsets` with `OffsetSpec.maxTimestamp()` (KIP-734) states the largest record timestamp a partition holds, from the broker's own index: one request for the whole cluster, no consumer, no record. It is also the better measurement — the old code read the record at the *end* of the log, whose timestamp is the newest only when producers stamp in order. The spec needs a broker at Kafka 3.0 and this application supports 2.1+, so an `UnsupportedVersionException` is not a failure but a route: `lastTimestampsByPolling` is the previous implementation, kept whole, and it is the only thing that opens a consumer now. **`getLatestMessage` is the same idea where a record really is wanted**: the same spec says which partition holds the newest one and at which offset, so the read assigns *that* partition instead of every partition of the topic and discarding all but one. **And `readRecordCounts` needed no consumer at all** — it read `beginningOffsets`/`endOffsets` and not a single record, so the client it opened was pure overhead on the dashboard's other bulk call; both bounds go through the admin client now, issued before either is awaited so they overlap, and awaited per partition so one that does not answer costs its own contribution rather than the batch. `KafkaAdminServiceLastMessageTest` pins the column against a mocked `AdminClient` and nothing else — a read that went back to polling answers nothing there — and it names the spec explicitly, since "answers correctly" would also be true of a much more expensive route. Five of its six cases were verified to fail against the revision they describe.

**`describePartitions` is where a topic name becomes a partition list**, for all three bulk reads. Two of them — the counts and the timestamps, which is to say both halves of the dashboard's table — did their own `describeTopics(...).allTopicNames()`, which fails *wholesale* when one name is unknown; and a topic deleted between the `listTopics` that named it and the call that uses it is an ordinary race on a live cluster, so one stale name emptied the whole table. `getTopicActivity` had already been fixed for that, alone, with per-topic futures and a loop of its own — that loop is this method now, so the rule holds for the two reads that lacked it rather than being restated a third time.

**The per-topic record fetchers stopped asking the admin client where the partitions are.** `getEarliestRecords`, `getRecordsWithPredicate` and `getLatestMessage` each opened with `describeTopics(topic)` and a five-second await purely to turn a name into a partition list, while the consumer beside them fetched metadata for that same topic anyway the moment it was assigned — one round trip and one client's worth of waiting, on every sample, and the audit takes a sample per topic of the cluster. `partitionsOf` reads it off the consumer (`partitionsFor`, bounded to the same five seconds the await gave, because the no-argument overload waits a minute). That is safe only because every internal consumer now carries `allow.auto.create.topics=false` — see `ExplorerConsumerGroups.configure`, where a read that invents a topic on the user's cluster is the failure it prevents.

**The three per-topic record readers can borrow a consumer instead of building one** (`KafkaConsumerPool`, `explorer.consumer-pool-size`, **0 = off, which is what ships**). Constructing a `KafkaConsumer` is a TCP connect, an ApiVersions exchange and a metadata fetch — plus a handshake and an authentication round trip on a TLS or SASL cluster, which is where the saving actually lives — and the audit reads once per topic, so that is the run it is for. It is **off by default and that is a statement about evidence, not about the code**: the saving's size depends entirely on the deployment, nothing here has measured it against a real cluster, and what a mistake costs is not a slow read but a *wrong* one — a client handed out with a previous read's assignment, paused partitions or buffered records answers a question nobody asked, which from outside is indistinguishable from an empty topic. Three rules make a lease safe: it is **exclusive** (a consumer is out of the pool while held, since a `KafkaConsumer` is single-threaded); it is **reset before anyone else sees it** — every paused partition resumed and then unsubscribed, both stated rather than inferred, because the readers now leave paused partitions behind deliberately and the pool's own test failed against the version that only unsubscribed; and **a read that threw does not return its consumer**. `init()` rebuilds the pool, which is also the repoint hook — an idle client carries the bootstrap address it was built with. The unit tests drive a `MockConsumer`, so `KafkaClusterIntegrationTest` is where the enabled path runs at all, and what it asserts is that a pooled read returns *the same records*, not that it is faster.

**`deserializeValue` keeps one Avro writer per schema.** A `GenericDatumWriter` resolves the schema when it is built and the JSON encoder allocates its own output stack — three objects and a schema walk per record, on the path the audit drives ten thousand times for one topic's duplicate scan. The writer is stateless once built and shared; the encoder is not and stays per call. Bounded on the schema, since a topic whose producers evolve it would otherwise grow the map without end.

**`offsetRange` asks for a partition's two bounds together.** `Consumer.beginningOffsets` and `endOffsets` each block, so a caller needing both waits two round trips in series — which is what placing a single record by its coordinates used to cost. These are futures, issued before either is awaited. It answers `null` rather than a range when there is no admin client or the broker did not answer, and the caller falls back to the consumer: "we could not ask cheaply" must not read as "this partition holds nothing".

**`drain()` no longer re-reads the end offsets its caller is holding.** Both callers read them to decide where to seek and the loop then asked the broker for the same numbers again: a second `listOffsets` per sample. The overload that takes them also means the cursor is compared against the same instant the seek was computed from. **It also pauses a partition it has finished with**: the fetcher keeps a request in flight for every assigned partition, so a drained one holds each poll for `fetch.max.wait.ms` with nothing to deliver while the partitions that still have records are already back. Nothing is ever resumed — the consumer is closed when the read ends, and a partition that reached its end offset does not un-reach it. Same rule, same reason, as `KafkaSnapshotReader`, which had it first.

Heavy metadata calls are Caffeine-cached (30s TTL): `listTopics` (`kafkaTopics`), `getTopicDescriptor` (`topicDescriptor`), `getTopicsSize` (`topicSizes`), `getTopicsLastMessageTimestamps` (`topicLastMessages`), `getClusterDetails` (`clusterDetails`), `getTopicConsumers` (`topicConsumers`), `getTopicActivity` (`topicActivity`) — cache names are registered in `WebConfig`. `topicPartitions` is registered there too but is read manually rather than through `@Cacheable`: it is consulted from *inside* this bean, where self-invocation bypasses the Spring proxy and the annotation would do nothing at all, and it is deliberately not shared with `getTopicActivity`, which reports a reason per topic it could not describe and has none to give on a cache hit. Recent-record seeks are clamped to the partition's beginning offset (retention-trimmed topics would otherwise trigger an `auto.offset.reset` to latest and return nothing).
- `TopicSearchService` — bounded server-side scan behind `POST /api/topic/{name}/search`. Assigns the partitions directly (fresh group, no commits — a search never moves anyone's offsets), seeks per `from` (EARLIEST / LATEST / LAST_N — the most recent records, spread over the partitions and clamped to the beginning offset — / TIMESTAMP / OFFSET) or per resume cursor. **A time window raises LAST_N's floor rather than replacing it**: seeking to the start of the window and reading forward (what TIMESTAMP does) spent the record budget on the window's *oldest* records, so a match from a minute ago was missed while the scan worked through messages from an hour before. It and reads until one of three budgets is spent (`explorer.search-max-hits` / `search-max-scan` / `search-timeout-ms`). The response carries `scanned`, `matched`, `stopReason`, `exhausted` and a `nextCursor` per partition, so the UI states what was covered and can continue — a search is never silently partial. `addPathWarnings()` turns the matcher's outcomes into warnings ("none of the 50 records scanned is JSON"), so zero hits on a path search says which kind of zero it is, and `looksBinary()` reports the records that are not text at all (a protobuf blob read as UTF-8 is replacement characters — no text search can ever match it). **`keyPartitioning`** narrows an exact KEY search to the one partition the default partitioner would have chosen (`murmur2(key) % partitions`): a twentieth of the work on a twenty-partition topic, unsound under a custom partitioner or a changed partition count, hence opt-in, restricted to KEY/EQ, ignored-with-a-reason elsewhere, and always stated in the warnings — a narrowed scan that found nothing is not the same answer as a full one that found nothing. **The scan stops on what it was handed, and pauses what it has finished with.** `reachedEnd` compared `consumer.position(tp)` against the end offsets — the client's *fetch* position, which advances as responses are buffered rather than as records are returned, the defect `TopicReadCursor` exists to state once — so a scan could announce `exhausted` with records still in flight. It reads the cursor the response already carries instead, and a partition the scan has read to its end is `pause()`d: the fetcher keeps a request in flight for every assigned partition, so a drained one holds each poll for `fetch.max.wait.ms` while the partitions that still have records are already back — on a `LAST_N` search over unevenly filled partitions, that is most of the wall clock. `readRecord` places its record with **one** round trip rather than two, through `KafkaAdminService.offsetRange` — the consumer's two offset getters block one after the other, and both bounds are needed before anything can be decided. `createConsumer()` is the test seam (`TopicSearchServiceTest` drives a `MockConsumer`).
- `MessageMatcher` — the predicate behind **every** search (topic search and stream-flow trace alike), built once per scanning thread. CONTAINS / REGEX work on the raw value (no parsing); FIELD walks the payload with a streaming parser, pruning any subtree whose path can no longer reach the target, and compares with EQ / NEQ / CONTAINS / REGEX / GT / GTE / LT / LTE / EXISTS. Paths use dot notation with `[]` for "any array element" (JSONPath is accepted and normalized via `PayloadDigestService.normalizePath`). XPATH and JSONPATH hand the payload to a full expression engine (DOM / Jayway) for what the dot walker cannot express — predicates, axes, recursive descent — so a simple path never pays for the general engine. KEY mode compares the record key itself: a text search finds it as a substring anywhere, which is not what "find record X" means and is not enough to justify reading a single partition. **Kafka headers are searchable**: HEADER mode compares one named header (matched exactly, then case-insensitively) with the usual operators, and `searchHeaders` widens a text/regex search to every header value — correlation ids very often travel there (`correlation-id`, W3C `traceparent`) and a search that never looks reports a confident "not found". Default off for a topic search (turning it on silently would change what an existing search returns), default on for a trace. `evaluate()` returns a `MatchOutcome` (MATCH / NO_MATCH / FORMAT_MISMATCH / PARSE_ERROR) so a caller can say *why* a path search found nothing — a payload it could not be applied to is not the same answer as a miss; `matches()` is the boolean shorthand. **Not thread-safe** (XML factory, DocumentBuilder, XPathExpression). A malformed payload simply doesn't match — one bad record must not fail a scan.
- **`LogSafe` is the only place a value is neutralised before it is logged**, and it has **three functions rather than one** because what this application logs does not have one legal alphabet. `name()` is the strict allow-list (`String.replaceAll("[^\\w.\\-]", "_")`) for a Kafka topic, a Flink table, a session / audit / mapping id — the alphabet of those *is* `[a-zA-Z0-9._-]`, so nothing legitimate is replaced. `slug()` adds `/` and `:` for a model identifier or provider label: `name()` would render `openai/gpt-4o-mini` as `openai_gpt-4o-mini`, which is not what the operator typed, in the line that exists to show it to them. `text()` flattens control characters to a space for **free text whose readability is the point** — a SQL query, an exception message — and is deliberately **not** a recognised sanitizer: the model admits only the negated-class `String.replaceAll` form, so a deny-list falls outside it, and putting a SQL query through `name()` would satisfy the check and destroy the log line, which is removing a deliberate behaviour to silence a tool. The findings that survive on those calls are therefore known and described rather than ignored. It lives in its own package because it is called from `service`, `web` and `parser`; it used to be a method **on `FlinkSqlService`**, reached across packages as `FlinkSqlService.sanitizeForLog(slug)` from `OpenRouterModelCatalog` — the same "one definition" argument that produced `SecureXml`. The measured history is worth knowing before touching it: the fix that introduced the allow-list took the tree from 27 `java/log-injection` findings to 24, and by the time the count was next *read* it was back to 28 — the four additions being `OpenAiCompatibleLlmClient` (×2), `SpectraLlmClient` and `AnthropicLlmClient`, i.e. exactly the LLM clients five consecutive pull requests had touched. Nobody noticed because nothing made the number legible; that is the gap `codeql.yml`'s log step closes, and it is why that step and this class belong to one another.
- `SchemaInferenceService` — samples messages and delegates to `JsonSchemaInferrer` / `XmlSchemaInferrer` / `AvroSchemaInferrer` (inferred column order is deterministic — `LinkedHashMap`)
- `DdlGeneratorService` — auto-generates Flink `CREATE TABLE` DDL from inferred schemas. `maskSensitiveProperties()` (static) redacts credentials (`*password*`, `*secret*`, `sasl.jaas.config`) and MUST be applied to any DDL returned to the UI (`/api/topic/{name}`, `/api/topic/{name}/ddl`, `/api/query/ddl-preview`, lineage `SHOW CREATE TABLE`) **or written to a log**; internal table registration uses the unmasked DDL. The log half was missing and is the one that had actually leaked: `FlinkSqlService`'s auto-registration wrote the raw DDL — every Kafka client property, so the SSL passwords and the Confluent `sasl.jaas.config` secret — into `logs/kafkaexplorer.log`, a named volume in every stack and the first file anyone pastes into a bug report. At DEBUG only, which is exactly the level an operator turns on to find out why a query failed, i.e. when that line runs. `theLoggedDdlCarriesNoCredentials` pins it by reading the appender rather than by checking that a function was called. Note that **CodeQL does not recognise the masking as a sanitizer** — `SensitiveLoggingQuery.qll` admits only a `substring` of 7 chars or fewer, an encryption/digest call and a couple of type sanitizers as barriers, so no redaction function can ever clear it. Its 14 `java/sensitive-log` findings are therefore unchanged by the fix (measured: 72 findings before, 72 after), and the four on the auto-registration lines are false positives to be dismissed rather than coded around. The exception path beside them was checked rather than assumed: a DDL that fails to register comes back as Calcite's own "Unknown identifier 'X'" with a line and column, so neither `e.getMessage()` nor the `AutoRegResult.fail` message it feeds carries a credential. What *is* fixable there is `java/log-injection`, and that is what `LogSafe` (below) exists for. **A format option carries the `value.` prefix when the format does** — and that is enforced by the connector, not by taste. The generated DDL declares `'value.format' = 'json'` and wrote `'json.ignore-parse-errors'` bare, which `FactoryUtil.validateUnconsumedKeys` rejects; the same rule applies to `'value.avro-confluent.url'` (by rule, not measured — no stack here carries a Schema Registry). What made it invisible is *when* it is refused: never at `CREATE TABLE`, which validates no option, but the first time Flink builds a source or a sink from the table. So registration succeeded, every JSON topic's table was unusable by the planner, and the SELECT path swallowed it whole — an unconsumed-option `ValidationException` is an engine failure, so the query fell back to the direct reader and returned rows without JOIN or subquery support, three of them enough to disable the planner for the rest of the process. `INSERT INTO`, which has no fallback, answered 500. Asserted in `KafkaClusterIntegrationTest` and nowhere else: a string assertion on the generated DDL pins whatever was written, where the fact under test is that *Flink* accepts the key. `pages/metricsEditor.ts` writes the bare key correctly, because its template declares `'format'` rather than `'value.format'`.
  - **The generated `event_time` carries a watermark, so it is a time attribute.** `WATERMARK FOR \`event_time\` AS \`event_time\` - INTERVAL '5' SECOND` sits in the column list beside the metadata column it declares — and only when this generator owns that column, an `event_time` coming from the payload being of a type nobody here chose (usually `STRING`), on which the same clause would produce a DDL Flink refuses and a topic that no longer registers at all. Without it the column resolved as a plain `TIMESTAMP(3)`, which is not a time attribute, and the planner refused **every** event-time construct over it: an event-time `OVER`, an `ORDER BY` on the timestamp (already reported as a user error by its own wording), an interval join, and the four window table functions — those last now reaching the planner only when the statement bounds its own scan, since a window over a topic is routed to the direct reader before the planner is asked. The application ships a Window Assistant that writes exactly that query over exactly that column, and a Help page whose window chapter is built on it, so the feature had never once run on the engine it documents — the refusal fell back to the direct reader, which approximates `HOP`, `CUMULATE` and `SESSION` as tumbling windows, and said so in a Calcite plan dump. Five seconds of lateness is the value `pages/metricsEditor.ts` already writes into the DDL template it offers, and the one the connector's own documentation uses; no deployment has asked for another, so it is a constant rather than a property nobody could set on evidence. Two tests measure it from both ends: `DdlGeneratorServiceTest` that the clause is written (and not written for a payload column), `FlinkDdlValidationTest` that **Flink resolves it** into a watermark spec on `event_time` — a watermark expression over the wrong type parses and fails at resolution, so a string assertion alone would prove nothing. `KafkaClusterIntegrationTest.aWindowOverTheGeneratedTablePlans` closes it against a real broker through `EXPLAIN`, deliberately: a window *executed* over an unbounded Kafka source never ends — its last window closes only when later records arrive — so it would spend its budget and fall back whatever the watermark says, while `EXPLAIN` stops at the plan and therefore answers exactly the question asked.
- `AuditService` — cluster health checks run on a dedicated single-thread executor (`startAudit` submits explicitly — do NOT reintroduce `@Async`, the self-invocation bypasses the Spring proxy and blocks the HTTP thread); per-topic audits fan out on a bounded 4-thread pool. Exact counts go through the direct SELECT engine (`COUNT(*) AS metric_value`, first numeric value of the row); duplicate detection and flow latency are computed **in-process** over fetched messages (key extraction via `MessageFieldExtractorService`) because the direct engine supports neither subqueries nor JOINs. Reports persist to `internal.audit.history` via a shared lazy producer. Retention is bounded (`MAX_RETAINED_RUNS` = 20) — the runs map used to grow forever. **The application's own state topics are out of scope**: the run listed every topic and filtered only on the prefix an operator asked for, so `internal.metrics.config` — a keyed store, therefore full of repeated keys — was reported as a topic with duplicates, and the run wrote its own report to `internal.audit.history` while that topic was being read. Same defect `ExplorerConsumerGroups` removed for the groups, the app reporting its own leftovers as findings, left standing for the topics. Naming their prefix explicitly still audits them — an explicit request is honoured, the rule the data model's typed `internal.*` already follows — and what was left out is named in `globalStats.scopeNotes`, since an excluded topic that says nothing about itself is indistinguishable from one audited and found healthy. Cluster-level findings go into `globalStats`: `getLaggingFeatures()` (KafkaAdminService, `describeFeatures`) compares finalized vs supported feature versions, and a lagging `metadata.version` adds a `metadataVersionWarning` (incomplete KRaft rolling upgrade — surfaced as a banner on the Audit page).
  - **One read per topic**: format detection, schema inference and the poison check share a single sample, fed to the `detectFormat(topic, samples)` / `inferSchema(topic, format, samples)` overloads — each used to open its own KafkaConsumer for the same ten messages. That sample now comes out of the **duplicate scan's own records** rather than a second read of the same end of the same topic, so an audited topic is read once rather than twice; `detectDuplicates` takes the records instead of fetching them, which is also why the wide read has to run first (the scan needs the schema, and the schema needs the sample). **Only when both are reading the same end**: `explorer.audit-duplicate-scan-from: EARLIEST` points the duplicate scan at the oldest surviving records, and on a topic with retention those answer a different question from the one every other check here asks — so under EARLIEST the two reads stay two reads, which `theSampleIsReadSeparatelyWhenTheDuplicateScanReadsTheOtherEnd` pins. The sample is taken off the **end** of the wide scan, and it is *recent records* rather than *the ten newest*: `drain()` collects in poll-delivery order, which is all the dedicated read it replaces ever promised either. Keep the sample threaded through when touching `auditTopic`.
  - **No check degrades to a silent zero.** Poison detection *parses* (a truncated `{"id":` is poison, first-character checks are not enough) and falls back to the sample's dominant format when schema inference is off; duplicate detection falls back to the Kafka record key when the schema has no id-like field; an exact count that errors reports the reason as a topic issue instead of quietly returning the offset estimate. `globalStats.scopeNotes` states the bounds of each scan (10 000 messages for duplicates, 10 for poison, 1 000 for latency).
  - The in-flight `RUNNING` report is republished after every topic with `phase` / `topicsCompleted` / `topicsTotal`, which is what drives the Audit page's progress bar. `globalStats` also carries `startedAt`, `durationMs` and `options`.
  - Flow latency memoizes `topic → Map<id, first timestamp>` for the run: a topic in the middle of a flow is both a source and a target and was otherwise fetched twice.
  - `FlowAudit.overallHealthScore` is a **0..1 ratio**, not a percentage (the UI multiplies by 100).
  - **Severity is graded**: `HealthStatus` is `HEALTHY < WARNING < CRITICAL` (`max`/`atLeast` helpers), and every finding is a `TopicIssue(message, severity)` — a topic takes the worst severity among its issues. CRITICAL = the audit failed, unparseable payloads, `COUNT(*)` returning 0 on a non-empty topic; WARNING = duplicates (often legitimate), a degraded measurement. `AuditReport` carries `criticalTopicsCount` + `warningTopicsCount`, and `globalStats.healthScore` (0..1, critical −1 / warning −½) is computed server-side so it is frozen into the persisted report. Reports already in `internal.audit.history` still contain the retired `UNHEALTHY` value — a future history reader must tolerate it.
  - **One run at a time**: `startAudit` returns `AuditStart(auditId, started)` and refuses to queue a second scan behind the single-threaded executor; the controller answers 409 with the in-flight id and the UI attaches to it. The slot is released in a `finally` — a failed or cancelled run must not block every later start.
  - **Time budget**: `explorer.audit-max-duration-ms` (30 min default, 0 disables) bounds one run. Past the deadline it stops through the same path as a cancellation and reports `globalStats.stopReason` = `TIME_BUDGET` vs `REQUESTED` — "cancelled" without saying by whom would be misleading. Raising the property beats reading a truncated report on a very large cluster.
  - **Consumer lag is a check, not a number** (`checkConsumerLag`, `consumerLagIssues`). The cluster's groups are read **once and shared across topics** (`KafkaAdminService.groupSnapshot`) rather than once per topic, and re-read when the snapshot goes stale (`explorer.audit-group-snapshot-ttl-ms`, 60 s; 0 takes it once for the whole run). The scope note states whichever applies: committed positions are up to that old while each topic's end offsets are read as it is audited, so a lag can only be overstated, never understated — and none of the reported findings turns on an overstated lag. The TTL exists because *never* refreshing is the other half of the trap: on a half-hour run the lag is overstated by half an hour of traffic, which is safe in its direction and useless in its magnitude. `GroupSnapshotHolder` refreshes under a lock, refresh included — letting three of the four topic workers read a stale snapshot while the fourth re-reads would buy a few seconds of parallelism for a report whose rows were measured against different instants. A topic whose groups could not be read at all now produces a WARNING instead of nothing, which was indistinguishable from "every group here is healthy". **A STALLED finding is also dated**: "4 000 messages behind" is four seconds of traffic on one topic and four days on another, so that one case — and only that one — pays for a second, costlier measurement (`delaySuffix` → `getConsumerTimeLag`, a record read per lagging partition) and the finding carries both numbers. Budgeted per run (`MAX_DELAY_MEASUREMENTS_PER_RUN` = 20, held on `GroupSnapshotHolder` beside the group snapshot) and stated in a scope note; a measurement that fails or is refused leaves the finding exactly as it was, since a backlog whose age could not be read is not a backlog of zero seconds. Deliberately no threshold on the lag itself: a large but draining backlog is ordinary on a live topic, and any number picked would be arbitrary — the same reason a message count moving is not a finding. What is reported is structural, via `ConsumerGroupLag.health()`: `STALLED` (records waiting, no member assigned to this topic — nothing will drain them) is CRITICAL, `PARTIAL` (never committed on some partitions, whose backlog the lag does not count) and `AHEAD` (a committed offset past the end) are WARNING, and a group that could not be read is a degraded measurement rather than silence. `Health` is kept in step with `healthOf` in `topicConsumers.ts`, which grades the same thing for the panel without a round trip.
  - **Duplicates are scanned from the END of each topic** (`explorer.audit-duplicate-scan-from`, `LATEST` default / `EARLIEST` to restore the old behaviour): every other check samples recent messages, and on a topic with retention the oldest surviving records answer a different question. The issue wording and the scope note follow whichever end was actually read.
  - **Cancellation is cooperative**: `cancelAudit` raises an `AtomicBoolean` on the `RunHandle`; the run polls it inside each per-topic task (every topic is submitted to the pool up front, so cancelling cannot un-queue them — the check has to be *in* the task) and before the flow phase. Never interrupt mid-topic: a topic's work is already bounded (500 ms poll loop, 5 s query timeout) and interrupting would abandon a KafkaConsumer or a Flink job. The report keeps the topics already audited, with status `CANCELLED`, `globalStats.cancelled` / `topicsInScope`, and a leading `scopeNote`; `totalTopics` counts what was audited so the KPI matches the table, and `healthScore` is computed over that same subset. In-flight progress carries `cancelling: true` so the UI can say "Stopping…" instead of looking frozen.
  - `totalMessages` sums the per-topic counts actually reported, not `topicSizes`, so the KPI and the table column agree when exact counts ran.
- `AuditHistoryService` — reads past reports back out of `internal.audit.history`, which `AuditService` had always written and nothing ever read. `listHistory()` (Caffeine-cached, cache name `auditHistory`) returns `AuditRunSummary` rows newest first; `findReport(id)` returns the stored JSON. **Bounded and says so**: at most `explorer.audit-history-max-records` (200) records from the end of the topic, with `recordsScanned` / `exhausted` in the response — a list that silently shows 20 of 500 runs reads as "the cluster was never audited before". - `AuditDiffService` — topic-by-topic comparison of two runs (`GET /api/audit/compare?from&to`). - `AuditController` — `@RestController` under `/api/audit` only: `start` (409 + in-flight id when one is running), `status/{id}` (404 on an unknown id), `{id}/cancel` (202 asked / 409 already finished / 404 unknown), `last` (204 when no run yet), `history`, `history/{id}` (404 when outside the scan window), `compare` (404 unknown / 409 legacy shape). - `DataModelService` — builds the deduced data model behind `POST /api/data-model` (`DataModelController`): each selected topic becomes an entity (schema inferred from one shared sample, same discipline as the audit; table name from `DdlGeneratorService.toTableName`), and relations are **deduced lexically, with their evidence stated** — Kafka has no foreign keys, so every edge is a claim carrying a `RelationConfidence` (`HIGH` when the referencing column and the target's own key agree, `MEDIUM` on a name match alone, `LOW` when only a shared key column links them) and a `reason` in plain words. The key column is *detected, never invented* (`primaryKey` is null when nothing id-like exists), words merely ending in "id" (`paid`, `valid`) are not identifiers, and generic correlation fields link nothing unless an entity actually owns the name — the same rule as everything else rather than a hand-kept blacklist. Bounded: **30 topics per run by default and 100 at most** (`DEFAULT_MAX_TOPICS` / `explorer.data-model-max-topics`, the rest named in a warning), 20 s per topic, inference fanned out on a dedicated 4-thread pool under `ShutdownBudget`. The budget is **a per-request choice under a configured ceiling**, not a constant: `MAX_TOPICS` was 30 in Java and 30 again in the browser, so a cluster with forty topics worth modelling needed a rebuild, and the two copies could only drift. `buildModel(topics, maxTopics)` clamps what a request asks for to the ceiling and **says so in a warning** rather than silently analysing fewer topics than were asked for; a request that names none falls back to the default. `GET /api/data-model/limits` (`DataModelLimits`) serves the two numbers so the page reads them instead of carrying a mirror — the ceiling is what bounds the run, so a mistyped 5 000 cannot tie the inference pool up for hours. It also serves `perTopicTimeoutMs` and `inferenceThreads`, which answer a different question: **how long may this request take?** A run is one POST that answers when every topic is inferred, so the browser has to decide how long to wait, and it waited a flat two minutes — survivable while the ceiling was 30, not at 100, where a run whose topics are slow to sample outlives it and the operator is shown a timeout *while the server is still working*. The two constants travel rather than being copied into the page, on the same rule that keeps the per-topic budget out of the build overlay: a UI that copies a server constant lies the day it changes. A topic that yields no schema or whose read fails costs that topic — reported with its reason — never the model. Composite map keys here are joined on **NUL written as the escape `'\0'`, never as the byte itself**: the character is the right separator (no topic name, entity id or column name can contain it), but a literal NUL in the source makes `file` report the file as `data` and `grep -r` skip it with "binary file matches" — which quietly takes it out of every codebase-wide search, this repository's own doc checks included. Three files carried one (`DataModelService`, `draftStore.ts`, `pages/dataModelGraph.ts`'s `relationKey`); the escape compiles to the same character.
- `LineageService` — builds dependency graph (topics → tables → views → jobs); uses `TableEnvironment` (not `StreamTableEnvironment`) — Flink 2.x uses the unified API. **Dependencies come from Flink's own parser**, not from a regex: `dependenciesOf()` runs `TableEnvironmentImpl.getParser().parse()` (under `runtimeCoordinator.runRead`, like every other environment access) and walks the resolved operation tree — `SinkModifyOperation` for the INSERT target, `SourceQueryOperation` for every source however deeply nested, `CreateViewOperation` followed down to the query it wraps, which is the shape `SHOW CREATE VIEW` returns. The lexical scan it replaces was wrong in ways that matter: `FROM TABLE(TUMBLE(TABLE orders, …))` yields the keyword `TABLE` and loses `orders` entirely (the same trap `FlinkSqlService.extractPrimaryTable` had to fix), a quoted identifier carrying a hyphen fails the identifier filter, and only the first `INSERT INTO` of a multi-statement script is ever seen. The regex remains as a **fallback** — a statement referencing a table that no longer exists cannot be resolved, and a graph missing one edge beats a lineage page that errors — and every statement that fell back is named in `warnings`, which the page renders: on a graph, a missing edge and an absent dependency look exactly alike.
- `StreamFlowService` — traces one message key across topics and derives the pipeline it travelled through. **It owns no matching and no scanning**: a trace is a topic search run over many topics, so it builds a `TopicSearchRequest` and delegates to `TopicSearchService` / `MessageMatcher`. It used to carry its own regex + JSONPath + XPath matcher and its own record fetch, which meant a key found by the Topic Explorer could be missed by the trace and every improvement had to be made twice. The search path picks the mode: `header:correlation-id` → HEADER, `/order/id` → XPATH, `$..id` or a filter → JSONPATH, anything else (`$.a.b`, `a.b[].c`, a bare field name) → FIELD; the operator is CONTAINS, or REGEX when `useRegex`. `exactKey` overrides all of it with a KEY/EQ search plus partition targeting, and refuses a search path or a regex rather than silently ignoring one — the key is not inside the payload, and an exact comparison is not a pattern. **Every request field but the key is boxed**: Jackson binds a record through its canonical constructor, so an absent property arrives as `null` and a primitive component failed the whole request with "Cannot map null into type int" — a body as small as `{"messageKey": "ORD-42"}` has to work. **A criterion the user can fix is rejected, never degraded**: an invalid regex used to be caught and dropped, leaving a plain substring search on the regex source; both it and a malformed path now raise `IllegalArgumentException`, validated on the request thread before a single consumer opens, and the controller answers 400 with `{"message": …}` (an explicit body, because `server.error.include-message` defaults to `never`). `MessageMatcher` is not thread-safe, so each topic scan builds its own from the same criteria. The response carries `hits` (per topic: occurrence count, first/last timestamp, partition/offset/key of the first match, payload preview, latency from the previous hop, `occurrencesCapped`), `stats` (topics in scope / scanned / skipped / failed, messages scanned, duration, `truncated`, `stopReason`) and `warnings` — an empty graph has to read as "not in the window I scanned", not as a bare "not found". **One node per topic, chained by first sighting** (tie-broken by name): the old code sorted every occurrence and linked each consecutive pair, so a key seen twice in one topic drew back-edges and topics sharing a millisecond drew a different picture on every run; a hop that goes backwards is reported as clock skew rather than hidden. **Streamed**: `trace(request, listener, cancelled)` reports a `StreamFlowProgress` after every topic and republishes the whole graph — rebuilt by the same `buildResponse` — whenever a topic adds to it, so a partial graph is assembled exactly like the final one and the chain rule lives in one place. Progress follows *completion* order (each worker records itself), not submission order, or one slow topic at the head would hold back the nine that already answered; a partial is `stopReason: RUNNING` with `topicsSkipped: 0` (the topics left are pending, not skipped). `cancelled` is polled inside each topic task — every topic is queued up front, so cancelling cannot un-queue them. **What already completed is kept**: the collection loop waits on the futures but the result is built from the tracker's snapshot, because harvesting the futures threw away topics that had answered before the client hung up. A cancelled run reports `stopReason: CANCELLED` and says how many topics were never read. `validateCriterion()` compiles the criterion without reading anything, so the streaming endpoint answers 400 before opening an event stream it would immediately have to close. Bounded on both axes — `explorer.stream-flow-timeout-ms` (remaining futures are cancelled, and a `supplyAsync` task that has not started never runs; each topic's own timeout is clamped to the remaining budget) and `explorer.stream-flow-max-topics` for a scan with no target topic, which also skips the explorer's own `internal.*` topics — through `ExplorerConfig.isInternalTopic`, where it used to be a `Set.of()` naming two of the three by hand, so `internal.field.mappings` and the demo stack's `internal.demo.seeded` were traced and a configured prefix moved the names out from under the literals. An omitted `maxMessagesPerTopic` floors to 100.
  **Which topics a whole-cluster trace reads is chosen by recent activity**, not by alphabet (`prioritiseByActivity`). It used to be `candidates.sorted().subList(0, maxTopics)`: on a cluster of nine hundred topics a trace read `a*` through `d*` and never touched `orders.*`, so "no flow found" meant almost nothing. `KafkaAdminService.getTopicsLastMessageTimestamps` (Caffeine-cached, one batched consumer) is consulted only when the choice matters — the cluster exceeds the cap, or a time window is set — and then a topic whose newest record predates the window is dropped outright (nothing inside the window could match, and the warning names them) while the rest are read newest-first. A topic with **no** known timestamp is kept and ranked last: unknown is not cold. If the timestamps cannot be read, the alphabetical truncation stands and the warning says so — a degraded choice is still a choice.
  **The topics that were never read are named**, not just counted (`stats.skippedTopics` / `failedTopics`, bounded to 50 while the counts stay exact): "2 skipped (time budget)" left a reader unable to tell whether the two dropped were the two that mattered, and the names are also the exact scope of a resumption.
  **A trace continues instead of restarting**: `priorHits` + `priorCoverage` on the request carry back what an interrupted pass found, the second pass scans only `targetTopics` (the unread ones), and `buildResponse` merges the two sets of hops before applying the *same* chain rule — one graph, one place where chains are built. `mergeHits` keeps the earliest first sighting with its coordinates and takes the **larger** occurrence count rather than the sum, since two passes may have read the same records. The coverage is summed across passes (`StreamFlowCoverage`), because a line reading "2/2 topics scanned" under a chain that rests on two hundred and fifty would be exactly the kind of lie the stats exist to prevent. Note what this deliberately does **not** do: reach further back in history. The per-topic scan is `LAST_N`, so a topic-search cursor points *forward*, past the newest record read — resuming with one would fetch what has arrived since, never older records. Going deeper into the past is what "Max messages / topic" is for.

- `StreamFlowController` — `/api/stream-flow` (whole result) and `/api/stream-flow/stream` (SSE: `progress` / `flow` / `result` / `failed`). The SSE traces run on their own 4-thread pool, never the service's topic workers — a driver waits on those tasks, so drivers occupying those threads would starve the work they wait for. A failed `send` means the client is gone: it raises the same cancel flag the trace polls, so hanging up really stops the scan. Do **not** add a `GET /stream-flow` mapping — `/stream-flow` is a client-side route and a controller mapping on it shadows `SpaController`, producing a circular-view-path 500 on a page refresh (there is no template engine); same rule as `/audit`.
- `SqlQueryValidator` — cross-join and system-table guard, **not** the statement whitelist. It checks the two `ExplorerConfig` switches and returns silently for anything that is not a `SELECT` or an `EXPLAIN` — which is what used to let `INSERT INTO` reach Flink Job mode. That mode is gone, so nothing downstream of this class accepts an INSERT any more; the silent return stays because the rule it states is about *this* guard's scope, not about which statements exist. The whitelist ("Only SELECT, EXPLAIN, SHOW, DESCRIBE and CREATE TABLE statements are allowed.") is enforced by `FlinkSqlService.executeSql`, and this file described the wrong class for it. Its `EXPLAIN` probe still swallows unresolved-table errors (it runs before auto-registration, so those are expected), but a **parse** error is rethrown as `IllegalArgumentException`: syntax never depends on the catalog, so `POST /api/query/validate` can reject a typo with its line/column before the query touches Kafka.
- `PayloadDigestService` — the Process Mining pipeline never handles a raw payload past ingestion. Each record is turned into a `PayloadDigest` (mapped fields, a bounded sample of other scalars, array cardinalities, a `PayloadShape` reference, original size) by a **streaming** parser: Jackson `JsonParser` for JSON, StAX `XMLStreamReader` for XML — no tree, and on the live path not even a `String`, since the value arrives as `byte[]`. Subtrees past `max-depth` and array elements past `array-sample-size` are `skipChildren()`-ed rather than walked, so a 1 MB / 10-level document costs a bounded walk and yields a ~1 KB digest. Structures are deduplicated by hashing the leaf-path set (array indices collapsed to `[]`) into a shape id, kept in an LRU registry, so a window of identical documents contributes one skeleton to the prompt. Non-JSON/XML payloads keep a bounded preview; unparseable ones carry `parseError` + preview.
- **OpenRouter is the default provider** (`ClaudeConfig.Provider.OPENROUTER`), and it replaced `OLLAMA` at `http://localhost:11434/v1` — a default that only ever worked in one situation, a developer running this application *outside* a container with Ollama installed on the same machine. Inside every image published here `localhost` is the container, where no Ollama runs, so the shipped default answered a connection refused to itself; a default is what the largest number of people meet first, and this one needs a key and nothing else. What it costs is stated rather than implied, in `application.yml`, on the Docker Hub page, in the README and on the Settings banner: it is a **hosted** endpoint, so the message digests Process Mining builds leave the host. `compose/ollama.yml` and the SpectraLLM stacks name their provider explicitly and are untouched by the change, which is the point — a deployment that must keep everything in-house says so, and every stack that has to already did. One consequence worth knowing: the 120 000-character prompt budget and the default provider now agree by construction (see the window section above), where before the shipped budget was sized for a hosted API the shipped provider was not. Two knock-on changes were forced by the move rather than chosen alongside it. `SettingsStore.Field.envAliases` is a **list**: `claude.api-key` is bound through a placeholder, so `StoredSettingsInitializer` has to be told which environment variables name it, and with OpenRouter as the default the variable an operator actually exports is `OPENROUTER_API_KEY` — a key set there being outranked by a stored one would be the identical defect the single alias was added to fix, on the identical field. The chain is `${OPENROUTER_API_KEY:${ANTHROPIC_API_KEY:}}`, with `CLAUDE_API_KEY` (the property's own relaxed name, and therefore a higher-precedence property source) outranking both on a machine that exports several. And `ConfigControllerTest`'s "whole form" fixtures now read the running configuration instead of spelling the shipped defaults out: those two tests are about the difference between a field *carried* and a field *changed*, and hardcoding the defaults made them fail the day one moved, on a rule that has nothing to say about which provider ships.
- **What becomes of the message content is stated on both pages that send it** (`pages/llmPolicy.ts`, pure + tested, rendered by `Config` and `ProcessMining`). The question was answered by halves: Settings spoke **only when the news was good** — `DENY` showed its restriction while `ALLOW` fell back to the generic "remote inference" line, so the one setting that *widens* exposure was the one that displayed nothing — and Process Mining, the page where the content actually leaves, said nothing at all beyond "digests are sent to this endpoint". `describeDataPolicy` returns one of four tones (`local` / `restricted` / `open` / `unenforceable`) from the facts `GET /api/config` already carries, and two rules hold it: a policy is asserted only where it is **enforceable** — OpenRouter imposes it at the routing layer, so it can be spoken about, while on Anthropic, an arbitrary gateway or a remote Ollama this application can neither impose nor observe one and says so — and the unknown is **stated rather than omitted**, which is also OpenRouter's own stance (it assumes retention *and* training where a provider's policy cannot be established). It describes what the deployment **enforces**, never what a model **declares**: the second would be a third-party claim rendered as our verdict. Settings reads it off a `inForce` state held apart from the form, like `persistence` — `llmDataRetentionRefused` is computed server-side and does not follow a provider changed in the form, so mixing the two would print one provider's policy under another's name, and a `policyIsStale` line says when the form has moved ahead of what is running.
- **The routing policy is where a privacy claim stops being a warning** (`routingPolicy()` in `OpenAiCompatibleLlmClient`, `claude.openrouter-data-collection`, default **`DENY`**). Everywhere else this application can only read *its own* address and say "remote"; what the upstream vendor then does with a Kafka message digest is unobservable from here. OpenRouter enforces it at the routing layer, so the request carries `provider: {data_collection: "deny"}` and the Settings banner states the property instead of the risk — `isDataRetentionRefused()` is what it reads, and that is false for every provider where the question cannot be enforced, so the sentence is never stronger than the mechanism. The accepted cost is stated where it is paid: a model served only by data-collecting providers stops being routable, and the gateway reports that with **the same 404 it uses for a mistyped slug** — hence `explainRoutingRefusal()`, which appends the policy and names the setting, because an unqualified "no such model" sends an operator to check a name that was correct all along. It keeps the exception's status, since `looksLikeSchemaRefusal` reads it. `claude.openrouter-require-parameters` is the sibling and is **off** by default on the `structured-output: AUTO` reasoning: it would make schema support a routing guarantee, but a model whose providers lack it becomes *unroutable* rather than degrading, and the per-model latch cannot rescue that — the refusal arrives as "no endpoints found", not as the 400/422 the latch keys on. **`claude.openrouter-max-price-usd-per-million` is the third, and it is the enforceable half of `session-cost-limit-usd`**: that one accumulates what has already been spent and stops the session afterwards, which is the right shape for a running total and the wrong one for a surprise — the expensive route has been paid for by the time the cap notices. A price ceiling is refused before the tokens exist. One value against both published prices (completion is the dearer in practice), in the unit the catalogue publishes and the picker renders, so the number written here is the number read on a row; **0** and off by default, on the same rule as its two siblings — every provider over the ceiling makes the model unroutable, arriving as that same "no endpoints found". And since a 404 on this gateway now conflates three causes, `explainRoutingRefusal` names all three and points at the Test button, which is the one place that asks the catalogue: doing that lookup from the analysis path is refused deliberately, or a live session that has begun failing would make one request per window.
- **A failure the gateway only relayed is not this application's to answer for** (`LlmHttpSupport.upstreamProviderOf`). On a routing gateway one model is served by several upstream providers, the choice is made per call and is not announced, and a provider's own failure comes back with OpenRouter's status over that provider's payload — `{"error":{"message":"Provider returned error","code":400,"metadata":{"provider_name":"AtlasCloud",…}}}`. Read as an ordinary 400, that produced the sentence *"the endpoint rejected the request body (a field it does not implement, or a malformed one)"*, which sends an operator to audit a body that is provably fine: measured on `liquid/lfm-2.5-2.6b:free`, the byte-identical request failed through AtlasCloud and succeeded through Liquid minutes later. `error.metadata.provider_name` is therefore read off the error body — defensively, since an error body is exactly where no shape is guaranteed, and a body that will not parse leaves the diagnosis as it was — carried on `ClientErrorException.upstreamProvider()`, and the message names the provider that failed and says another attempt may route elsewhere. **The second half is what it costs elsewhere**: `looksLikeSchemaRefusal` fires on 400/422, so an upstream failure used to latch the model into `modelsRefusingSchema` — for the client's whole lifetime, on the strength of one provider's bad afternoon, with every later Process Mining window running unconstrained and nothing saying so. The unconstrained retry still happens (an upstream that genuinely lacks `response_format` is a real case, and one extra request is the cheap half); only the durable conclusion is withheld, since a relayed refusal is a fact about a provider, not about the model. Note what this does **not** fix, because it cannot be fixed here: a `:free` slug is usually unroutable under `claude.openrouter-data-collection: DENY` — the free endpoints are the ones that train — and the gateway reports that as the same 404 as a mistyped model, which is what `explainRoutingRefusal` exists to qualify.
- **A 4xx names the thing to go and change** (`LlmHttpSupport.remedyFor`). Every client error read "check base URL, model and API key", which on a metered gateway names three things that are all correct: a **402** is an account out of credit or past a spending cap and no amount of configuration fixes it, a **403** is a moderation or permission refusal. The provider's own body still follows — it is the half that says *which* cap or *which* guardrail — and the wording stays "what this status usually means" rather than a verdict, since a corporate gateway is free to use these codes its own way.
- **OpenRouter is a provider, not a client** (served by `OpenAiCompatibleLlmClient`). It speaks the OpenAI `/chat/completions` API verbatim, so a class of its own would be a second copy of the retry, usage-reading and schema-degradation logic — what is specific to it lives in the config instead: a default base URL of `https://openrouter.ai/api/v1`, a key that `isApiKeyRequired()` treats as mandatory (an anonymous request is a 401, so a blank key there is a deployment that cannot analyse anything, not "optional credentials" as on a local Ollama), and membership of the `AUTO` structured-output set on the per-model latch described below. It is the reason that latch had to become per-model: a routing gateway is one endpoint whose capabilities differ per model. The client also sends OpenRouter's two **attribution headers** (`HTTP-Referer`, `X-Title`) and only to OpenRouter — they name this project and carry nothing about the deployment or the messages, and posting an unsolicited `X-Title` at somebody's corporate gateway is not this application's business. Nothing else changes: the model field takes a slug of the form *vendor/model*, which is also why switching provider in Settings replaces a model name carrying no `/` rather than sending `qwen3:4b` to a gateway that has never heard of it.
- **`OpenRouterModelCatalog` answers the question `test-llm` was not asking.** That endpoint proved *something responded*, which is worth knowing and is not what an operator wants to know when Process Mining misbehaves — that question is whether the slug they typed can do this job. Everywhere else in this application a model's capabilities are discovered by **provoking a failure**: the schema latch learns that a model refuses `response_format` from the 400 it returns, and a slug that cannot emit text is found out on the first analysed window, reported as the same 404 OpenRouter uses for a mistyped name. OpenRouter publishes all of it per model, so on that provider one small `GET /v1/model/{author}/{slug}` — about the one slug configured, never the several-hundred-model catalogue — turns four guesses into facts, carried on `LlmModelCheck`. **The one that matters most is invisible to the running code**: `supported_parameters` lists `response_format` and `structured_outputs` **separately**, and a model carrying the first without the second *accepts* the field and then ignores the schema — no 4xx, so the per-model latch never fires and the deployment believes decoding is constrained while `LlmJsonSupport` quietly carries every answer. A guarantee that silently is not one is worse than an outright refusal, hence `SchemaSupport` having four values rather than being a boolean (`CONSTRAINED` / `ACCEPTED_UNCONSTRAINED` / `UNSUPPORTED` / `UNKNOWN`), and hence nothing acting on it: `structured-output: AUTO` already declines to decide for an endpoint it does not know, and the same restraint applies. It also retires a claim made a few sections above — *"the window belongs to the endpoint, so nothing in this application can check that it fits"* — which is true of every other provider and not of this one: `context_length` is published, so `process-mining.prompt-char-budget` is compared against it, **plus `claude.max-tokens`, since the answer is generated into the same window**. That comparison is a **floor, not a calibration**, on the same optimistic four-characters-per-token ratio `docs/check-compose.py` uses — a budget it passes may still not fit, one it rejects certainly does not — and the word *floor* is in the sentence the page renders, since without it the phrase promises what only the model's tokeniser can decide. Four rules keep the read from becoming a liability. It runs **only against OpenRouter's own host** (`isOpenRouterEndpoint()`, the attribution-header test, deliberately not the routing-policy one: that carries a guarantee and must survive a proxy, this is a convenience and can be withheld on a guess). It is **best-effort without exception** — every failure becomes `LlmModelCheck.unavailable` naming why, never a changed verdict about reachability, because "we asked and the answer is no" and "we could not ask" are different answers. It takes **no retry and a short deadline**: it is a side read on an interactive gesture. And it runs **from `test-llm` and nowhere else** — a capability report is worth one deliberate button press, not a request per window. It is reported on the failing branch too, which is where it earns the most: an unroutable model comes back as that same ambiguous 404, and *"this model emits embeddings only"* is the sentence that stops an operator checking a model name that was correct. Every field is boxed and `null` means the catalogue did not say — a record that exists to replace guesses must not return a fact it could not establish looking like one it established negatively, so an unreported modality never renders as "this model does not emit text". The verdicts are computed **server-side** and `pages/llmModelCheck.ts` only turns them into sentences: a grading rule written on both sides is one that drifts, which is what `keyBase` cost the data model before it was moved back.
- **Choosing an OpenRouter model is recognition, not recall** (`OpenRouterModelCatalog.shortlist`, `GET /api/config/llm-models`, `pages/llmModelPicker.ts`). The Model field was a bare text box: you recalled a slug, typed it, saved, pressed Test, read the verdict — and step three was a real mutation, since `handleTestLlm` began with `POST /api/config`, so *trying* a model repointed the running deployment and, with `explorer.settings-persistence` on, wrote it into the settings store. Exploring and committing were one gesture, which is why nobody compared two models. Three things change. **The shortlist is one request, not a catalogue download**: OpenRouter filters *and* sorts server-side, so `output_modalities=text` + `supported_parameters=structured_outputs` + `context=<the deployment's own floor>` + `sort=pricing-low-to-high` returns about twenty rows that are already the models which can do this job — every filter is a fact the application knows about itself, `estimatedPromptTokens()` included. It is lazy and behind a button (nothing whose only product is a form convenience goes near page load), OpenRouter-only, and `criteria` travels in the answer because a filtered view presented as "the models" is the same lie as a silently truncated list — `available: false` with an empty list and `available: true` with an empty list are different answers, and only the second says anything about the catalogue. **The probe applies nothing**: `POST /api/config/test-llm` takes an optional body carrying `llmModel`, and `ClaudeConfig.probeCopy` builds a throw-away configuration naming it — no bean mutated, nothing reaching `SettingsStore`, and `candidate: true` in the answer so "reachable" does not claim to describe the deployment when it describes something else. **Only the model is overridable, and that restriction is the security boundary rather than a simplification.** A first draft let the body carry the provider, base URL and key too; CodeQL called it critical and was right — an unauthenticated request choosing the URL is a server-side request forgery, the client reflects the response body back to the caller in its error message, and since a blank key falls through to the stored one, a single call that changed no state and left nothing in the settings file would post the operator's API key to any host. Repointing this deployment is what `POST /api/config` is for: deliberate, validated and persisted. `GET /api/config/llm-models` takes no connection parameters for the same reason, and the accepted cost is stated on the page — switching provider in the form must be saved before the shortlist and the probe describe the new endpoint, which `connectionIsStale` says in as many words. That is also the one place `LlmClientFactory` is called outside `LlmClientProvider`, and the exception is the rule's own logic rather than a lapse — the rule exists so a probe cannot claim to have tested what the engine uses; a candidate probe is testing what the engine explicitly is *not* using, and says so. **And a row carries what it would cost**: `pricing.prompt` / `pricing.completion` are published per token, so `LlmModelOption.projectedCostUsd` is the prompt budget at the prompt price plus `claude.max-tokens` at the completion price. It is a **projection, not a measurement**, and the distinction is load-bearing rather than pedantic — `LlmUsage.costUsd` is *read* from the provider precisely because no price table lives here, while this one is published prices times the same optimistic four-characters-per-token floor, so it can understate. `PROJECTION_NOTE` is rendered under the list and asserted by a test; half a published price yields `null` rather than a cheaper-looking model, and a free model prices at `0`, which is a real measurement. `ACCEPTED_UNCONSTRAINED` is the one grade shouted in a row, for the reason it exists: a refusal repairs itself in one request, while a schema accepted and ignored raises no error and nothing else would ever say so. **And a free model is marked when the routing policy is `DENY`** (`isFreeOption`, the second argument to `describeOption`): the list is sorted cheapest-first, so free models arrive *at the top* — and they are precisely the ones that policy usually rejects, the free endpoints being the ones that train. The first rows offered were therefore the ones that answer 404, qualified only afterwards by `explainRoutingRefusal`. It warns rather than deciding — which providers serve a model today is the routing's business, not this application's — and it keys on the **published price being zero**, a real measurement, never on the `:free` suffix, which is a naming convention; an *absent* price stays `null` and produces nothing, on the rule the whole picker follows. The flag comes from `inForce`, the policy that is running, never from the form: the list describes the saved endpoint, and mixing the two would print one configuration's warning under another's models.
- **A credential does not follow the endpoint to a different host** (`POST /api/config`, `ClaudeConfig.sameEndpointHost`). That endpoint accepts any base URL with no validation and guards the key with `containsKey`, so a body naming a new host and omitting `llmApiKey` repointed the deployment while leaving the stored key in place — and the next `test-llm` sent that key there, with `firstChoiceContent` reflecting up to 300 bytes of the answer back to the caller. Two unauthenticated calls, and the caller needed no key to begin with. This is the same defect CodeQL called critical on the probe, one door over, where the taint crosses a persisted bean between requests and the scanner does not follow it. **"An operator may repoint this application" and "anyone may have its credentials" are different statements**, and only the first is what `SECURITY.md` accepts as a deployment constraint. The rule is deliberately about the **host** — a changed port or path is the same endpoint, a changed hostname is not — and it applies to a *derived* move too, since switching provider fills in a new default base URL. A save is the deliberate act, so re-entering the key is a reasonable thing to ask; that is exactly why the same rule would be wrong on the probe, where nothing is committed. What was cleared is **named** in `credentialsCleared` rather than done in silence: the form's key field is blank either way, so without it the next call fails on a missing credential with nothing connecting the two.
- **The Settings page says when it could not read the configuration** (`loadError`, `fetchConfig`). The load effect swallowed its failure in an empty `catch` — "Backend may not expose REST config yet", which stopped being true long ago — set `loading` false, and drew a complete-looking form having received nothing. That is the unverified claim this codebase keeps removing (the connection pill's third state, `inForce` starting null, `describePersistence`'s fourth tone), left standing on the one screen whose entire purpose is data entry: letting someone type over an unknown baseline produces a save whose effect nobody can predict. It is an `ErrorPanel` with a retry now, and the form is not rendered at all until the server has answered.
- **A model slug is refused at save time, not at the first analysed window** (`validateModelSlug`). Deliberately syntactic and OpenRouter-only: it checks the shape of an address the gateway can resolve, never that a model exists — that is what Test is for, and it asks the catalogue. Elsewhere a model name is whatever the endpoint accepts and this application has no opinion. It mirrors `OpenRouterModelCatalog`'s own pattern (each segment starts alphanumeric, which is what excludes a `.` or `..` segment from a URL path); the server still decides, this only moves the moment you find out.
- **The Test button also says what is left on the key** (`OpenRouterModelCatalog.describeKey`, `LlmKeyStatus`, `pages/llmModelCheck.ts`'s `describeKeyStatus`). The credit was consulted nowhere: a key running out answers 402, which `LlmHttpSupport.remedyFor` already reads correctly — but only *after* an analysis has failed. It is published, so the press that already asks what the model can do can ask this too, under the same four rules (OpenRouter's own host, best-effort, no retry, never on the analysis path). It is also the number `claude.session-cost-limit-usd` had been missing: that cap ships disabled because "any figure chosen here would be arbitrary", and arbitrary is what a cap is while nothing on screen says what the budget is. **Three states, and the third is the one to get right**: a limited key with credit left, a limited key with none (a 402 waiting to happen), and a key with **no limit at all**, which has a known usage and no remainder — "unlimited minus what you spent" is not a number, and rendering it as `0` would announce an exhausted key to somebody who has an unlimited one. `error` is a fourth thing entirely and renders nothing: it says the question could not be asked. `limit_remaining` is read where it is published rather than subtracted here, and derived only as a fallback and only when both halves are real numbers.
- **`GET /v1/models/user` disambiguates a refusal** (`availableToKey` on `LlmModelCheck`). An org key restricted to part of the catalogue is refused with the same 404 as a mistyped slug, and those send an operator to two different places. It is consulted **only when the per-model lookup already failed** — one extra request, on a failure branch, behind a deliberate button press — and it takes no filters, only `limit`/`offset`, so one generous page is read and **a slug missing from a list that filled the page is reported as inconclusive rather than absent**: `null` means the question could not be answered, and only an exhaustive list yields `false`. The browser renders the note on `false` alone, never on `null`, or it would assert a restriction nobody observed.
- **The Settings page no longer mirrors the shipped defaults** (`llmProviderDefaults` on `GET /api/config`, from `ClaudeConfig.defaultBaseUrl` / `defaultModel`). `Config.tsx` carried the shipped OpenRouter slug twice — as initial form state and in the provider-switch fallback — beside a table restating `defaultBaseUrl`, which is the mirror-drift pattern this codebase keeps removing (`keyBase`, the four literal `'internal.'` prefixes): the day a shipped default moves, the form offers one model while the engine runs another. The initial state's base URL and model are now **empty**, which is the true value — the form sits behind a `loading` guard, so nothing of it is displayed before `GET /api/config` answers with what is actually in force. `defaultModel` is empty for `OPENAI_COMPATIBLE` (an endpoint we know nothing about) and for `SPECTRA` (which ignores the field), and empty means "nothing to propose", not "no model". The response's defaults are pulled out of the payload *before* it becomes form state, for the reason `splitPersistence` documents: a key no form carries would otherwise enter the comparison deciding the form is modified, and the draft written to `localStorage`.
- `LlmHttpSupport` — shared plumbing for the plain-HTTP clients (OpenAI-compatible, Ollama, OpenRouter, SpectraLLM). **A 429 is retried on the server's schedule, not on the backoff** (`retryAfterMillis`). It was handled as a 5xx, and the two are not alike: a 5xx may well pass half a second later, while a rate limit *states when it stops being true*. The default schedule — 500 ms, then 1 s — spends all three attempts inside a second and a half, which is shorter than any rate limit worth the name, so the caller was told "status 429" about a request that would have gone through a few seconds later. `Retry-After` is read first and in both its legal forms (delta-seconds and an HTTP date), then OpenRouter's `X-RateLimit-Reset`, which is an *instant* rather than a delay and is taken as seconds or milliseconds on the same 10^10 threshold `setup-demo.sh` uses. Bounded twice — 30 s, and never past the call's own request timeout — and a delay beyond that is a **refusal naming it** rather than three more attempts arriving at the same answer, since nothing here can shorten it. Everything unusable (an unparsable header, a negative delay, a reset already past) answers `-1`, which selects the ordinary backoff: a gateway that says nothing is exactly as it was. The parsing is pure and takes its clock as a parameter, so `LlmRateLimitTest` covers it without a server and without waiting. **Not every failure is worth retrying.** Connection errors, 5xx and 429 are retried three times with backoff; 4xx fails fast (a bad URL, model or key does not improve on the second try); and a **request timeout is now terminal**, because retrying replays the whole prompt on a model that has already shown it needs longer than the budget — it tripled the load and the caller's wait for the same outcome, and on a live session the window being analysed is stale by then. The message names `claude.request-timeout-seconds`. The **connect timeout is capped at 10 s** rather than being the request timeout: that one is sized for how long a model may take to *generate*, and applying it to the TCP handshake meant a wrong port took a full minute to say so, three times over. `OpenAiCompatibleLlmClient.firstChoiceContent` refuses an answerless body instead of crashing on it — `path("choices").get(0)` returns `null` when the array is absent or empty, which is precisely what a 200-with-an-error-body looks like on Ollama, and the NPE reached the user as "LLM call failed: null"; the provider's own `error.message` is reported instead. **And an answer that never arrived says the model ran out of budget** (`noContentMessage`): a small reasoning model that spends its whole output allowance deliberating returns a 200, a well-formed body and no content at all, which the bare wording *"LLM response choice carried no message content"* sent an operator to diagnose as an endpoint, a model name or a key — all three correct. It is not an exotic shape here, where the application is routinely pointed at small models: measured on the free slug one session ran against, 3 562 of 7 089 output tokens went on reasoning in the runs that **succeeded**. Three answers rather than one, and the difference is what may be asserted — `finish_reason: "length"` is the provider stating the cap was hit, so the message says so and names `claude.max-tokens`; tokens generated with no content is the same symptom *without* that confirmation and is reported as the counts it is; neither, and the old wording stands, because a gateway that omits the reason must not be paraphrased into one. **Blank content counts as absent**, since every caller parses the answer as JSON and an empty string only moves the failure one step on, to a parse error that says nothing about where the answer went. `LlmJsonSupport.hasUnterminatedReasoning` already reported this cause for an answer that got as far as opening a reasoning block; this covers the one that never got that far.  **The unconstrained-retry latch fires on 400 and 422 only**, not on any 4xx: those two are how a gateway says it does not understand a request field, whereas 401 and 404 mean a wrong key and a wrong model or path. Latching on those disabled structured output for the client's lifetime — and that lifetime outlasts the mistake, since `LlmClientProvider` fingerprints provider, base URL and key and *not the model*, so correcting a mistyped model in Settings reuses the very client that had given up. The deployment then ran unconstrained for ever, silently, because of a typo fixed a minute later. **The latch is now keyed on the model** as well as being narrowed to those two statuses, which closes the same hole from the other side: even a genuine 400 only teaches us about the model that provoked it, so a schema-less model on a routing gateway costs one extra request for itself and does not degrade the next model chosen.
- `LlmSchemas` / `LlmOutputSchema` — **the answer is constrained, not merely requested.** The prompt has always ended with "Return ONLY valid JSON. NO markdown", and `LlmJsonSupport` exists to balance braces and dig the object back out of whatever prose or ``` fence came around it; when that failed the user got a parse error. Asking is not constraining. A JSON Schema now travels with the request — `output_config.format` on Anthropic, `response_format: {type: json_schema}` on the OpenAI-compatible path — so the decoder cannot emit anything else. It matters most on the small models this application is routinely pointed at — a 4-billion-parameter local one, or whichever cheap slug an operator picks on OpenRouter — which are far likelier than a frontier model to editorialise around the JSON they were asked for. The schemas stay **shallow on purpose** — constrained decoding narrows the model's choices at every token, so pinning enums and minimums everywhere would buy validation nobody needs and cost quality on the parts that matter, the prose in `description` and the Mermaid in `flowchart`. `LlmJsonSupport` stays on the path as a net, and the prompt keeps asking, because SpectraLLM's query API has no notion of schemas at all.
- `LlmJsonSupport` — **the net, and it has to hold, because the unconstrained path is not exotic.** It is what SpectraLLM, an arbitrary `OPENAI_COMPATIBLE` gateway, `structured-output: OFF` and any endpoint that has refused a schema once all fall back to; it had no test of its own until `LlmJsonSupportTest`. Two things it does beyond balancing braces. **A reasoning model's trace is stripped first** (`<think>` / `<thinking>` / `<reasoning>`, any case, several blocks): it was found on `qwen3:4b`, this application's default model for several releases, which reasons before answering — and a model reasoning *about the JSON it is about to write* quotes fragments of that JSON while doing so — so the first `{` in the answer sits inside the deliberation, and the balanced scan returned a piece of it. That parsed cleanly into a flowchart the model never proposed, which is worse than failing. Reasoning is removed **before** the Markdown fences, since a fence can be the first thing left once a trace is gone. And an **unterminated** block — an opening tag with no closing one — is the model spending its whole output budget thinking: everything from the tag on is dropped, which leaves nothing, and both services report *that* (`hasUnterminatedReasoning`, naming `claude.max-tokens`) rather than a parse error describing an object the model never got round to writing.
- **Both LLM answers are parsed leniently about keys they do not know.** `LlmAnalysisService` and `FieldProfilingService` build their `ObjectMapper` with `FAIL_ON_UNKNOWN_PROPERTIES` disabled; a bare `new ObjectMapper()` keeps Jackson's default, which is *on*, so one key a model volunteered — a `summary` beside `comments`, a `confidence` on an anomaly — threw the whole analysis away, and the failure was reported with a hint naming `claude.max-tokens`, which would not have fixed it. Note the asymmetry with the schema: constrained decoding prevents extra keys where it is in force, and every path listed above is a path where it is not.
  **`claude.structured-output: AUTO` is not "on everywhere", and that is the whole design.** `OPENAI_COMPATIBLE` points at an endpoint we know nothing about — llama.cpp, vLLM, LM Studio, a corporate gateway — and some answer an unrecognised `response_format` with a 400. Turning a working deployment into a failing one to gain a guarantee it may not need is the wrong default, so AUTO enables it where support is known (`ANTHROPIC`, `OLLAMA`, `OPENROUTER`) and `ON` is the opt-in for a gateway whose operator knows better. Either way `OpenAiCompatibleLlmClient` **degrades on its own**: a 400 or a 422 on a schema-carrying request earns one unconstrained retry, and the refusal is remembered **only if that retry then succeeds**. The order is the whole of it — remembering first drew a durable conclusion from evidence that never established it, since those two statuses say the endpoint did not understand the *body* and not which field of it: `max_tokens` (which the OpenAI API refuses on reasoning models in favour of `max_completion_tokens`), `temperature: 0.0` on those same models, and a prompt over the context all answer 400 to a request this client always sends those fields in. The retry failed identically, the caller got the real error, and the model stayed marked schema-incapable for the client's lifetime — which outlasts the fix, the fingerprint not carrying the model. The unconstrained call is the experiment, so it is run before the verdict is written down. **Remembered against the model, not the client**, which is what lets `OPENROUTER` be in the AUTO set at all: it is the one provider here whose answer to "do you support schemas" is per *model* — one base URL and one key route to hundreds of them, and only some of them, served by only some upstream providers, implement `response_format`. A single flag per client meant one schema-less model disabled constrained decoding for every model chosen afterwards, silently and for the client's whole lifetime, since `LlmClientProvider` fingerprints provider, base URL and key and the model is in none of them. Per model, a refusal costs one extra request for that model and nothing for the next. Without the retry at all, an operator would be told their gateway is broken when it merely lacks a field.
- `LlmUsage` — **what a call actually cost**, in tokens *and in money*, carried on `LlmResponse` and out through `ProcessMiningResult.usage` and the live `ANALYSIS_USAGE` event. `costUsd` is **read, never derived**: OpenRouter prices every response and that figure was being dropped — on the provider now shipped by default, which bills per token — while no price table lives in this application, so a figure on screen is one a provider stood behind. It follows the same nullability rule as the tokens and needs it more: a provider that prices nothing (the OpenAI API, Ollama, SpectraLLM) reports `null`, never `0`, since `0.0` is a real measurement (a free model). **`reasoningTokens` is the symmetric breakdown on the output side** (`completion_tokens_details.reasoning_tokens`), and it is a breakdown rather than an addition — the deliberation is already inside `outputTokens`, so what it buys is the *explanation* of a cost, not the cost. It matters here because this application meets reasoning models routinely: `LlmJsonSupport` exists to strip their traces, and `hasUnterminatedReasoning` already reports a model that spent its whole output budget thinking and never reached the JSON — but only after that run failed. The figure shows the same budget being eaten on a run that *succeeded*, in time to raise `claude.max-tokens` or change model. Its nullability reads the other way round from `cachedInputTokens`: `0` is the ordinary case (a model that did not deliberate) and only `null` means nobody counted, which is why the UI shows it solely when it is above zero. The browser's `totalCostUsd` refuses a session total as soon as one call was unpriced — the partial sum would understate a real bill with the assurance of an exact one — and `formatCostUsd` drops to six decimals under a cent, two decimals having printed `$0.00` on every analysis. Nothing measured this before, which meant every tuning decision in the ingestion pipeline — `prompt-char-budget`, the per-topic sample, the digest caps — rested on reasoning rather than on a number, and nobody could say what a snapshot cost. **Token counts are boxed and `null` means "not reported"**: SpectraLLM returns no accounting at all and a lean gateway may omit `usage`, and a zero there would say the call was free — the same class of lie the previous audit removed elsewhere. `durationMs` is measured on our side, so it is real even when the tokens are unknown. A *failed* analysis carries its usage too (`ProcessMiningResult.failed(message, usage)`): a run that times out still burned tokens, and hiding that would make a repeatedly-failing session look free.
- `LlmClientProvider` — **the only way to obtain an `LlmClient`**, and the reason `LlmClientFactory` is called from exactly one place. `POST /api/config` repoints the LLM at runtime, but the two services that call the model resolved their client in their constructor: what they read per call (base URL, model) followed a change, while what the client *carries* — the provider chosen by the factory, and the API key baked into the Anthropic SDK client — did not. Switching Ollama → Anthropic in Settings therefore left every analysis on Ollama, and `POST /api/config/test-llm` built a client of its own and cheerfully reported the new provider reachable: a settings page confirming a change the engine ignores. The provider rebuilds only when a fingerprint of `provider|baseUrl|hash(apiKey)` moves, so the common path is a volatile read rather than a new HTTP client (and its connection pool) per request; `test-llm` now goes through it too, since the point of that endpoint is to prove what the analyses will use. Both services hold a `Supplier<LlmClient>`, which is also the test seam.
- `FieldProfilingService` — sends Kafka message samples to the configured model for semantic field detection (CORRELATION_ID / TIMESTAMP / STATUS / AMOUNT); returns `FieldProfileResult`. Profiles from digests (structures + a few example values per path, `maxSampleFields = maxShapePaths`), not from raw payloads. Never swallow exceptions — propagate so callers surface the real error. **Its prompt budget is global, like the analysis prompt's**, which it was not: it sized itself `max(4 000, prompt-char-budget / topics)` *per topic* with no ceiling, the exact arithmetic corrected in `LlmAnalysisService.appendMessages` and left standing in the sibling — so "Select all" on a hundred-topic cluster claimed 400 000 characters against a budget of 120 000, in the one prompt that runs on every pipeline whether or not an analysis follows. A global remainder now governs how many topics are detailed, and the ones past it are named in the prompt (with an instruction not to invent mappings for them) rather than dropped in silence. **What the read could not cover is named to the operator too** (`SnapshotRead.scopeNotes()`, prepended to `warnings`, which `SchemaValidationPanel` already renders): a topic that never resolved and a topic the model looked at and had nothing to say about both produce no row in the validation panel, so without the note they are the same screen — and the notes go *first* because they explain an absence the model cannot know about, never having been shown the topic.
  **A profiling run that did not happen is not one that found nothing** (`FieldProfileResult.error`, and the two `failed()` factories beside it). Every failure path — no API key, an unreachable endpoint, an answer that would not parse — answered 200 with an empty `topics` list and the reason in `warnings`, which is the *same shape* as a genuine profiling of topics that hold no messages. The two send an operator to opposite places: one is a cluster to go and look at, the other an endpoint, a model or a key to go and fix. It is the distinction `ProcessMiningResult.error` already draws for the analysis half of this pipeline, and its absence from the profiling half cost real time in the session that fixed `KafkaSnapshotReader` — three model failures were read as failed Kafka reads and chased through two rebuilds of the consumer, because "sampled 0/6" meant both things. When `error` is set nothing else in the record is a finding and the page returns to the topic selection with that message; a run that profiled nothing *without* an error keeps its own wording, which now says to check that the selected topics hold messages rather than sending the operator back to the LLM settings. The usage still travels where it is known — a run that burned tokens and then failed to parse is not a free one — and both exception paths report through `SqlErrorClassifier.explain`, which is never blank where `getMessage()` is null for an NPE. **And the model does not get to set it**: `error` is a record component and the model's own JSON is bound into that record with `FAIL_ON_UNKNOWN_PROPERTIES` disabled, so a model volunteering an `"error"` key beside twelve good profiles had its run reported as a hard failure and the profiles thrown away — the converse of the confusion the field was added to remove, and one word of the answer undoing the rest of it. It carries `@JsonProperty(access = READ_ONLY)`, the same annotation and the same reasoning as `usage` beside it: `error` means *this run did not happen*, which is a fact about the call and never something the answer may assert about itself. What the model wanted to say survives in `warnings`, which is the field the prompt asks for it by name.
- `ProcessModelBuilder` + `ProcessModel` — **the process, measured.** Four of the five entries in `AuditPromptCatalog` are questions about a *case* (ordering, orphans, latency, duplicates are each "par correlation id"), and `LlmAnalysisService` sampled its messages **per topic, independently, on offset order** — so whether one case survived in two topics' samples at once was an accident of those topics carrying the same cases, in the same order, at comparable volume, which stops being true the moment a pipeline branches, filters or retries. On the seeded demo cluster the overlap is nil by construction: `demo.payments.*` / `demo.shipments.*` are correlated to the orders **by header only** and never carry the order id in the payload. What a small model can still do with such a sample is infer a plausible pipeline from the **topic names**, and nothing in the answer distinguishes that from an observation. `PayloadDigest.fields()` already carried the case id, the timestamp and the status per record — that is an event log, and nothing ever grouped by the first column. The builder does: directly-follows edges with occurrence counts and p50/p95/max latency, variants (distinct end-to-end paths) with case counts, start/end distributions, repeated `(case, activity)` pairs, and the case ids to inline as worked examples. Pure, so two runs over one window produce the same model, and pinned by `ProcessModelBuilderTest` rather than judged by reading an answer. Four things are load-bearing. **The activity is the topic**, except on a topic the operator mapped a *status* for — mapping one is a deliberate statement that the status is what moves, which is the event-sourced shape — and that is **bounded**: past `max-status-activities` a "status" is not the closed set a status is, so the topic collapses back to one node and the model is *told* which topic that happened to. **There is no notion of a terminal activity and nothing is called an orphan**: which activity ought to end a process is a business fact this application does not have, and deriving it from the data is circular, so what is reported is the *distribution* of end activities and the reading is left to the model. **The window boundary is stated**, because a snapshot manufactures incomplete cases at both ends — a case whose first event predates the read is missing its start, one still running when the read stopped is missing its end, neither is a defect and both look exactly like one. And **not available is a state**: with no mapping there is no case id and therefore no event log, reported as `available = false` with a reason rather than as a process with zero cases — same rule as `SnapshotRead` and the activity series. **A record whose payload broke off mid-parse is not a case**, which the eval found the hard way: a streaming parser reads the fields it reaches, `id` is usually the first of them, so each of the two truncated records `setup-demo.sh` plants inside `demo.orders.3.enriched` arrived carrying a correlation id and became a one-event case that *ended* at enrichment — a pipeline stalling at its third stage, reported where a producer had written two bad records, and `ORD-666` nominated as a spotlight case and inlined into the prompt as a worked example. They are outside the log now, and the exclusion is **counted and named** in `notes` rather than done in silence: dropping records without saying so is the mirror defect of counting them, and it is named apart from "carried no correlation id", since a mapping that does not cover a topic and a producer writing corrupt bytes send an operator to different places. The audit stays where a corrupt payload is a finding in its own right. A backwards hop cannot surface as a negative duration (the log is sorted by event time), so what is counted instead is `outOfOrderCount`: pairs the broker saw in the opposite order to their business timestamps, which is what a skewed producer or a back-dated event looks like.
- `EventTime` — the one place a field value is resolved to epoch millis (below 10^10 is seconds, then ISO-8601, then a space-separated local date-time read as UTC; `null` means *unresolvable*, never the epoch). It was written twice identically, and the second copy said so — `FlinkSqlService.parseEventTimeMillis` carried the comment "mirroring the metric engine" above a body byte-equivalent to `MetricService.toEpochMillis` — with a third file keeping the threshold on its own. Both now delegate. Same argument as `SecureXml` and `LogSafe`.
- **Process Mining runs without an LLM, for the half that never needed one.** The key was checked *before* the read (by what was then `isApiKeyMissing()`, since superseded by `ClaudeConfig.configurationProblem()`, which asks the wider question — key *and* address), so a deployment with no key configured got nothing at all — while the directly-follows graph, the variants and the latencies are counting over records this side already holds. The key is checked after the read and the measurement now: a run with no model reports the `ProcessModel` it built, with `error` naming what is missing (the flowchart, the narrative and the anomalies, which is the half a model was for) and, when there is no field mapping either, saying so too — those send an operator to two different screens. It is the same rule `coverage` already followed on a failed analysis: `usage`, `coverage` and `processModel` are measurements taken on *this* side of the call, so losing the call cannot invalidate them, and all three are `@JsonProperty(READ_ONLY)` so a model can never assert its own scope, its own bill or its own process.
- **The measured process is on screen, not only in the prompt** (`ProcessMiningResult.processModel` → `components/processmining/ProcessModelPanel.tsx`, wording in `pages/processModel.ts`). It was computed and only the model saw it, so an operator read a *narrative* about a directly-follows graph they had no way to check — the opposite of what this application does everywhere else (Stream Flow's evidence table, the coverage notice, the evidence attached to every proposed KPI). The panel renders the transitions with p50/p95/max, the variants with their case shares, where cases ended, repeated steps and the limits of the measurement; a transition the broker saw in the opposite order to its business timestamps is marked `clock skew`, which is a finding about the estate rather than a defect to smooth away. **Unavailable renders as the reason, never as rows of zeros** — and it is what the page shows when there is no LLM configured at all. `slowestEdge` returns null below two transitions, the same rule Stream Flow's chain follows: "the slowest" says nothing when there is only one.
- `LlmAnalysisService` — generates Mermaid flowcharts + `AnomalyReport` list from correlated messages (snapshot and live modes via `analyzeSnapshot` / `analyzeLiveDigests`; `analyzeLive(List<KafkaMessage>)` digests first — the erasure clash is why the digest entry point has its own name). The prompt opens with **PROCESSUS MESURÉ** — the `ProcessModel` above, computed over *every* record read, so that part of the evidence is immune to the sampling that follows it — and the instructions tell the model to draw the flowchart from the listed transitions rather than from the topic names, since an arc the measurement does not show does not exist however obvious it looks. What is inlined after it is **whole case traces**, one per selected variant (`CAS DÉTAILLÉS`), labelled as worked examples rather than a representative sample: the proportions are in the variants section, computed over everything. A topic no spotlight case passes through is **named**, so its silence is not read as a finding about it. Where no event log could be built the section says so and **forbids the inference** — a prompt that merely omitted the flows is one the model fills in for itself — and the old per-topic `evenSample()` path is what still runs there, since describing the topics is all that is on offer. Both paths share one **STRUCTURES DE PAYLOAD** section, emitted for exactly the records that follow it (the body is built into a buffer first, so the shapes cannot describe a different sample). `sample` is capped at `max-sample-fields-in-prompt` per message with the remainder counted in `sampleOmitted`: the digest keeps forty because profiling aggregates them per path across a topic, but inlining forty *per message* spent a topic's whole share on the values the mapping did **not** name. Escaping is single-pass — chaining `String.replace()` copied every payload four times.
  **A failure is reported as one**: `ProcessMiningResult.error` is what separates a refusal from a result. Every failure path — no API key, an unreachable provider, an unparseable answer — used to put its message in `comments` and answer 200, so the page rendered "LLM call failed: Connection refused" inside its *Analysis Commentary* panel, under an empty diagram, exactly as it renders a real narrative. A parse failure on an answer that stops mid-object names `claude.max-tokens`, because hitting the output cap is the commonest cause and the setting is the fix.
  **The prompt budget is global, not per topic × a floor.** The per-topic share keeps a 2 000-character floor (a topic allotted 200 characters contributes nothing an analysis can use), but a floor multiplied by the topic count is not a budget: at 2 000 apiece, 100 topics claim 200 000 against a 120 000 `prompt-char-budget`, and the ceiling the whole digest pipeline exists to enforce was quietly exceeded by the section that inlines the messages. A global remainder now governs how many topics get their share, and the ones past it are named in the prompt rather than dropped in silence.
  **And the answer states what it was able to look at** (`ProcessMiningResult.coverage`, a `ProcessMiningCoverage` of `TopicCoverage` rows). A flowchart and a list of anomalies cannot say what they rest on, and three things reduce the scope without saying so: topics that hold nothing, topics that do not resolve on the cluster, and — the one nothing could see — topics read in full whose records never fit the character budget, which was named *in the prompt*, to the model, and nowhere else. A run over eight topics where two never reached the model rendered exactly like a run over eight, so the model's silence about them read as a finding **about** them rather than as the absence of a question, which is the strongest way this feature can mislead. Each row carries **three** numbers, and the third was added because the measured process broke the other two: `messagesRead`, `messagesMeasured` (records that entered the event log, so they bear on every transition, variant and latency whether or not any of them is shown) and `messagesDetailed` (records inlined verbatim — a worked case trace, or the per-topic sample where no event log could be built). Folding the last two into one `messagesAnalysed` reported **"6 of 3,000"** about a run whose aggregate covered all three thousand, and sent the reader to raise a prompt budget that was 6 % spent — measured on a six-topic, 3 000-record fixture. A **total** `messagesMeasured` of zero is the exact signal that no event log was built and the per-topic sampling ran instead, which is what lets `processMiningCoverage.ts` pick the right sentence without a second flag to keep in step: on that path a topic read and never shown is the budget case, on the measured path it is a topic no record of which carried the mapped correlation id — two causes with two different repairs, and raising the budget fixes neither of the second. `readable` false is a name that resolves to nothing here, never an empty topic; totals are derived from the rows, so the header cannot disagree with them. Deliberately **structured rather than sentences** — `pages/processMiningCoverage.ts` does the wording, in one place — with `warnings` left for what the rows cannot express, such as the field mapping the controller could not resolve. It travels on a **failed** analysis too: a run that read four hundred messages and then lost the model still knows what it read, and that is what sizes the next attempt. The live path carries none of it, its scope being already reported per window by `WINDOW_STATS`.
  **A read that came back with nothing is not a question worth asking.** Both this service and the profiling one used to build a prompt of headings and pay for an answer about the absence of data — an invented pipeline, or a mapping proposal about topics nobody had shown the model, which step 3 then invites the operator to validate. The reason is stated instead, and `SnapshotRead.emptyReadExplanation()` names which of the three empties it was. The two halves report it differently, on the rule each record was written for: the analysis has no answer at all, so it sets `ProcessMiningResult.error`; for profiling, topics that merely hold nothing is a finding about the cluster — where the page already sends the operator — and only a **failed read** sets `FieldProfileResult.error`.
- `KafkaSnapshotReader` — temp KafkaConsumer (group `snapshot-reader-{uuid}`, `enable.auto.commit=false`) supporting EARLIEST / LATEST_N / TIMESTAMP seek modes. `read()` returns raw `KafkaMessage`s; `readDigested()` uses `ByteArrayDeserializer` and digests each record as it arrives, so nothing accumulates — that is the one both LLM services use. Fetch sizes come from `process-mining.*`. **Three separate faults made a multi-topic snapshot read a random subset of what it was asked for**, and the symptom was identical each time: Process Mining profiled one topic of six and reported the rest as empty, an analysis then concluding in as many words that only one topic contained messages. None of them is visible from outside — a snapshot that read nothing and a cluster holding nothing are the same empty list — so the three were found one behind the other, each hiding the next.
  - **`seekToLatestN` clamped to `0` instead of the partition's beginning offset.** This is the root cause and the one that survives every retry: retention deletes the oldest segments, so on a trimmed topic offset 0 no longer exists, seeking there is out of range, the consumer applies `auto.offset.reset` — **`latest`** in this mode — and the position jumps to the **end** of the log. Nothing is delivered and a full topic reads as an empty one. On the demo cluster, after the seed data had aged out and been reseeded, five of six topics came back empty and the sixth was the only one whose log still began at 0. `KafkaAdminService` already followed this rule for its recent-record seeks — it is documented a few paragraphs above — and this class did not.
  - **Termination was decided by an empty poll** (`if (records.isEmpty()) break;`). A fresh consumer's first poll very often returns nothing while metadata resolves and the assignment settles; read as "these topics are exhausted", it made the outcome non-deterministic — three runs of one identical request sampled 1 topic, then 0, then 6. Same defect `drain()` was fixed for.
  - **And the offsets it was then made to steer by were `consumer.position(tp)`, which is not a consumption watermark.** It is the *fetch* position: the client prefetches in the background, across every assigned partition, and advances it as responses are buffered rather than as records are returned. Measured against the demo broker, one poll delivered 2 records of one topic while `position()` reported the log end for all eighteen partitions, twenty-odd records still sitting undelivered — so the read stopped after a single poll, exactly reproducing the symptom the empty-poll fix had just removed. `drain()` compares the same thing and is single-topic, which is what has been masking it there.

  What the loop does now: a **per-partition cursor of its own**, seeded from the seek position before any poll and advanced only by records the handler was actually given, compared against end offsets taken once up front. `hasUnreadOffsets` is pure and never asks the consumer anything. It also consults the **per-topic cap** — once a topic has its quota its partitions stop keeping the loop alive, or a busy topic filled in the first poll would hold the read open for a quiet one already finished — and a partition with no known end offset counts as read, since turning a missing entry into an unbounded read is the opposite of the bounding. A **5 s silence budget** and the 30 s wall-clock budget remain as nets against a broker that stopped answering, never as the normal exit; the silence net is expressed in time rather than as a count of empty polls, because what makes it safe to stop is that nothing has arrived for a while and a count only means that through whatever the poll timeout happens to be. **What restarts that clock is a record the read *kept*, not one it was merely handed**, and the partitions of a topic that has its quota are `pause()`d. Those two go together and both were missing: a capped topic went on being fetched to its end offsets, every record of it discarded at the cap check — and each of those polls counted as activity, so the net could never fire in the one shape it exists for. A busy topic beside a partition whose leader has gone away held the read open for the full 30 s wall clock on the Process Mining hot path, spending the rest of the fetch bandwidth on records nobody would keep. Nothing is resumed: the consumer is closed at the end of the read, and a topic that has its quota does not stop having it. `aFloodOfRecordsItIsDiscardingDoesNotKeepTheReadAlive` pins it, and measures 30 000 ms against the code it describesAnd the read says at DEBUG what it is about to do** — partitions assigned, how many hold records, the `start..end` of each — then what it collected. Its absence is what made the three causes indistinguishable: every one of them ended at the top of the loop, the one exit with nothing to say, so three rebuild-and-observe cycles went into re-deriving what one line states. It is also what finally separated a failed *read* from a failed *analysis*: with the reader fixed, a profiling run still reported five of six topics as unprofiled, and the log showed all sixteen records collected in 30 ms — the empty answer was the model returning a body with no content at all, having spent its output budget reasoning. A read that comes back empty must be able to say which of those it was. **The end offsets are read once, by whoever needed them first.** Two of the three seek modes have to read them to work out where to start, and the loop then asked the broker for the same numbers again — a second `listOffsets` over every partition of every topic in the snapshot, on the Process Mining read path. `Seek` carries them back from the seek, with `null` (never an empty map, which the loop would read as "nothing left to fetch anywhere") for the beginning-offset mode, which needs none. Reading them once also means the cursor is compared against the same instant the seek was computed from. `createConsumer()` is the test seam (`KafkaSnapshotReaderTest` drives a `MockConsumer`); each defect test was verified to fail against the code it describes before the fix landed, and the prefetch one has to make the mock **lie the way a real client lies** — report the log end — rather than throw, since a throw is caught by the reader's own error path and would pass against the very code it exists to fail against.

  **A fourth fault sat one line above all three, and cost more than any of them: a topic the broker describes no partition for used to cost the whole read.** `partitionsFor` answers `null` for a topic that does not exist, `.stream()` on it threw, and the catch below returned an empty list *for every topic in the request* — so one deleted topic, or one typo in a selection of eight, produced a profiling run and an analysis of nothing at all, logged as an error nobody reads and rendered as a cluster with no messages in it. Such a topic now costs itself, is named at WARN, and the read goes on; a request naming only unknown topics returns immediately rather than spending the silence budget polling an empty assignment.

  **And the read says what it could not do** (`readSnapshot` → `SnapshotRead`; `readDigested` is the same read with the answer thrown away, kept for callers that only want records). A short list has three meanings that send the reader to three different places — the topic holds nothing, the topic does not resolve here, the read stopped on its own budget with records still waiting — and an empty list says none of them. It is the rule the consumer-lag and activity work was done for, on the one read that had been left with a bare list: `messagesByTopic` keys **every requested topic**, so a caller can tell an absent row from a zero; `unreadableTopics` names what did not resolve; `readError` and `budgetExhausted` say the counts are partial. `emptyReadExplanation()` and `scopeNotes()` live on the record rather than in either service, because both callers had been about to write the same three sentences.
- `KafkaLiveConsumer` — sliding window consumer; triggers LLM on window fill (default 100 msg) or timeout (default 30s); pushes via `SseEmitterManager`. **Buffers digests, never payloads**: values are consumed as `byte[]` and digested on the poll thread, so a window of a hundred 1 MB documents costs a few hundred KB instead of hundreds of MB; the buffer is capped by count (`windowSize × 10`) *and* by estimated heap (`max-window-digest-bytes`), dropping oldest and reporting the count. Partitions are seeked to the end from a `ConsumerRebalanceListener` (not after a fixed 500 ms poll), so a backlog is skipped reliably and again after any rebalance. `WINDOW_STATS` is emitted from the poll thread when the window is cut — before the LLM runs — and carries the ingestion counters (`messagesReceived`, `bytesReceived`, `maxPayloadBytes`, `droppedMessages`, `parseFailures`, `distinctShapes`). **Threading contract**: the KafkaConsumer is only ever touched by the per-session polling task (init subscribe included); `stopSession()` just raises a stop flag + `consumer.wakeup()` and the polling task closes everything in `finishSession()`. - `ConsumerLagMetrics` — exports consumer lag as Prometheus gauges (`kafka_consumer_group_lag{group,topic}`, `kafka_consumer_group_partitions_without_commit`, `kafka_consumer_group_assigned_members`, `kafka_consumer_group_lag_last_success_timestamp_seconds`), which is how a backlog *triggers* something instead of being noticed afterwards. The three series together say what a threshold on lag alone cannot: zero assigned members with a non-zero lag is the stalled case, and a group ignoring half the partitions has a backlog the lag does not count. **Opt-in and topic-scoped by construction**: a series per group x topic x partition is how a metrics backend gets killed, so partitions are aggregated away, the topics polled are named in `explorer.lag-metrics-topics` rather than discovered, nothing is registered (and no thread starts) when that list is empty, and `explorer.lag-metrics-max-series` freezes the exported set — the cap is logged once, since a silently truncated metric is worse than an absent one. The poll interval matches the 30 s cache behind `getTopicConsumers`; a failed refresh keeps the last value, because falling back to zero reads as "the backlog was resolved". **Three things count as a failed refresh, not one**: the call throwing, a response with `available == false` (an unreachable broker returns no groups, which acted on would publish "nobody consumes this any more"), and a single group carrying an `error` — that row's lag is zero because nothing could be read, and exported as a gauge a zero reads "caught up" and silences the very alert that should fire. **But a group that a successful read no longer returns is dropped** (`dropVanished`, run before the export so the freed slot is available to a replacement in the same pass): keeping the last value is right for a failed read and wrong for a decommissioned consumer, which otherwise exported the backlog of its last day for the life of the process, under an alert that could never clear. **And what keeps its last value is dated**: a frozen gauge is otherwise indistinguishable from a fresh one, so an alert on `lag > N` fires the same way whether the backlog is real and stuck or simply no longer measured — and the operator it wakes cannot tell. `kafka_consumer_group_lag_last_success_timestamp_seconds` is set only on a row that was actually measured, so the alert can require both (`lag > 10000 and time() - ..._last_success_timestamp_seconds < 120`). A timestamp rather than a boolean: same cardinality, and it carries *how* stale, which is the part a threshold needs. It costs a fourth series per group×topic, paid because a number nobody can date is a number nobody should act on; `admits` still counts group×topic pairs, so what `explorer.lag-metrics-max-series` bounds is unchanged. **The same backlog in *time* is exported too, opt-in** (`explorer.lag-metrics-time`, off by default): `kafka_consumer_group_lag_seconds{group,topic}`, the age of the oldest message the group has not read. Opt-in because it is the only series here that reads a *record* — one per lagging partition, per group, per refresh — where the others read metadata; a group committed at the end of every partition publishes 0 without reading anything, since caught up is a measurement. In seconds because the suffix has to mean what it says, while the `CONSUMER_TIME_LAG` metric template reports the same measurement in milliseconds like its sibling templates: one measurement, two units, each following the convention of where it lands. **And this one is removed rather than frozen when a refresh cannot measure it** — the opposite of the rule above, deliberately: a count that stopped being read is still roughly the count, while an *age* is not, because a backlog ages by construction. A frozen "3 min" against a backlog that has been growing for hours is not stale, it is false, and it gets worse every minute; absent, `absent()` sees it.
- `ClaudeConfig` — `@ConfigurationProperties(prefix="claude")`; reads `ANTHROPIC_API_KEY` env var via `${ANTHROPIC_API_KEY:}`
- `MetricService` — bridges Flink SQL to Prometheus metrics via Micrometer. Supports 4 Prometheus types:
  - `GAUGE` → Micrometer `Gauge` (point-in-time value)
  - `COUNTER` → Micrometer `Counter` (service tracks delta between polls and increments accordingly)
  - `HISTOGRAM` → Micrometer `DistributionSummary` with `publishPercentileHistogram=true`
  - `SUMMARY` → Micrometer `DistributionSummary` with client-side quantiles (p50/p75/p90/p95/p99)

  Three templates sit beside raw SQL (`MetricTemplateType`): `TOPIC_COUNT_DELTA`, `TOPIC_TRANSIT_LATENCY` and **`CONSUMER_TIME_LAG` — a backlog expressed in time rather than in records**, and the only one that runs no SQL. It exists because a count is not actionable on its own: the same 4 000 messages are four seconds of traffic on one topic and four days on another, and it is the second case that wakes somebody. Neither number the KPI needs is in a payload — the position is in `__consumer_offsets` and the age is a record timestamp — so `KafkaAdminService.getConsumerTimeLag(topic, group)` reads them: committed offsets, then **end offsets last** (same ordering as the record lag, so a consumer racing the two calls can only overstate), then one consumer that seeks every *lagging* partition to its committed offset and keeps the first record each yields, in **one poll loop** rather than a read per partition. A partition committed at the end costs no read at all — caught up is a measurement. The value is the **age of the oldest waiting record** (`now − timestamp`), not `latest − committed`: a producer that stops leaves a backlog that keeps ageing, which is what "how stale is what this consumer serves" means. Bounded to 64 partitions and an 8 s budget. **A partition that could not be read is `null` with its reason, never 0** (`PartitionTimeLag`) — 0 means caught up, and a gauge saying so while nothing could be read silences the alert it exists to raise; when partitions are missing the metric still publishes (the ones that answered are real) with a `scopeNote` saying the value is a **floor, not a maximum**. The group is a **required** parameter rather than "the worst group reading this topic": that choice would move between refreshes and the series would change subject without saying so — same reason `topic` and `group` are the only labels. `aggregation` is `MAX` (default, what an alert is set on) or `AVG`.

The sentinel is still understood on the way in, a topic written by an earlier build being exactly what this store exists to read. `createProducer()` is the test seam (`MetricServiceTest` drives a `MockProducer`). Within one `refreshMetrics` cycle, identical queries (same sql/maxRows/timeout/readMode) execute once and are memoized (ThreadLocal cycle cache).
- `FieldMappingStore` — the field mappings validated in Process Mining, **persisted** to `explorer.field-mapping-topic` (`internal.field.mappings`, keyed by mapping id, so the topic is meant to be compacted). It was the only artefact this application produces by *correcting a model* and then threw away: a restart lost every mapping, the Metrics suggestions reported one they could no longer resolve, and recovering it meant replaying two model calls to re-derive something an operator had already fixed by hand — the proposal is cheap to replay, the correction is not. Both halves are best-effort and bounded, on the same rule as `MetricService`: the restore is driven by the **end offsets** (an empty poll is not an exhausted topic) under a 10 s budget, an unreadable record costs that record rather than the restore, an unknown JSON property is a field a later version added rather than a reason to lose the mapping, and a failure at startup leaves an empty store and a log line — never a boot that hangs on an unreachable broker. The write is **asynchronous** (with `max.block.ms` capped at 5 s): a validation is an interactive gesture, and holding it for a broker round trip would trade a real second for a hypothetical one. In memory it stays access-ordered and bounded to `MAX_ENTRIES` (200), so a live session's mapping is not evicted from under it by newer ones — **and the topic now follows that same bound**. Every validation mints a *fresh* UUID, so this topic gained one new key per click and kept it for ever: compaction cannot reclaim a key that is never rewritten, and nothing had ever deleted one. A store bounded in memory and unbounded on disk is also incoherent in a way that shows, since a restart resurrects mappings the running process had already stopped answering for. What the bound drops is tombstoned — a null value, the only thing a compacted topic can reclaim — and the accepted cost is stated where it is paid: a mapping evicted by two hundred newer ones is gone, not merely absent from this process, which is the policy `find` already applied to its answer. A **restore** is a replay and tombstones nothing, or every boot on a long topic would answer with a write storm against the store it is in the middle of reading. `createProducer()` / `createConsumer()` are the test seams (`FieldMappingStoreTest` drives a `MockProducer` and a `MockConsumer`).
- `SettingsStore` + `StoredSettingsInitializer` — **what the Settings page is used to enter, kept across a restart.** `POST /api/config` mutated `KafkaConfig` and `ClaudeConfig` and wrote nothing anywhere: the one screen whose entire purpose is data entry was the only one whose input did not survive a stop, and it lost it *silently* — the page then rendered the `application.yml` values as if they were the operator's own, so a cluster repointed on Monday was quietly reading a different one on Tuesday with nothing on screen or in the log connecting the two. Four things are load-bearing. **A file, not an `internal.*` topic**, unlike every other store here, and it is not interchangeable: these settings *contain the bootstrap address*, so a save that repoints from cluster A to B has no answer to which of the two should receive it, and a boot cannot read the topic that would tell it which broker to read. It sits beside `FlinkTableStore` under `data/`. **Only the fields an operator actually entered** are taken over — `touchedFields` compares against the values in force *before* anything is applied, so a field is "entered" when it **changed**, not merely when the request carries it. That distinction is the rule rather than a refinement of it: the Settings page posts its entire form (Test connection applies before it probes), so "the fields this request carries" is every field there is, and the first click on Test connection would otherwise have frozen this release's whole configuration into the file, where a default that moves later could never reach the deployment again. It is also the only way back out of a stored address pointing at a cluster that is gone. `claude.api-key` carries an `envAlias`, because `application.yml` binds it as `${ANTHROPIC_API_KEY:}` and the relaxed name `CLAUDE_API_KEY` is not what a deployment sets — without it a stored key would silently outrank the one in the environment, on a credential. **A store that could not be written is reported, never a failed save**: the settings are applied and this process is using them, and what must not be left standing is the belief that they will still be there after a restart, so the answer carries `settingsPersistedNow` / `settingsPersistenceError` and the page shows it instead of "Saved!". Credentials are written in clear, owner-only (`JsonStoreFile`), never returned by the API; `explorer.settings-store-secrets: false` omits them and **names** the fields it left out, in the save's answer and in the boot log — storing everything except the passwords otherwise keeps half the promise and keeps it silently, the connection failing for a credential nothing said had been dropped. Applied through an `ApplicationContextInitializer` registered in `Application.main`, not a bean: `KafkaConfig` validates in a `@PostConstruct` and `MetricService` / `FieldMappingStore` each open a consumer in theirs, so a bean assigning the stored address would be racing all three — a property source is read by the binder before any of them exists, and none needs a line of code for this. Registered from `main` rather than `spring.factories` so `@SpringBootTest` contexts cannot pick up a settings file left in the working directory.
- `FlinkTableStore` + `FlinkTableRestore` — **the `CREATE TABLE` statements written in the SQL editor**, replayed into Flink's in-memory catalogue after `ApplicationReadyEvent`. Losing them produced no error but a **substitution**: the hand-written definition died with the process, the next query on that name auto-registered a *generated* table under it, and the query then ran — same name, rows returned, a watermark or a chosen subset of columns or a connector option quietly gone. Auto-registration writes its DDL through `executeMutationSql` and never reaches the store, which is the distinction the whole thing rests on: a table derived from a topic is re-derived on demand, one somebody typed is not. Keyed by table name so a rewrite *replaces* (keeping both would replay the older one at boot and make the outcome depend on file order), `TEMPORARY` is refused because the word is the author scoping it themselves, and a statement that *failed* is not kept. The replay goes back through `executeSql` — same whitelist, same validator, same coordinator — since a second route into the engine is how the two come to behave differently, and it would otherwise be a way to run stored SQL the API itself refuses. **Each failure costs one table**, named at WARN: a definition that no longer works (a deleted topic, an option a Flink upgrade renamed) must not lose every definition written after it. And **`DELETE /api/query/table/{name}`** exists because this takes an escape hatch away — restarting used to be the only way to clear the catalogue — so a store that could only grow would be a worse defect than the one it fixes. **The name is resolved against what exists, never interpolated**: the request has to clear `isSafeIdentifier` first, and what then reaches the statement, the log and the store is the application's own string — Flink's catalogue entry, or the store's key — so a name matching neither drops nothing and submits no statement. That ordering matters twice over: the store is consulted after Flink because a table can legitimately be in it and not in the catalogue (written by an older build, or already dropped) and must still be removable, or the boot would go on replaying a definition nobody can get rid of. **`remember` refuses a name that is not a safe identifier**, which is the guard the rest rests on — a backtick-quoted Flink identifier may hold a newline, and that name goes on to be a log line, a JSON key and the body of a `DROP TABLE`; refused where it enters, not cleaned up at each place it comes back out. Its pattern reads a quoted segment whole rather than stopping at the first space, which it used to: ``CREATE TABLE `weird name` `` was filed under the key `weird`, a different table from the one just created. The bin icon in the schema browser is the gesture, behind a confirm.
- **The analysis picks the KPIs to follow, and picks only from what was measured** (`MetricCandidates`, `ProcessMiningResult.metricPriorities`, `highlightPriorities` in `pages/metricSuggestions.ts`). Half of this already existed without a model: a measured process already yields hop-latency and rework KPIs, ranked by a hand-written comparator. What that comparator cannot know is that on *this* estate the payments hop is the one that costs money and the enrichment hop is cosmetic — which is judgement, the thing a model is for, where the numbers are counting, which it is not. So the model is shown the **candidate ids** the panel will mint and asked to name at most four with one sentence each. It returns ids, never metrics: every card carries evidence naming a run and a measurement, thresholds are multiples of a measured p95 and say so, and the SQL is generated — a model filling any of those would produce something that looks derived and is not, which is the single thing that panel exists to refuse. `MetricCandidates` exists so the two sides cannot disagree about an id: `MetricSuggestionService` mints them when it builds the cards and `LlmAnalysisService` lists them in the prompt hours earlier, and two copies of `"pm:hop-latency:" + from + ">" + to` in two files would surface as a banner naming a card that is not there. Four rules hold the rest. An id absent from the list it was shown is **dropped and counted in a blind spot** — a model naming a card nobody offered has invented it, and the operator is entitled to know it went outside. The section and **the instruction that reads it** are both omitted when no event log could be built: emitted unconditionally, that instruction told the model to choose among a heading that does not exist, which is the invitation-to-fill-in this whole prompt is written against — its own test caught that. It rides the analysis call rather than paying for one of its own, and it has to: on the Metrics page the candidates still exist but the anomalies the model has just found do not, and those are exactly the context that makes "which of these matter here" answerable. And the banner **designates, it never reorders** — the list keeps the order a written, replayable rule produced, the model's sentence sits above it labelled as a reading rather than a measurement, and a choice whose card is no longer proposed is counted rather than named. The choice travels beside the measurement it rests on (`recordMetricPriorities`, keyed on the same route as `pm:process-models`), so an opinion about one pipeline cannot be rendered over another's cards.
- `MetricSuggestionService` — **contextual KPIs derived from what this cluster has been observed to do** (`POST /api/metrics/suggestions`). The Metrics page knew nothing about the cluster: its four quick-start cards posed a `COUNT(*)` on the first table found, identical on a three-topic cluster and on an order pipeline. Two features do know something — the **audit** (per-topic counts, findings, and the flows it reconstructs) and **Stream Flow** (a key's real path, hop by hop) — and neither fed a metric. Each proposal carries a ready `MetricConfig` plus the reason it exists, and four rules hold it together. **No suggestion without evidence**: `evidence` is never empty and names the run, the measurement and its scope — a KPI nobody can trace back to an observation is the invented "99.98 % availability" tile the Metrics guide was stripped of, on the page that teaches measurement. **Thresholds are derived and say from what** (`thresholdBasis`): warning at 2× / critical at 4× a measured hop latency, 2×/4× a measured throughput gap floored at 1 %/5 %, 1.5×/2× an audited volume, the observed duplicate count and twice it. Where nothing was measured — a hop the audit could not correlate, an end-to-end volume ratio a single-key trace says nothing about — there is **no threshold, or a threshold that states it is a placeholder**, never a round number that looks considered. **Nothing is created**: a suggestion is a pre-filled form, because the SQL rests on an inferred key column and on an aggregate (`COUNT(DISTINCT …)`) only the Flink planner runs — both carried in `caveats`, and the preview is what settles them. A topic the audit flagged for a consumer finding gets a **`CONSUMER_TIME_LAG` KPI — the backlog in time, which is the half no count can express** — and it is the one proposal that goes and reads the cluster: the group id comes from `getTopicConsumers` (the largest readable backlog), **never parsed out of the audit's wording**, because a finding is prose and reading a name out of it is the lexical dependency this codebase keeps removing. What *is* lexical is only which topics to look at (`isConsumerFinding` matches "consumer group", the phrase all four of `consumerLagIssues`' messages are built from — matching "lag" caught one of them). It is deliberately proposed **without thresholds**: nothing has ever measured this topic in time, so any number would be the round one this panel exists not to print, and the caveat says to set it from the metric's own first readings. When the groups cannot be read, there is no card and a note says so rather than a silence that reads as "this topic needs no KPI". What the audit found but SQL cannot measure stays a **note**: the backlog in *records* is already exported from committed offsets by `ConsumerLagMetrics` (the note names `explorer.lag-metrics-topics`), and a parse failure is not something a query engine can count. The audit is read from this process, and from `internal.audit.history` otherwise so the panel survives a restart — a **RUNNING** report is refused (its topic list changes under the reader between two polls) and a stored report the current record cannot bind is reported, not silently dropped. The key column comes from the registered Flink schema when there is one (`id`, `*_id`, `correlation_id`, …) and falls back to the audit's own `id` convention **flagged as assumed**. **The panel is bounded, and the bound cuts by relevance** (`BY_RELEVANCE`, `MAX_SUGGESTIONS` = 24): the cap existed but sliced the list in *source* order — audit, then traces, then lineage, then mapping — so a pipeline edge a running job *declares* was dropped before a routine volume KPI, purely because lineage is consulted third. Proposals are now ranked by what they are about (the kind, read from the structured id, `time-lag` and `duplicates` ahead of `volume`), then by whether the thresholds were derived from a measurement, then by how few assumptions the card carries, with the source only as a tiebreak and the id last so the order is deterministic — cards must not shuffle between two identical audits when a browser-side dismissal is keyed on that id. **Marking precedes the cut**, which it did not: a proposal an existing metric already covers could take one of the 24 slots and push out a fresh one, so the panel said "already measured" on a card that had displaced the suggestion the operator did not have. And the truncation note says what it dropped, counted by kind, where it used to assert the remainder were "of the same kinds, on other topics" — an claim nothing checked and that was false as soon as the list mixed sources. A proposal an existing metric already covers is **marked, not hidden** (`alreadyConfigured` + the metric's name): "you already measure this" is an answer to the question. Ids are stable across runs (`source:kind:from>to`), which is what makes a browser-side dismissal stick when the next audit re-derives the same card, and one hop yields one card — **the measured process wins over the audit, which wins over a trace**, and that order is the whole of the precedence decision, since `deduplicate` keeps whichever source was built first. It used to be audit-first, on the reasoning that its evidence was the broader of the two then available; a directly-follows graph is broader still. **Three further sources feed it, and none of them infers anything.** *Lineage*: a running `INSERT INTO` job **declares** a pipeline edge, where the audit groups topics by their names and a trace follows one key — so each single-source job yields a gap KPI on a pair nobody had to guess, resolved by `LineageService.dependenciesOf` (shared, not re-implemented as a regex) over `getHeldJobs()` rather than by building the whole graph. A **join is refused with its reason** stated in a note: "everything that entered came out" is a sentence about one source, and two inputs against one output have no ratio worth a threshold. **Bounded like every other family** (`MAX_LINEAGE_JOBS` = 12): resolving a statement is a Flink parse taken under the runtime's read lock, on every load of the Metrics page, so it cannot scale with whatever the cluster happens to be running — the cut is by start time, newest first, because `getHeldJobs()` hands back a `Map.copyOf` with no order of its own and the jobs read would otherwise vary between two calls; what was not resolved is counted in a note, never silently absent. *Process Mining*: the field mapping an operator validated is the only place this application knows a topic's **real** correlation key and its status field. It mostly **improves the other cards** rather than adding its own — `KeySource` records whether a key came from the mapping, from the registered schema or from the `id` convention, and the caveat says which, so the operator knows whether the preview is a formality or the thing to check — and it adds one card per topic with a status field (`GROUP BY status`, one Prometheus series per value, no threshold: which status matters is the one thing this application cannot know). A **nested path is refused**, not turned into SQL that would fail on its first refresh. The mapping id travels from the browser's Process Mining draft (`pm:mapping`) like the traces do, and a mapping the server no longer holds — it aged out of the mapping topic, or the broker could not be read at startup — is **reported**, since the cards it would have produced are missing and silence would read as "Process Mining had nothing to say". *The measured process* is the third and the strongest: a `ProcessModel` carries a **distribution per transition** — p50, p95, worst, over every case the window held, grouped on a correlation id an operator validated by hand — where the audit has one average over a flow reconstructed from topic names and a trace has one observation. It reaches the server the way the traces do, because nothing keeps it: `pages/processModelEvidence.ts` mirrors `flowChains.ts` (versioned envelope erased rather than guessed at, seven-day expiry, three entries deduped on the **topics** rather than the activity labels, so two windows of one pipeline are one route) and the Metrics page posts **the freshest one only** — two graphs of two windows would produce two cards for one hop, settled by arrival order rather than by which measurement is better. What travels is `ProcessModelEvidence`, deliberately narrower than `ProcessModel` and for two reasons: every component is boxed, on `FlowChainEvidence`'s rule that a partial body must not fail a whole request, and the variants, the activity table and the spotlight case ids are the prompt's material — shipping them back to be ignored is data nobody needs to hold. Two families come out of it. A hop-latency KPI per transition **between two topics**, with 2×/4× the p95 as thresholds; a transition inside one topic — which is what a mapped status produces — is counted in a note instead, since the latency template correlates two topics and pointing it at one would compare a topic with itself. And a rework KPI per topic a case was seen revisiting, **deliberately with no threshold**: the measurement counts cases revisiting a step inside the window while the query counts keys sharing the topic over a bounded scan, so a number taken from one and applied to the other would only *look* derived. One constant is arithmetic rather than taste, which is why it exists at all on a panel that refuses round numbers: below **20 observations** there is no value strictly above the 95th percentile, so the p95 *is* the maximum — the figure is used either way, and the basis line names it "the worst of the N cases observed" rather than a percentile. The clock is stated too (`MIXED` / `RECORD_TIMESTAMP` add an evidence line): a transport delay and a business duration are different measurements. `MetricSuggestions.processMeasured` is carried separately from the cards it produced, because a run that measured a pipeline and suggested nothing is a different state from one that never ran, and deriving it from the proposals would erase exactly that distinction. **And the fourth rule is that the evidence has to still hold** (`verifyDataAvailable`, `MetricDataState`). Every source above has already aged by the time it is read — an audit comes back from `internal.audit.history` and can be weeks old, a trace and a measured process are kept in the browser for seven days — and nothing asked the cluster whether the topics those cards name were still there. So a KPI was offered, with the same confidence as any other, over a topic deleted since, with thresholds that are multiples of a count retention had erased; the operator found out once the metric had been refreshing against it every thirty seconds, which is the invented-figure defect this panel exists to prevent, one step later. The check is **two cached metadata reads for the whole request** — `listTopics` on the `'all'` entry every other screen already warms, and one batched offsets read — against a panel that already pays a coordinator round trip per lag finding and a Flink parse per running job. **Four answers, and the fourth is the one to get right.** A topic that is **gone drops its proposal**, named in a note: the metric could only fail at every refresh, the same rule that makes a nested status path a note rather than SQL that would fail on its first run. A topic that is **empty marks it and keeps it** — retention refills, a topic created for a pipeline being built is legitimately empty, and on a gap KPI an empty target beside a populated source *is* the alarm the card exists to raise — with the caveat naming **which** of its topics is empty, since that is the whole of the reading on a two-topic card, and `BY_RELEVANCE` sorting it just under `alreadyConfigured` so it is what the cap drops first. And a check that **could not run changes nothing and says so once**: an unreachable broker leaves every card exactly as its family built it, because "we asked and the answer is no" and "we could not ask" are different answers and rendering the second as the first would empty the panel on a blip. The two halves are separable — the topic list establishes existence, the counts establish emptiness — so a counts read that fails leaves the cards `UNKNOWN` rather than empty, and the note names which half did not run. That last distinction is why **`KafkaAdminService.getTopicRecordCounts` exists beside `getTopicsSize`**: the latter pre-seeds every topic at `0` and swallows its failure, which is right for the dashboard's column (a missing key there is a null pointer in the UI) and is exactly the flattening this codebase keeps removing for any caller that must act on the difference. One offsets read serves both, the honest one omitting what it could not measure — including a topic **none** of whose partitions answered, whose sum would otherwise be a fabricated zero. Lineage is the one family whose two ends are *table* names rather than topics, so the map is built forwards from the topics that exist (`toTableName` is not injective); a name matching neither is settled by **asking Flink's catalogue, never by looking at the spelling** (`unresolvedState`). The first version read "no dot, no hyphen" as "must be a Flink table", which is a guess wrong in both directions — a flat `orders` is an entirely ordinary Kafka topic name, so a deleted one was kept, and a quoted Flink identifier may carry a dot, so a live table could be called deleted. A registered table is `UNKNOWN` (what sits behind it is the connector's business, and dropping on it would penalise the family whose evidence is the strongest there is); a name neither the cluster nor the catalogue carries is one nothing on this deployment can read, whatever it is spelled like. One catalogue lookup per unresolved name, which is normally none, and the same lookup `keyColumn` already makes per topic.
