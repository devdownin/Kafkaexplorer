# Frontend — design notes

Extracted from `CLAUDE.md`. The SPA's conventions, page-by-page rationale and the
rules that keep the pure modules testable. Read the entry for a page before changing it.

## The SPA

The SPA lives in `src/main/webapp/src/`. Stack: React 19 + TypeScript + Vite + Tailwind, Monaco (SQL editor), Recharts (metric charts), Mermaid (process-mining flowcharts), `lucide-react` + Material Symbols (icons), `axios` (API).

**App shell** — `App.tsx` wraps everything in `ToastProvider` + `ConfirmProvider`, renders the `Layout`, and defines the routes. **Pages are lazy-loaded** (`React.lazy` + `Suspense`, `ProgressBar` fallback) for code-splitting; unknown routes render a `NotFound` (404). `Layout` (`components/Layout.tsx`) is the shell: collapsible `Sidebar` (drawer on mobile) + `Header` + an internally-scrolling content viewport. It polls `/api/dashboard` every 30s for connection health and to feed global search (topics + Flink tables).

**The connection pill states a name and a verified address, never a version** (`components/connectionStatus.ts`, pure + tested). It rendered `explorer.cluster-name`, whose shipped value was `KRAFT 4.2`: a Kafka version asserted by every deployment without anything ever having asked the broker — in the one element whose job is to say what you are connected to — and left untouched by the runtime repoint of `POST /api/config`. Nothing overrode it: no compose stack, no Settings field, and it was absent from the documented environment variables. The label is now a display name (`Kafka cluster` by default, `EXPLORER_CLUSTER_NAME` to name an environment), and what *is* checkable travels beside it in the tooltip: `bootstrapServers`, added to `DashboardResponse` and read from the running `KafkaConfig`, so a repoint moves it. Disconnected, the tooltip names the address that did not answer — "Disconnected" alone never helped anyone diagnose anything. Before the first poll answers, the pill says `Connecting…` rather than a hardcoded name; the frontend's own fallback used to be a third value (`Docker Cluster`, against `DOCKER CLUSTER` in Java and `KRAFT 4.2` in YAML). **Health has three states, because there are three**: `isHealthy` is `boolean | null` and starts `null` — it started `true`, so the pill was green before anything had been probed, and stayed green for as long as an unreachable broker takes not to answer. Unknown is neutral grey with a pulsing dot (`connectionTone`), and it is what a screen reader is told too.

The router is a **data router** (`createBrowserRouter` + `RouterProvider`, a `Shell` layout route holding the `Layout` and the `Suspense` boundary, built once at module scope), not `<BrowserRouter>`. No loader is used; the reason is `useBlocker`, which only exists on a data router and is the single point where react-router lets an *internal* navigation be intercepted before it happens — `beforeunload` never sees a sidebar click.

**Typed data survives leaving the page** — `draftStore.ts` (`usePersistentState`, `readDraft`/`writeDraft`/`clearDraft`, keys under `kse:draft:`). Routes mount and unmount their page, so every `useState` on it died on navigation: the four-step Process Mining pipeline (two model calls deep), a half-written metric, unapplied connection settings. Writes are best-effort — quota, private mode and corrupt JSON all fall back to the empty form rather than throwing, and a draft past `MAX_DRAFT_BYTES` (512 kB) is dropped *and* cleared, since a stale draft read back is worse than none. Three rules keep it from becoming a nuisance: values are stored in a versioned envelope carrying the write time and **expire after `MAX_DRAFT_AGE_MS` (7 days)** — a three-week-old draft would reopen a pipeline on topics that may no longer exist — an unrecognised envelope is erased rather than guessed at, and **nothing is written until the form actually moves**, so merely visiting Process Mining no longer seeds thirteen keys for someone who typed nothing (a draft that already existed keeps being maintained, including back at the initial value: erasing there would decide for the caller, whose explicit gesture is `clearDraft`). `useDraftConflict(names)` listens on the `storage` event — fired only in *other* tabs, so no self-echo — and the page **says** that another tab is editing the same draft rather than synchronising: overwriting a form in mid-typing because something changed elsewhere is worse than the problem. Wired into `ProcessMining` (pipeline acquis only — `processMiningDraft.ts`'s `resumableStep` refuses to reopen `PROFILING`, whose request died with the page, or a live `RESULTS`, whose SSE stream did, and the page says it resumed), the `Metrics` editor modal (restored open, cleared when the modal is closed — closing *is* the cancel gesture), `Compare`, and `Config`. **`Config` never drafts a secret**: `configDraft.ts` is an allowlist (`DRAFTABLE_FIELDS`), so `truststorePassword` / `keystorePassword` / `keyPassword` / `confluentSecret` / `llmApiKey` stay out of `localStorage`, as does server-owned state (`isConnected`, `llmApiKeyConfigured`) — the server's response is the base and the draft goes on top, which is also why `savedRef` tracks the server's version and a restored form correctly reads as modified.

**Navigation is centralized** in `navigation.ts` (single source of truth): `NAV_ITEMS` grouped into **Explore** (SQL Editor, Compare, Stream Flow) / **Observe** (Metrics, Audit, Cluster) / **Analyze** (Lineage, Process Mining), plus pinned Dashboard, and `CONFIG_ITEM` (Settings) / `HELP_ITEM` (Help). `resolvePageName()` and `groupNavItems()` derive the Header breadcrumb and Sidebar sections. Add a screen here, not in each component.

**Command palette** — `CommandPalette` (⌘K / Ctrl+K, wired in `Layout`) is the single global search over quick actions, pages, Kafka topics and Flink tables, fully keyboard-driven. What an operator types there is very often an identifier rather than a page name, so any text that is not a known topic offers **`Trace "<text>" across topics`** first (`buildTraceLinkForKey`, exact-key mode): an investigation starts from anywhere, instead of navigating to an empty form and retyping the key into it.

**Design-system library** — `components/ui/` (`import { … } from '../components/ui'`), built on the `tailwind.config.js` + `index.css` tokens; prefer it for any new surface: `Button`, `Card`/`CardHeader`, `Badge`, `EmptyState`, `ErrorPanel`, `Tooltip`/`HelpTip`, `PageHeader`, `Stat`, `Field`/`Input`/`Select`/`Textarea`, `Combobox`/`TopicInput`/`NumberInput`/`PasswordInput`, `Checkbox`, `RadioCards`, `Table` (+ `Th`/`Td`/…), the `Skeleton` family, `Spinner`/`ProgressBar`, `ConfirmProvider`/`useConfirm` (async confirm dialogs), `useUnsavedGuard` (confirm before leaving an unsaved screen — `useBlocker` for internal navigation *and* `beforeunload` for reload/close, two different exits, asked through the same `useConfirm` dialog), `useVirtualRows` (row virtualization), and `cn()` (clsx + tailwind-merge). Other shared components: `Toast`/`ToastProvider`, `ErrorBanner`, `LoadingSpinner`.

**The three SVG graphs share one viewport** — `components/graph/useGraphViewport.ts`, used by
`Lineage`, `StreamFlow` and `DataModel`. They carried the same implementation copied three times:
the same `isPanning` / `lastPos` refs, the same three pointer handlers line-for-line, the same
non-passive `wheel` listener, the same keyboard step. That is exactly the shape that lets a fix
land on one page and not the other two, and it had already happened here — the move to *pointer*
events, without which a tablet cannot pan a graph at all, had to be made three times.

The split is **mechanics in the hook, policy in the pages**. The hook owns the transform state,
the gestures, the wheel zoom and the viewport measurement, and exposes `panBy` / `zoomAround` /
`zoomFromCenter` so a page's keyboard handler is a few lines. What stays in each page is what
genuinely differs: what `0` recadres (a fit for Stream Flow and Data Model, a fixed origin for
Lineage), what `Escape` deselects, and which node a table selection brings into view. Absorbing
those through three more callbacks would have made the hook harder to read than the forty lines
it replaces.

Three things are parameters rather than constants because the pages really disagree: the scale
bounds (Data Model goes to 0.1–3, the other two 0.15–4 — a hundred entities need the lower
floor), the initial transform, and whether a press on a `[data-node]` starts a pan. `viewAdjusted`
is the hook's, with `markFitted()` / `markAdjusted()` as the pair of verbs: `panBy` and
`zoomAround` raise it themselves, and a page that sets its own transform — centring on an entity —
says so, because Data Model's automatic refit on a resize must not undo a framing the operator
chose.

**`svgRef` is a callback ref, not an object ref, and that is load-bearing.** Stream Flow and Data
Model render their canvas only once a result has arrived, so an effect keyed on anything else runs
once with `ref.current` still null and never runs again — which is exactly how the `wheel` listener
stopped attaching on two of the three graphs when this hook was extracted. Each page used to work
around it with its own dependency (`[hasResult, nodes.length]`, `[zoomAround, model]`) under a
comment reading "re-attach after the SVG mounts"; sharing the code dropped the dependency and the
defect came back. A callback ref makes the mount observable, so the question no longer reaches the
caller — and pages read the element as `canvas` rather than `svgRef.current`.

Only `zoomTransform` is unit-tested; the rest is pointer plumbing over geometry jsdom does not
have, where a test would assert that mocks were called rather than that a graph pans. What covers
it instead is **`docs/screenshots/graph-gestures.mjs`**, run by CI in the screenshot job: real
pointer, wheel and keyboard events against the compiled SPA in Chromium, asserting that the pan
follows the pointer, that the zoom stays anchored under the cursor, that the keyboard reaches the
graph and that `touch-action` is neutralised. It is what found the wheel defect above.
**`Checkbox` exists for a measured reason, and is deliberately 24 × 24.** `layout-probe.mjs` counts targets under the 24 × 24 CSS px of WCAG 2.5.8, and on the Data Model page — the worst ratio after the SQL editor — **40 of the 42 undersized targets were outside the graph**, almost all native `<input type="checkbox">` at the browser's default **13 × 13**, one per topic in the selector. It was never forty problems but one control, on the six screens that carry checkboxes; the measured effect is `data-model` 42 → 9 at 390 px, `audit` 30 → 24, `topic-explorer` 14 → 11. The visible box really is larger — keeping a 16 px box and widening only the hit area is the tempting version and does not work: `padding` is not reliably applied to a replaced control, and a `transform` shrinks the real target along with the drawing, fooling the probe exactly as much as the user. It stays a native input, so semantics, keyboard and form behaviour are the browser's, and its accent comes from the `primary` token — three call sites had hardcoded `#a3adff`, which *is* `primary`.
**`RadioCards` exists because a group of `<button aria-pressed>` is not a choice.** The Settings page drew its security mode and its LLM provider as cards that behaved like independent toggles while meaning one exclusive selection — which `aria-pressed` does not say. Concretely: five providers cost five tab stops, the arrow keys did nothing, and nothing announced "2 of 5". A native `radiogroup` gives all three without a line of JavaScript reimplementing them, the same reason `Checkbox` stayed a native `<input>`. Two details are load-bearing. The input is **`sr-only`, never `hidden`** — it stays focusable and is what actually takes focus, so the visible ring is carried by the sibling `<span>` through `peer-*` (a sibling selector, not `:has()`) and keyboard focus stays visible where `:has()` is not available; the selected state is computed in JS for the same reason, a component that exists for accessibility not being one to make it depend on a CSS variant. And the card carries `p-3`, so the target clears WCAG 2.5.8 by a wide margin — which is what made the *probe* the thing that had to change when this landed, not the page: `layout-probe.mjs` counted the 1 × 1 hidden input rather than the card labelling it, 13 false rows on one page, and `targetBox` now attributes a visually hidden control to its label.
**An explanation that only the mouse can reach is not an explanation.** `title=""` shows up on hover and nowhere else — never on keyboard focus, never on touch, with a delay and a rendering the browser owns and screen readers do not reliably announce. `Tooltip` opens on hover *and* focus, closes on `Escape`, and keeps its content mounted so `aria-describedby` always resolves; `HelpTip` is the small ⓘ trigger for controls that are not themselves inviting to hover, such as a `<select>` or a checkbox. Keep `title` for a bare affordance ("Copy"), and use the component wherever the text explains a *semantic* — what a mode compares, what an operator ignores, what a budget bounds, what an engine cannot do. The pass covered Topic Explorer, Stream Flow, Audit, the SQL editor and Metrics; what stays a `title` elsewhere only reveals a truncated or compacted value (the exact number behind `1.2K`, the absolute date behind a relative one), where a tooltip would add a tab stop per table cell and cost keyboard users more than it gives them. In `Metrics` the component is imported as `InfoTooltip`: Recharts exports a `Tooltip` of its own, and the file uses both.
**A failure that needs acting on is not a toast.** `ErrorPanel` renders a `QueryErrorInfo` (from `describeApiError`) with the three levels the SQL editor already had to itself — readable title, actionable hint, raw server text one click away — and stays on screen. A toast lasts three seconds, which suits a confirmation and not a refusal: `catch { toast('Failed to save metric') }` threw away the only useful part, the reason. Reach for the toast on success and for the panel on failure.

**Form conventions** — build every form out of these; hand-rolled `<input className="…">` blocks drift from the tokens and skip the accessibility wiring.
- `Field` owns the label ↔ control ↔ error/description `aria` plumbing and renders its child through a render prop (`{p => <Input {...p} />}`). Pass an explicit `id` when the form needs to focus the first invalid control after validation.
- **Validate every field at once**, into a `Partial<Record<field, string>>` handed to each `Field error=…`, and focus the first offender — not one message at a time in a banner at the bottom of the page.
- `NumberInput` keeps the raw string while typing and only coerces on blur. Never `parseInt(e.target.value) || fallback` on change: clearing the field snaps it to the fallback mid-typing, and `0` is falsy so a leading zero does too.
- `catalogStore` carries **what `Layout`'s existing `/api/dashboard` poll already answered**, and nothing else: the topics, the Flink tables, `internalPrefix`, and `bootstrapServers`. That last one was read by the Metrics page through a `GET /api/config` posted at mount for that single field, under a response shape declared by hand at the call site (`{ bootstrapServers: string }`) — a request more, and a shape `check-api-types.py` cannot see, which is the pattern that killed the Compare page. It comes off `DashboardResponse`, which is `@java`-verified and already carried it. The rule is the one written beside `internalPrefix`: a value belongs here when it is *the same response* that brings it, and a second carrier is how two answers to one question begin.
- `TopicInput` suggests topic (or Flink table) names from `catalogStore`, which `Layout` fills from its existing `/api/dashboard` poll — no extra request. Free text stays valid: a topic can exist before the 30s cache shows it. **Opening the list deliberately — the chevron, or ArrowDown from the field — shows every option, unfiltered** (`browseAll` in `Combobox`); typing goes straight back to filtering. Suggestions are filtered by the field's own value, so a value already chosen filtered the list down to one entry identical to itself, which the "a suggestion equal to what you typed teaches nothing" rule then dropped: the list was empty from the moment anything was selected and the chevron did nothing at all. In the metric editor, which pre-fills the topic with `topics[0]`, that removed the ability to change the topic from the list outright — the `<select>` it replaced could always be reopened.
- `PasswordInput` adds a reveal toggle and `autoComplete="new-password"`. Secrets typed blind fail at connection time with nothing to diagnose.
- Wrap in a real `<form onSubmit>` so Enter submits from any field. `Button` defaults to `type="button"` for that reason — submit buttons declare `type="submit"` explicitly.

**Routes / pages** (`pages/`):
- `Dashboard` (`/`) — topic list with filtering. **The refresh cadence is a control, and the page dates what it shows** (`pages/dashboardRefresh.ts`, pure + tested): the poll was a module constant — 5 s, not adjustable, not switchable off, and never stated — yet every turn calls `/api/dashboard`, which lists the topics, their sizes and their last-message timestamps. The reads are cached 30 s server-side, so six turns in seven re-read the same entry and the seventh pays the broker round trips; nobody watching a pipeline start could speed that up, and nobody keeping the page on a second screen could slow it down. Four rules hold it. **The default is today's behaviour** (`DEFAULT_REFRESH_CHOICE` = the 5 s that were hardcoded): making a cadence adjustable must not change what an existing install does. **`Off` is a value of the same selector**, like the activity column's, and for the same reason — the poll costs broker round trips, so it has to be switchable from the screen and not only from a configuration file — but **returning to the tab still reads once**, polling off included: what `Off` asks is that the broker not be queried in a loop behind the operator, not that they be shown hour-old numbers at the moment they come back to look. **The activity column follows the same setting with its own floor** (`activityIntervalMs`, `ACTIVITY_FLOOR_MS` = the 30 s server cache): the choice *slows* it and never speeds it up — a 2 s dashboard must not hammer a 30 s cache — and `Off` stops both, one switch, or the page would go on polling after being told to stop. And **the page says when it read and what it will do next** (`describeRefreshStatus`): `fetchedAt` existed and only fed the relative last-message times, so nothing stated the age of the figures. That was survivable while the cadence was 5 s for everyone and stops being so the moment it can be five minutes or nothing — a number nobody can date is a number nobody should act on, the same rule as the Prometheus gauges. Both halves together: the age alone reads as a breakdown, the cadence alone doesn't say where in the interval you are. An **activity sparkline per row** sits beside it (`components/dashboard/Sparkline.tsx`, pure logic + tests in `pages/topicActivity.ts`). The table said how many messages a topic holds and when the last one arrived, which is a level and an instant — neither says whether the topic is *working*, and "1 200 messages, 3 min ago" reads the same on a topic doing forty a minute and on one that received a burst yesterday and stopped. Four rules keep the column from claiming more than it measured. It reads **only the rows on screen** (`pagedTopics`), on its own 30 s cadence rather than the dashboard's 5 s poll — asking for a nine-hundred-topic cluster would spend an offset sweep nobody is looking at, and re-asking every 5 s would only re-read the same cache entry six times. The **scale is per row** (`sparkline`), since a scale shared across the table would flatten every topic that is not the busiest of the cluster — so the peak is **written beside the curve** (`describeRate`, `620/h`), not only in the tooltip: an explanation only the mouse can reach is the exact defect `title=""` was replaced for elsewhere, and two curves of equal height can be 40/h and 40 000/h. Hovering a bucket replaces that number with the bucket's own value and marks it on the curve, rather than opening a twenty-sixth tooltip. **The curve is a button and the click leads to the messages** (`bucketLink`): seeing a spike and reading what was in it are the same question asked twice, and the second half was being done by hand. It opens the topic's explorer with the search *primed* at that bucket's instant — primed and not run, because the topic search has no "everything" criterion by design (KEY + `EXISTS` was deliberately removed from that UI for returning everything scanned), so the link carries what it knows and the operator says what they are looking for. It travels through the **URL** (`?start=TIMESTAMP&at=…`, read back by `seedFromQuery`) rather than through the explorer's `localStorage` draft: that is the convention of every other screen here, it makes the link shareable, and it does not silently overwrite an unrun criterion on another topic. A button rather than a bare SVG because the affordance has to exist for the keyboard too — `Enter` opens the **peak** bucket, which is what the accessible name already names. That adds one tab stop per row, which this codebase refuses for a *tooltip* and accepts here for the same reason the row's `Explore` link is one: there is an action behind it. **Beside the peak sits the current regime, when it departs from the topic's own** (`detectTrend`, `▲ 2.4×`): the shape answers that question badly at the size of a cell and the peak does not answer it at all — it describes the busiest moment of the window, which may be twenty hours old. The reference is the window's **median**, not its mean, which the very burst one is trying to situate would pull; and the ratio reads without knowing the topic, where `620/h` does not. Same discipline as the badge beside it: at least six buckets with four non-empty (a median needs matter), a non-zero median (a ratio against zero is a division dressed up as information), and a departure of at least a factor two — below that it is the ordinary noise of a live topic, and an indicator that lights up always is one that stops being read. An **empty** last bucket produces nothing here: that is `detectSilence`'s case, which says it better and has its own threshold. **A topic that produced and stopped says so** (`detectSilence`, an amber `silent 6 h+` in place of the peak): it is the one thing a curve of this size does not show — a series fallen to zero and a low series look alike — and `Last Message` only gives the instant, not the fact that there was a regime before it. Three guards keep the badge from being noise (a prior regime of at least two non-empty buckets, a silence of at least two buckets *and* 15 % of the window, and a window that is not entirely empty — that last one is not a topic that went quiet, it is a topic nobody saw produce), and what it states is a dated fact rather than a verdict: `silent 4 h+` is true of a topic that sleeps at night, and whether that is a problem is the operator's to know. The duration is a **floor** — the last message sits somewhere inside its bucket — which is what the `+` carries. **Nothing is drawn where nothing was measured**: the stretch retention emptied is greyed rather than traced at zero, a series short of a partition is dashed, a topic that could not be read says `not measured` instead of showing a flat line, and a failed read replaces the curves with its reason instead of leaving them flat — a flat line is a claim that the topic is quiet. And the **window is a control** (`Last hour` / `Last 24 h` / `Last 7 days` / `Off`, kept in `kse:dashboard-activity`): `Off` is one of its values because the column costs broker round trips, so it must be switchable from the screen and not only from a configuration file. Each window carries its own resolution, and the week's is **56 points of 3 h, not 28 of 6 h**: over seven days the question is almost always whether the shape repeats, and a day reduced to four points shows no cycle at all — the night and the morning fall in the same one. The cost is the server's and is bounded there (57 boundaries per partition instead of 29, all issued in parallel, all counted against `explorer.activity-max-lookups`). **The vertical scale is a second control** (`Linear` / `Log`, `kse:dashboard-activity-scale`, `ActivityScale`): a burst a hundred times the ordinary regime crushes everything else onto the baseline, and what happens the rest of the time is usually what one is trying to read. It stays an option rather than the default because changing the scale changes what the image asserts — under `log` two heights are no longer in the ratio of their values — which is also why the column header names it when it is on: an undeclared scale is precisely what makes a chart mislead. `log1p` rather than `log`, so an empty bucket sits exactly on the baseline instead of running to minus infinity or needing an arbitrary offset, and the peak is the top of the box under either scale. It is a **reading** control and touches one thing: the shape. It changes nothing that is asked of the server, and nothing the accessible name states, which is raw counts either way. The response is held with **the question it answers** (`activityState.key` = window + topics), so changing page or window never leaves the previous series under the new header for the length of a round trip. The column is deliberately **not sortable**: it is measured for the displayed rows only, so sorting the cluster on it would sort on what was never read. **What a topic's name says about its role lives in `pages/topicKinds.ts`**, not in the pages that ask (`isRetryTopic` / `isDeadLetterTopic` / `deadLetterLabel`, pure + tested). The rules were written in clear at four sites across two files — the row's state, the `Hide …` filter, the Topic Explorer's badge, and the retry marker — which is the pattern this repository already paid for once with the four literal `'internal.'` prefixes now held by `internalTopics.ts`: four copies is four chances for the fifth to be written differently, and the divergence does not show, a topic merely unrecognised looking like an ordinary one. Three decisions are load-bearing. **Retry matches anywhere in the name, dead letter only as a suffix** — a retry queue is as often `retry-orders` as `orders.retry.5m`, while a dead letter is a suffix by convention, and recognising the marker mid-name would badge a live topic as dead. **Both spellings count**: only Spring Kafka's `DeadLetterPublishingRecoverer` writes `.DLT`, Spring Cloud Stream and most of the ecosystem say `.DLQ`, so the rule that knew one of them let the other half through in silence — with the three separators the ecosystem uses (`.`, `-`, `_`) for the same reason, recognising only the dot repeating the half-coverage one notch down. And the badge **names the suffix the topic carries** rather than saying `DLT` to everyone, which would assert a convention the producer did not follow; the switch is `Hide dead letter`, since a label naming one spelling would understate what it hides. Nothing here is configurable — these are ecosystem naming conventions, not settings of this deployment — and the day they must be, the value travels on `DashboardResponse` like `internalPrefix` rather than as a second browser-side copy.
- `QueryController` — `/api/query/**`. A path-less `@PostMapping` duplicating `/run-sync` was removed: nothing here ever posted to it, so it was a second public entry point to the query engine that no test exercised — two paths to one behaviour is how they drift. `ddl-preview` reports a failure through `SqlErrorClassifier.explain()`, **not** `e.getMessage()`: that is null for a `NullPointerException` and `Map.of` rejects a null value, so the handler's own error path answered 500 in exactly the case where the caller most needs a reason. Its `@RequestParam` is named explicitly so the mapping resolves without `-parameters` on the compiler command line (the offline harness compiles with plain `javac`). `init` **reports why it came back empty** (`kafkaError` / `flinkError` on `QueryInitResponse`) instead of ending both of its probes in an empty catch: an unreachable broker, a wrong bootstrap address, an authorisation failure and a Flink runtime still starting up all rendered as the same "Engine offline · 0 tables · 0 topics". The probes stay independent — one side failing must not empty the other — and a broker that answers `pingDetail()` but refuses the metadata call keeps `health: true` with the reason beside it, since "offline" would send an operator to check a connection that works. `cancel` **says what it achieved** (`{cancelled, outcome}` from `FlinkSqlService.CancelOutcome`) rather than returning `void` behind a 200: a `KAFKA_DIRECT` scan has no Flink job by construction, so "nothing to cancel" is the common case and the UI must not report it as a cancellation — it says "Request aborted — the server finishes its in-flight read" instead. Still 200 either way, since nothing to cancel is a legitimate outcome of a well-formed request. `QueryControllerTest` pins the three endpoints with standalone MockMvc. `submitJob` **answers with a reason** (`ApiError`, the shape `MetricController.save` already serves) instead of an empty status body. It had two ways of saying nothing: the whitelist refusal travelled in a `ResponseStatusException`, whose reason lands in the `message` field of Spring's default error body — suppressed, since `server.error.include-message` is `never` — and every other `RuntimeException` was not caught at all. The browser reads `message` then `error` and had neither, so `describeApiError` fell back to the status label and the one gesture of the SQL editor with no fallback engine was also the only one that could not be diagnosed. The status splits on `SqlErrorClassifier` rather than on a second rule written here: a user error is a 400, an engine failure stays a 500, and both carry the engine's own sentence. Flink's wording for a missing INSERT *target* (`Cannot find table '…' in any of the catalogs`) was added to that classifier — a SELECT's source says `Object 'x' not found` and was already covered, so a typo in a sink name was the one name error answering 500.
- `QueryWorkbench` (`/query`, nav "SQL Editor") — Monaco SQL editor; saved queries + history in `localStorage` (`kse:saved-queries`, `kse:query-history`). **Every failure lands in one error panel**: `pages/queryError.ts` (`describeQueryError` / `describeApiError`, pure and unit-tested) turns a raw engine message into a readable title, an actionable hint and — when the message cites one — a line/column, which drives both a "jump to line" button and a native Monaco error marker; the raw text is always kept behind "Show raw error". The `panelError` state carries failures that no `QueryResult` holds (execution-mode rejection, `POST /api/query/validate`, transport failure) through that same panel, and is cleared as soon as the SQL is edited so a stale marker never points at a moved position. `QueryResult.warnings` is rendered above the grid — the direct engine reports the WHERE predicates it could not apply, and dropping them presented an unfiltered scan as a filtered one. Tabs persist to `localStorage` (`kse:tabs`, restored once at first render, **written on a 400 ms debounce** — the effect ran on every keystroke, so each character cost a `JSON.stringify` of every tab and a synchronous storage write; a `?sql=` opens an *extra* tab rather than clobbering the first), which is why there is no longer a `beforeunload` guard. **The `?sql=` is then stripped from the URL**: since the tabs are persisted and the parameter was not, every reload re-appended the same tab, without bound. Closing a tab that holds SQL asks first — that text exists nowhere else afterwards — and `nextActiveTabId` picks the successor *outside* the `setTabs` updater, which used to call `setActiveTabId` from within it. The row cap is a real control wired to `maxRows` — the "limit reached" badge compares against the limit *that query* ran with, not a frontend constant that silently drifted from `explorer.default-max-rows`. Autocomplete and hover cover **Kafka topics as well as Flink tables** — they read `schema.tables` only, while the sidebar lists topics, clicking one writes `SELECT * FROM demo_orders_1_received`, and the backend auto-registers a topic on a plain SELECT, so typing that name got no help at all; topics are offered under their table name, labelled and sorted behind the registered tables. Column autocomplete is scoped to the tables the query actually cites (`pages/sqlScope.ts`, pure and unit-tested: comments and string literals stripped, `TABLE(TUMBLE(TABLE t, …))` understood, topic↔table naming normalized), and their schemas are fetched on a 500 ms debounce, at most once per name per catalog refresh. **What Run sends**: a non-empty editor selection when there is one, otherwise **the statement the cursor is in** (`splitStatements` / `statementIndexAt`, which walk strings, quoted identifiers and both comment forms so a `;` inside any of them separates nothing, and pick the statement *just finished* when the cursor follows its semicolon — as DataGrip and DBeaver do). Run used to send the whole tab whatever the cursor was in while the backend classified on the first word, so selecting by hand was the only way to run one query among several. `offsetLocation()` maps the engine's line/column back into document coordinates in both cases; without it the Monaco marker would point at the top of the file. The toolbar states `Statement 2/3` before you press, and **`Run all`** (⌘⇧↵) executes them in order, stopping at the first failure and naming it — creating a table then reading it is what auto-registration encourages, and it had become two gestures.
  **Running several statements keeps what each one gave, not only the last.** `planRun` decides what a gesture sends — the selection when there is one, the cursor's statement otherwise, every statement for `Run all` — and a **selection spanning several statements now runs them one after another** instead of going to the planner as one query it rejects on the `;`; a selected *fragment* still goes verbatim, since trying a sub-expression has to keep working, and a tab holding only blanks or comments answers `Nothing to run` rather than asking the engine to say what was already known. Each statement of a batch keeps a `StatementRun` (kind, status, duration, rows, engine, result), listed in a strip above the grid: selecting one brings its rows back **with the row cap it ran under**, since the "limit reached" badge must not judge an old result by how the selector is set now. `runAllStatements` used to call a loop that begins with `setResults(null)`, so five statements left one grid and no trace of the other four — no rows, no duration, no engine, no proof they had run. Retention is bounded and **stated**: `forgetOldestResults` releases the oldest rows past `MAX_RETAINED_BATCH_ROWS` (10 000 across the batch, never the entry on screen) and the released ones render as "4 000 rows, no longer held" with a rerun button — an empty grid would read as zero rows, which is the opposite answer. Statements the batch never reached are `skipped`, distinct from a run that returned nothing. Three things that could go wrong while a batch ran are closed: `executeStatement` returns an outcome (`ok` / `failed` / `cancelled`) rather than a boolean, so a **Stop is no longer reported in red as a failure**; `batchRef` refuses a `⌘↵` landing *between* two statements, where `executingRef` is false and a keystroke started a query concurrent with the loop; and **Stop stops the batch**, through a flag the loop re-reads after each statement — aborting the in-flight request did nothing in that same gap, and the button was not even rendered there. `Statement 2/3` and `Run all` are unconditional — they were once shown in Read mode only, which meant a tab of several statements ran one of them with nothing saying so. And `isResultStale` now consults the tab's statements: comparing what ran against the whole tab made every multi-statement result permanently "stale", and a warning that is always on stops being a warning. A **`Link`** button copies a replayable `?sql=` URL: the editor accepted one without ever producing one, unlike Stream Flow and the Topic Explorer. `readSqlParam` does the **single** decode `URLSearchParams` already performs — the caller decoded a second time, which throws `URIError` on any `%`, so a shared `LIKE '%foo%'` took the whole page down from inside a `useState` initializer — "Run statement" without saying which one is the worrying half of the feature. The Window Assistant (`pages/windowSql.ts`, pure and unit-tested) **folds to a rail** (its state in `kse:query-layout`; it used to cost the editor 288 px permanently for an occasional tool) and emits genuinely different SQL per window type (the dropdown used to produce `TUMBLE` whatever the choice), pre-fills the time column from the loaded schema instead of hardcoding `event_time`, states its caveats (SESSION needs a `PARTITION BY`; HOP/SESSION are approximated if the query falls back), and **replaces the whole editor content** rather than inserting at the cursor: what it emits is a complete query, not a fragment, so an insertion almost always left two statements stuck together to untangle by hand. The replacement goes through Monaco's edit API over the full model range rather than through `updateSql` — writing the value from React calls `model.setValue()`, which clears the undo stack, so the overwritten query would be gone for good; through `executeEdits` it is one ⌘Z away, and the toast says so. A tab that already holds SQL asks first (`useConfirm`, as everywhere else): the undo rescues the loss but is only discovered afterwards, and one click must not erase a query being written without saying so — an empty tab has nothing to lose and asks nothing. CSV export goes through `pages/resultExport.ts` (RFC 4180): the old `JSON.stringify` per cell left a multi-key object's comma unquoted, shifting every following column — and it now serialises **what is displayed**, `sortedRows`, where it used to take `results.rows` and hand back a file in a different order from the screen.
  **The sidebar's shortcut poses a bounded read, and nothing else** (`sidebarSqlFor` / `sidebarActionLabel`, pure and unit-tested): `SELECT * FROM <table> LIMIT <maxRows>`. It used to follow an execution mode, posing an `INSERT INTO` skeleton in **Flink Job mode** — a target chosen out of the catalogue, its columns listed to keep `proc_time` out of the projection, the sink name posed selected. That mode has been **removed from the editor: it did not work**, and a gesture whose only possible outcome is a failure is worth less than no gesture. Everything that existed only to serve it went with it rather than being left without a caller (`pickSinkTable`, `insertableColumns`, `sinkNameRange`, `starterJobQueries`, `StarterQuery.preview`, the `job` field of `StatementRun` and its type parameter) — a helper nobody calls is the affordance this codebase keeps removing. Its server side went with it as an *entry point*: `POST /api/query/jobs` no longer exists, so nothing reachable over HTTP can submit a continuous job. `FlinkSqlService.submitJob` itself is still there — it is what `FlinkSqlServiceInsertVariantsTest` drives against a real MiniCluster to enumerate the shapes of an INSERT, so it is the service-level home of those semantics rather than dead code, and removing it would mean deleting that suite. The three job *reads* have gone too. They outlived the mode because the Dashboard's "Flink SQL Jobs" panel called them, and without a submission that panel no longer listed jobs: it listed the synchronous reads `FlinkJobStore` recorded on the way past, already finished, one per Run and ~2 900 a day per planner-answered metric. The panel went, and `GET /api/query/jobs`, `GET /api/query/jobs/{queryId}`, `POST /api/query/jobs/{queryId}/cancel` and the store itself with it. `POST /api/query/cancel/{queryId}` stays — it is the editor's Stop button, and it reads the in-memory registry those synchronous reads still feed.
  **A changelog is marked in the grid, not smoothed away** (`rowKindOf`, `describeChangelog`, `exportColumns`/`exportRows`, `ResultsGrid`'s leading marker column). The server now says which rows are corrections; what only the interface can do is show it per row and change what "limit reached" means. The marker column appears **only** when the result is a changelog — a column reading "+" on every row of an ordinary SELECT costs width for nothing — it is a column of its own rather than an entry in `columns`, so it is never sorted, never exported as a value and never described as engine data, and it carries the full wording for a screen reader beside its symbol. The `limit reached` tooltip is replaced on a changelog: the ordinary "raise Rows to fetch more" is true and beside the point when what the cap cut off is the row that settles the answer. **The export carries the marker too**: a file cannot be interrogated, so a CSV that does not say which of its rows are corrections presents them as results — the exact lie the marker removes from the screen — and the kind is written on *every* row there, an implicit `+I` being unreadable in a file.

  **A refusal the engine now returns is a refusal the editor can explain** (`describeQueryError`). Making the classifier hand user errors back instead of falling back to the direct reader surfaced messages the editor had no family for, so they arrived as a raw title with no hint — on the half of the machinery that exists to make a correct message actionable. Five families were added: an unbounded `ORDER BY` (a stream has no last row, so the fix is a `LIMIT`), a correlated subquery (rewrite it as a JOIN), a projection that does not fit the sink — Flink words that one fault three ways, and "Different number of columns", the commonest, fell into the generic fallback while "Incompatible types for sink column" fell into the type family, which advised casting a column when the problem is the column *list* — a sink that cannot honour `INSERT OVERWRITE`, and an options hint applied to a view. The `CREATE TABLE … AS SELECT` refusal got one as well, its two-line server message having arrived as a title.

  **An `EXPLAIN` plan is text, and is rendered as text** (`explainPlan`, the `ExplainPlanPanel` component under `components/query/`). Flink returns a plan as **one row of one column** whose content is twenty indented lines. The grid took it as it came: a giant cell, truncated to a single line as soon as the grid virtualises, readable only by opening the row-detail panel — the same fault this repository replaced `title=""` for everywhere else, content that exists and needs one more gesture to reach, on the one query whose result *is* text to read. It is `whitespace-pre` rather than `pre-wrap`, because a plan's indentation carries its structure and wrapping the long lines destroys it; the overflow scrolls horizontally like every other wide surface here. Two conditions decide it rather than one, and that is what makes it safe: the statement that ran must be an `EXPLAIN` **and** the result must have a plan's shape (one row, one column, text). If Flink ever returns something else, the grid takes it back instead of being handed a rendering that does not suit it. The SQL consulted is the one that *ran*, never the tab's current contents.

Three were gone at that point: **`GET /api/query/sink-ddl`** (its only caller was the submitted-job panel's "create the target" button, so an HTTP endpoint taking two query parameters to go and read a schema was left with nobody guarding it — the rule this repository already applied to `POST /api/metrics/preview` and to `TableController`), with `DdlGeneratorService.sinkColumns` behind it; **`insertTargetAndSource`**, whose production caller was that same button; and **`flinkJobHistory.isJobTerminal`**, whose production callers were the panel and its poll. The rest of that module has since gone with `FlinkJobCard`, when the Dashboard's job table was removed. Each had tests, and the tests went with the code — a test that renders a component nothing imports is what keeps dead code looking alive. `sink-ddl`'s three cases are replaced by one pinning its absence, the shape `theUncalledSqlPreviewEndpointIsGone` already uses.

It is unreachable over HTTP and it is not dead code — it is where `FlinkSqlServiceInsertVariantsTest` drives nineteen cases against a real MiniCluster to establish what an INSERT means here, including the classifier rules only an INSERT can provoke (a projection that does not fit the sink by arity or by type, a sink that cannot honour `INSERT OVERWRITE`) and the two editor error families that read them. Deleting it would take all of that with it, so what was corrected is the *claim*: the setting's documentation described a live ceiling.

That panel followed a submitted job, and it was reachable from exactly one place: a submission. A helper nobody calls is the affordance this codebase keeps removing; this was the same thing one size up — a whole feature's wiring left without the feature. Same rule as everywhere else on this page: a refusal that names the cause beats one that names a rule.

A second `⌘↵` while a query runs is refused through a synchronous ref: the Run button disables itself but the keybinding bypassed it, and the second run overwrote the abort controller and query id, leaving Stop unable to cancel the first.

- `TopicExplorer` (`/topic/:name`) — message sampling, schema preview and **server-side search** over the whole topic. **The page opens on one read of the topic, where it used to take three**: `GET /api/topic/{name}` called `detectFormat`, which sampled the topic, then `inferSchema`, which sampled it again for the identical ten records, then fetched the messages to display — three `KafkaConsumer`s, three reads, on the one endpoint a user actually waits on. The audit had already learned this and the `detectFormat(topic, samples)` / `inferSchema(topic, format, samples)` overloads exist for exactly this; the controller was left on the un-shared path. Inference now reads the records the page displays, capped at `explorer.inference-sample-size` so that property still governs how much inference looks at — which also makes the two agree, the schema and the DDL having been inferred from the *newest* records while the panel below showed the oldest, so the column list could describe records nobody was looking at. (`components/topic/TopicSearchPanel.tsx`): text / regex / field / header / key modes (plus a "search headers too" switch that widens a text or regex pass to every header value, and a "only this key's partition" switch on an exact key search), the field list fed by the inferred schema, a time range, and a status strip stating hits, records scanned and why the pass stopped. Pure logic (critère, corps de requête, couverture, surlignage, URL) lives in `components/topic/topicSearch.ts` and is unit-tested; the panel only renders what it decides.
  **Which end the scan enters by is a choice, and the default is the newest** (`ScanDirection`, `buildSearchBody`): `NEWEST` sends `from: LAST_N`, so the server walks back from the end and a time window *raises that floor* instead of replacing it. The panel used to send `EARLIEST` always (`TIMESTAMP` with a window), which spent the whole 20 000-record budget on the oldest history of a topic with millions — a record from ten minutes ago was reported as "scan budget reached, 0 match", and the page's own Earliest/Latest toggle (which only drives sampling) made that look deliberate. Because a cursor points *forward*, past the newest record read, "continue scanning" cannot reach older records: `nextScanAction` therefore offers `RESUME` (cursor) only while the pass has not reached the end of its range, and `DEEPEN` — the same `LAST_N` read again with a doubled `maxScan`, up to the server's 1 000 000 cap, results replaced — once it has. For the same reason `describeCoverage` never says "whole range scanned" on a `NEWEST` pass: it says *newest N records scanned*, since everything before the window read was never opened.
  **The coverage is that of every pass together** (`SearchCoverage` / `coverageOf`): a response describes only its own pass, so showing `response.scanned` after three resumes claimed 20 000 records where 60 000 had been read. A resume adds up (it reads new ground), a fresh run or a deepening replaces (it re-reads the same). **A pass is cancellable** (`AbortController` + a generation counter, like a trace): what comes back from a superseded or abandoned pass is dropped, and the panel says the pass was abandoned rather than letting the displayed results pass for its outcome.
  Messages carry their coordinates (partition, offset, timestamp, key, headers), and **a hit shows why it is one, whatever the mode**: `highlightFor` marks the literal of a text search, the pattern of a regex one (`splitOnRegex`, which returns the text unmarked on an invalid pattern and cannot loop on a zero-width match) and the compared value of a field / header / key search — but nothing at all for `NEQ` / `GT` / `EXISTS`, where marking the value would designate precisely what is *not* there. Highlighting describes the run that is displayed (`ranCriteria`), never the form as it is being edited. Kafka **headers are rendered inline** and expand on their own when the match could have been decided there (`revealsHeaders`), with the compared header named (`highlightedHeader`): they used to live in a `title` tooltip, so a HEADER search returned ten cards whose evidence was reachable only with the mouse, one at a time. The read-mode toggle drives which end of the topic is sampled, not only the generated DDL. **The unrun criterion survives leaving the page** (`readCriteriaDraft` / `saveCriteriaDraft`): the URL carries an *executed* search, so a half-typed criterion abandoned to go check a field name elsewhere died with the page. One slot, stamped with the topic it belongs to — a key per topic would grow `localStorage` without bound for a case that is always "I am coming back to the topic I just left" — and a criterion from another topic is not restored. A search carried by the URL always wins. **A URL can also *prime* the form without running it** (`seedFromQuery`): the dashboard's sparkline links here with a start instant and no criterion, which is not executable — `criteriaFromQuery` rightly answers `null` — and answering `null` while posing nothing would land the operator on an empty form, losing the only thing the link carried. The two functions are exclusive by construction (`canRun` decides which one answers), and a *present but unknown* `mode` stays refused by both rather than being reinterpreted as a text search. A search **round-trips through the URL** (`?mode=&q=&field=&op=&value=&case=&keys=&headers=&keyPartitioning=&since=&dir=&parts=&scan=`, `criteriaFromQuery` / `buildSearchQuery`): it is applied and run on open — which is how a Stream Flow hop lands on its messages instead of having the criterion retyped into a form that has different fields — and rewritten after each run so a search can be shared and replayed, with `Link` copying it and `Clear` stripping it (`Clear` keeps the criterion in the form: erasing the results should not erase the question). The page guards against reading back the query string it wrote itself, which would rerun the search that produced it, forever. The last eight searches per topic are kept in `localStorage` (`kse:topic-search-history`, de-duplicated on the criterion, entries from an older shape completed against `emptyCriteria` rather than replayed with holes), and the hits export to CSV or to JSON — the JSON carrying the criterion, the coverage and the warnings, since an export pasted into a ticket has to say what it covered.
  **Where the scan starts is a choice too** (`StartMode`, `switchStart`): a relative window, an absolute instant (`fromTimestamp`) or an offset (`fromOffset`) — the last two were served by the API and reachable from nothing, while an incident question almost always takes the form "from 14:02" or "from offset 128000", the latter usually arriving from a lag alert that already gives the number. An instant behaves exactly like the relative window it replaces (a floor under `LAST_N`, a starting point under `TIMESTAMP`); an offset is a forward read, so it overrides the direction, which then disappears from the form rather than sitting there being ignored. A future instant is refused: the broker returns no offset for it, so the floor would silently vanish and the scan would read the newest records while claiming to start from that date. `describeCoverage` never says "whole topic" after a chosen start — everything before it was never opened — and `nextScanAction` offers no deepening there, since a wider budget cannot move a fixed starting point.
  **The hit cap is a control** (`HIT_CAPS`, the API's `maxHits`, clamped to 1 000 server-side) and `raiseHitCapAction` is what a `MAX_HITS` stop offers. Resuming reads on *past* the records already scanned, so the matches skipped beyond the cap are out of reach for good — "12 of 340" with a "continue" button was an invitation to a scan that would never show them. Rereading with a higher cap is the only gesture that does, and it replaces the results.
  **A truncated record can be read whole** (`GET /api/topic/{name}/record?partition=&offset=` → `TopicSearchService.readRecord`): a hit is cut to `search-max-value-chars` so that a hundred of them stay a small response, which left the `truncated` badge pointing at a remainder nothing could fetch. Reading one record on purpose is the opposite need, so it has its own budget (`explorer.record-max-value-chars`, 1 000 000) — and still reports `truncated` and the original size at that boundary. The endpoint answers 404 when the offset holds no record: out of range, or compacted away, which a caller must be able to tell from a failure.
  **The scan can be narrowed and deepened from the screen**: a partition chip row (the API's `partitions`, which the server honours *over* key partitioning and without warning — hence `keyPartitioningApplies`, which stops offering the key switch once a partition is picked, and `describePartitionScope`, which states the restriction in the coverage strip, or a "0 match" on one partition of twenty-four would read like a "0 match" on the topic), and a scan budget (`SCAN_BUDGETS`, the API's `maxScan`, which the server clamps to a million). `describeScanShare` situates the pass against the topic's estimated size — 20 000 records read means something different on a topic of 30 000 and on one of two million. When nothing matched, `suggestWidenings` turns the advice into at most four one-click reruns (match anywhere in the field, search the raw payload, search headers, ignore case, every partition, drop the window, a bigger budget), each changing one thing and stating it.
  **A message has its own link** (`?record=p:offset`, `recordFromQuery` / `withRecord` / `buildRecordLink`): the URL described a search, never a record, so pointing a colleague at *this* message meant describing how to find it again. The parameter is independent of the criterion — a URL carrying only it runs no search, one carrying both shows both, and a search rewriting the URL keeps it — and the record is read through the same coordinate endpoint, so a compacted or aged-out offset answers with the server's own reason rather than an empty panel.
  **The working loop**: a **Follow** toggle repeats the cursor resume every `FOLLOW_INTERVAL_MS` (5 s) — resuming *is* a tail, since the cursor points past the last record read, so this only automates a click an operator was making by hand; it stops on an error, a cancel or a clear, and a resumed pass no longer writes history (a follow would rewrite it every five seconds). The value field in FIELD mode becomes a `Combobox` fed by `valuesAtPath` over the samples already loaded — no extra request, and free text stays valid — because nobody knows from memory whether the status reads `SHIPPED`, `shipped` or `Shipped`, which is the most banal cause of a zero. Searches **pin** (`kse:topic-search-pinned`, `togglePinned`) beside the history that scrolls past. Keyboard: `/` focuses the search field, `j` / `k` walk the hits in table view (through `nextSelectedRank`, over the *displayed* list so a filtered-out record is never selected), `Escape` deselects, all of it ignored while a field has the focus (`isTypingTarget`); `announceResult` fills a visually hidden `role="status"`, since the disappearance of "Searching…" tells a screen-reader user nothing.
  **The panel is a real `<form>`**: Enter submits from any field, `validateCriteria` checks every field at once into a `Partial<Record<field, string>>` rendered next to each control, and the first offender is focused through the stable ids `FIELD_IDS`. The Search button is no longer disabled on an incomplete criterion — it was grey and silent about what it wanted. The regex is compiled client-side, a numeric operator refuses a non-numeric value (the server compares numbers and would silently never match), `operatorsFor` drops `EXISTS` from a key search (it answers true without comparing, so it would return every record scanned), `switchMode` carries the typed text into the input the new mode actually uses, and a failed search lands in an `ErrorPanel` through `describeApiError` instead of a small red line.
  **Hits read as cards or as a table** (`kse:topic-view`), **and the table is the default**: one arrives here from the Dashboard, which is to say without having chosen anything, to see what is in a topic — a question a table answers at a glance (coordinates, key, preview, one line per record) where cards unroll a JSON tree per message and fit three on a screen. Cards remain the right tool for reading *one* payload whole, which is the next question, and selecting a row already answers it. The stored preference wins either way, which is why `readViewMode` compares against `'cards'` and not `'table'`: built the other way it would have shown the table to whoever had explicitly chosen cards, which is not changing a default but ignoring a choice — and an unreadable stored value falls back to the default, the same rule as `readActivityChoice`. The table is one fixed-height line per record (coordinates plus a `previewOf` payload) with the detail on selection, windowed through `useVirtualRows` — a hundred hits, each rendering a recursive JSON tree, both scanned badly and cost a lot. Columns **sort** and a text box **filters what is already fetched** (`rankHits` / `filterHits` / `sortHits`) without a server pass; a hit's `rank` is its order in the scan, so it survives both, and the selected row is tracked by rank rather than by index. `analyzeHits` / `describeHitInsight` read the hits above the list — the busiest partition, the time span, the keys seen more than once — because forty rows do not show by themselves that thirty-eight are on one partition. `MessageCard` is `React.memo`-ed and its parse/format memoized, with every prop the page passes it memoized too: the criterion lives in the page, so each keystroke in the form re-rendered the whole list and re-parsed every payload.

  **The scan options fold away** (`kse:topic-search-advanced`, `readAdvancedOpen` / `describeAdvanced`): direction, budget and partitions each earn their place and together they made a bar the eye stopped scanning. Folded, whatever departs from the default is still announced as a chip — an active option nobody can see is exactly what must not happen.
  **Warnings accumulate across passes** (`mergeWarnings`, de-duplicated, replaced by a fresh run or a deepening like the coverage): showing only the last response's warnings erased, on a resume, a warning that still described part of what was on screen. It refuses anything the panel's own `Search` button would refuse (unknown mode, no value, no target), snaps a free time window onto an offered scope, and a field path absent from the inferred schema is **added to the select** rather than leaving "Select a field…" above a search that uses it. Each message with a record key carries a **`route` action** back the other way (`buildTraceLinkForKey`): it opens Stream Flow on that key in exact-key mode — the key is known exactly, so an entire-value comparison on one partition beats a substring search that would also match messages merely mentioning it
  **An `Activity` tab answers "what does this topic's production look like?"** (`components/topic/TopicActivityPanel.tsx`, the same measurement the dashboard's column carries, from the same `GET /api/dashboard/activity`). The page knew what is in the topic, who reads it and how far behind — not the shape of what it produces, which is the first thing anyone looks at on an incident. Here there is room for what a cell cannot hold: a time axis (`axisTicks`), a hover that names the bucket and its count in words, and a **click that primes the search at that instant** — seeing a spike and reading what was in it becomes one gesture instead of two screens, where the dashboard's curve has to cross a page boundary to do the same. Mounted only when the tab is opened, the same rule as the consumers panel and for the same reason: the measurement costs broker round trips and nobody arriving to read messages should pay for it unasked. The chart is one `<svg>` stretched horizontally (`preserveAspectRatio="none"` with `vector-effect="non-scaling-stroke"`, so the time axis fills the width without thickening the line) — which is also why nothing in it is drawn with a circle, a circle becoming an ellipse, and why the hover marker is a plain line. The response is held with the question it answers (`key` = topic + window), so switching window never leaves the previous graph under the new label, and "loading" is that same comparison rather than a state posted from an effect.
  **A `Consumers` tab answers "why is this piling up?"** (`components/topic/TopicConsumersPanel.tsx`, pure logic + tests in `topicConsumers.ts`). It is mounted only when opened — reading committed offsets costs several coordinator round trips, and nobody arriving to read messages should pay them. `healthOf` grades each group rather than showing a bare number, because the number alone misleads in three directions: `STALLED` is records waiting with **no member assigned to this topic** (nothing will drain them, whatever the count), `PARTIAL` is a group that has never committed on some partitions (the total does not count what it ignores), and `AHEAD` is a committed offset past the end of the log. Expanding a group shows the per-partition detail — where an imbalance is actually visible — with `never committed` and `—` where the API returns `null`, never a zero, and the server's **per-group reason** where a group could not be read: it was carried in the payload and displayed nowhere, so "Unreadable" was a verdict with no diagnosis. Unknown membership renders as `—`, not `0/0`. **A per-group "how long has it been waiting?" button** measures the backlog in time on demand (`GET /api/topic/{name}/time-lag?group=`): on a button and not at load, because that read opens a consumer and reads a record per lagging partition where everything else on the panel reads metadata. `describeDelay` says which of the three answers it is — measured, partially measured (the value is then a **floor**, not a maximum, and the sentence says "at least"), or not measurable — and a partition with no measurement renders `not measured`, never a zero. `describeScope` states what the read covered, so an empty list cannot pass for "nobody consumes this topic" — and a read that *failed* says so rather than borrowing either sentence

- `StreamFlow` (`/stream-flow`) — message tracing across topics. A trace is a bounded scan and the page says so: a coverage line (`describeCoverage`) states what was read, the backend `warnings` are listed as they are, and the "no flow found" panel repeats the coverage rather than a bare "not found". The **evidence table** under the graph is the checkable part — one row per topic with hit count, first sighting, Δ from the previous hop, partition/offset and a payload preview, the topic name linking to its explorer — and selecting a row highlights the node (and vice versa). The run is **cancellable** (`AbortController`; a whole-cluster trace can legitimately take a minute), the scan window is a real choice ("most recent messages" vs a time window, whose read-forward caveat is stated), zoom is anchored on the pointer and the reset button **fits the graph to the viewport** instead of returning to a fixed `translate(40,40) scale(1)` that left half a seven-topic chain off screen. The trace **streams**: the page consumes `POST /api/stream-flow/stream` with `fetch` + a `ReadableStream` (not `EventSource`, which only speaks GET and silently reconnects — on a network blip mid-scan it would restart a whole-cluster trace), so hops appear on the graph as they are found, a progress bar states `42/250 topics · 12 800 messages · 3 matches`, and **Stop keeps what was found** instead of discarding it. `parseSseBuffer` is a pure, unit-tested frame reader (events split across chunks, multi-line `data:`, CRLF, comments); a browser without a readable body falls back to the non-streaming endpoint. The **unrun criterion survives leaving the page** too (`readTraceParamsDraft` / `saveTraceParamsDraft`, cleared as soon as the form is emptied): a URL that already describes a trace always wins, or a shared link would overwrite its recipient's form. The criterion is **shareable and replayable**: the whole form round-trips through the query string (`?key=&path=&topics=&window=&max=&regex=&case=&headers=`), the URL is rewritten after each run, a shared link reruns itself on open, "Link" copies it, and the last ten traces are kept in `localStorage` (`kse:flow-history`, de-duplicated on the criterion). Hops export to CSV (through `pages/resultExport.ts`) or to JSON carrying the criterion, the coverage and the warnings — a trace pasted into an incident ticket has to say what it covered. Toggles for exact record key (which disables the path field and the regex it contradicts) / regex / case sensitivity / header search sit under the criterion, and the field description states what the typed path will actually do (dot path, JSONPath, XPath or header). **`analyzeChain` reads the chain instead of leaving it to be read**: end-to-end duration, the slowest hop (only from two hops up — on a single hop "slowest" says nothing), the topics that saw the key more than once with the span they saw it over, and the hops that go backwards. They surface as a line above the table, as row badges, and on the graph itself (the slowest edge thickened in amber, a skewed one dashed in red). A negative latency is **rendered**, not hidden behind an em dash: producer clocks set the record timestamps, so it is the one fact that explains a doubtful chain order. Nothing is inferred past the data — the last topic is not called a dead end, since in a complete chain it is simply the destination. Pure logic (validation, path scope, URL round-trip, history, export, response parsing, layout, fit/zoom, formatting) lives in `pages/streamFlowLogic.ts`.
  **A completed trace is kept as an observation, not only as a criterion** (`pages/flowChains.ts`, `kse:flow-chains`): `recordTracedChain` stores the chain — topics in first-sighting order, per-hop latency, occurrences — so the Metrics page can derive KPIs from the path a key really took (see `MetricSuggestionService`). `kse:flow-history` records what was *searched* and would answer nothing about the pipeline. Same three guards as `draftStore`: a versioned envelope (an unknown shape is erased, never guessed at), a seven-day expiry (a chain from three weeks ago describes topics that may be gone) and five entries, de-duplicated **on the route** — retracing the same key an hour later describes the same pipeline, and keeping both would give two copies of one proposal rather than two proposals. A trace that touched a single topic writes nothing: one sighting is not a path.
  **Ergonomics of the working screen**, all of it driven from that same pure module: the criteria panel **collapses** to a rail (state in `localStorage`, `kse:flow-panel`, `readPanelOpen` — collapsed by default under 1024 px) and the graph refits to the width it gains, while the summary pill keeps the traced key on screen; the panel's action bar is sticky, so `Trace Flow` never falls below a list of topic chips. The graph answers the **keyboard and the finger**: the SVG is focusable (arrows pan, `+`/`−` zoom, `0` fits, `Escape` deselects), each node is a `role="button"` reachable by Tab, panning uses *pointer* events with `touch-action: none` (a tablet could not pan at all before), and a click on the background deselects. Selection is symmetric — a node selected on the graph scrolls its evidence row into view, a row selected in the table brings the node to the centre **only if it was off screen** (`centerOn` / `isNodeVisible`, scale untouched). The overlays are one flex bar rather than four floating boxes, so the cancellation notice no longer covers the scan summary; the amber and dashed-red edges get a legend. A form edited after a run marks the graph **stale** (`sameCriterion`) with a chip that reruns on click, and `Link` / `CSV` / `JSON` describe the *displayed* run (`ranParams`), never the edited form. "No flow found" is actionable: `suggestWidenings` turns the advice into at most four one-click reruns (drop the path, search headers, drop the window, read 1000/topic, ignore case, scan every topic), each changing one thing and stating it. The evidence table gets a filter past six hops (`filterHits`, hop numbers preserved), and its topic link carries the criterion into the Topic Explorer (`buildTopicSearchQuery`). A run is stamped with a generation number: what comes back from a superseded pass — its "trace cancelled" notice, its `loading: false` — is dropped instead of landing on the run that replaced it. A trace stopped by its budget offers to **continue** rather than to start over (`buildContinuation` / `describeContinuation`, in the coverage strip and first in the "no flow found" panel — finishing the scan beats widening a criterion that was never fully applied): only the unread topics are rescanned, the hops already found travel back to be merged server-side, and the displayed criterion, the URL and the history stay those of the whole trace, since the narrowed topic list is a means, not the search. The label states the real scope (`Continue on 2 of the 412 topics never read`) because the server bounds the names it returns.
  **Two traces compare side by side** (`compareFlows` / `describeComparison` / `slowestDivergence`): "ORD-42 arrived, ORD-43 vanished — where?" is the incident question, and it used to take two tabs and two tables read in parallel. `Compare` replays a criterion from the history through the **non-streaming** endpoint (a comparison has nothing to show before it is complete) and puts the two chains in one table: hop number on each side, the per-hop latency on each side, and their difference. What is compared is **hop latency, never absolute timestamps** — two keys processed an hour apart have nothing to say to each other in the absolute, while "this hop took 200 ms there and 4 minutes here" is the finding. A topic only one side saw is badged `not seen`, drawn dashed-amber on the graph (which keeps showing A) and named in the legend; `sameRoute` refuses to call two *empty* traces identical, since that would be a conclusion drawn from no data. A new trace clears the comparison rather than leaving two unrelated criteria side by side.
  **Target topics take a list or a pattern** (`parseTopicList` / `expandTopicPatterns`): commas, spaces and newlines all separate, so a list pasted from a runbook goes in at once, and `orders.*` expands over the catalogue `Layout` already polls — no extra request. `*` is the only wildcard and the dot is literal. A pattern matching nothing is **reported** instead of being sent as a topic name, which would only produce an "unknown topic" warning at the far end of a scan; a plain name that the catalogue does not know is still accepted, since a topic can exist before the 30 s cache shows it.
  **Reading the evidence**: the table's columns **sort** (`sortHits` — chain order stays the default, since it is the meaning of the trace, and a hop's rank comes from `hopNumber`, never from its row position, so it survives sorting and filtering alike); a hop with no latency, the first one, always sorts **last** whichever way the column goes, because asking for the slowest hop and reading an em dash at the top answers nothing. The graph/evidence split is **draggable** (`clampEvidencePct`, `kse:flow-evidence`, 15–75 %, also settable from the keyboard — it is a `role="separator"`), where it used to be a fixed 45 % that left a fifteen-hop chain scrolling inside a slot while four nodes kept the top half. "Max messages / topic" pairs the slider with a `NumberInput`, since 750 was otherwise a matter of hitting one pixel. A finished run is announced in a visually hidden live region: the progress bar is a `status` while it runs, but its disappearance tells a screen-reader user nothing
- `DataModel` (`/data-model`) — generates an entity-relation diagram from a selection of topics (`POST /api/data-model`): each node is a table card listing the inferred columns (key columns first — they carry the edges — capped at 12 with a counted overflow), each edge is styled by its confidence grade and labelled with the referencing column, and the inspector shows the full column list plus every relation **with the evidence it rests on**. Same graph gestures as Lineage (pointer pan, wheel zoom, arrows/`+`/`−`/`0`/`Escape` on the focusable SVG, background click deselects). The selection round-trips through the URL (`?topics=`, rewritten after each run, self-write guarded) so a model is shareable and replays on open; a selection edited after a run marks the model stale rather than letting the graph pass for current, and the coverage line plus the server's warnings say what the model does *not* cover. **The diagram reads like an ER diagram, not like a generic graph**: each edge is anchored on the *row of the column that carries it* (`computeEdgeGeometry` / `columnRowY`) rather than on the node's centre — so an edge leaves `order_id` and lands on the target's key row, which is what makes the link legible without reading the label — and cardinality is drawn in crow's-foot notation (many side on the referencing entity, bar on the referenced one), which frees the line style to mean confidence and nothing else. Edges sharing an anchor are spread (`anchorSpread`) instead of stacking, a column folded into the `+N more` overflow falls back to the node centre rather than pointing at a row that is not on screen, and the graph is **fitted to the viewport** after each run and on the reset button (`graphBounds` / `fitTransform`) — a reset to a fixed `scale(1)` left a fifteen-table model half off screen. The fit is **capped at `MAX_FIT_SCALE` (1.75), not at 1**: the old ceiling meant a three-table model rendered at its natural size in the middle of a canvas three quarters empty, which is the "the graph doesn't use the space" half of the complaint. `fitTransform` still defaults `maxScale` to 1 so any caller that does not ask sees exactly the old behaviour, and the scale itself is computed by `fitScale`, shared with `chooseNodeSizing` — with one difference that is the whole point of splitting it out: the fit needs the `MIN_FIT_SCALE` floor (0.1), the *comparison* must not have it, or two calibres that both bottom out declare themselves equivalent when one fits in a tenth of the space. `fitTransform` takes an optional `topPadding`, reserving space above the content for the coverage/warnings banner: that banner sits `absolute` over the canvas, so `fitToViewport` used to fit against the SVG's whole rect, and a run with warnings rendered its topmost row under the banner it had no way to make room for. `fitToViewport` measures the banner's live height (it varies with how many warnings it lists) and passes it through; the parameter defaults to the horizontal `padding`, so a fit with nothing to reserve reproduces the old symmetric centring exactly. **That measurement is shared with `chooseNodeSizing`** (`measureTopPadding`, one definition, mirrored into state for the memo that cannot read the DOM): the fit reserved up to ~150 px while the calibre chooser assumed 40, so on a height-bound model a calibre could be elected for a legibility the real fit never gave it — on a nine-spoke star of ten columns at 1280×800 the two assumptions pick the two opposite extremes. The fit keeps measuring live rather than reading the state, because state lags one render and the post-generation fit falls in exactly that render, the one where the warnings have just appeared; the chooser lagging a frame is harmless, since a calibre change refits anyway. **And the fit is recomputed when the available space changes** (`isSignificantResize`): it was recomputed after a generation, on crossing the `lg` threshold, and on the reset button — everything else left it describing a rectangle that no longer existed. Two cases mattered, both measured in a real browser: resizing the window *without* crossing the threshold, and **opening the inspector**, which takes 320 px from the canvas on desktop — the graph then ran 220 px and 280 px past the right edge respectively, the overflow sitting under the panel that had just opened. The refit is skipped when the operator has framed the view themselves (`viewAdjusted`, raised by every pan, zoom, arrow key and centring, cleared by a fit): re-centring under someone who has just zoomed into a table is worse than the off-centring. A sub-pixel or scrollbar-sized change is ignored, and a zero-sized measurement — a hidden tab, a collapsed panel — never reframes, since fitting to zero yields an absurd transform that would still be there on return. Entity headers are tinted by **topic domain** (`topicDomains`, the first segment after dropping the leading segments *every* topic shares, so `demo.orders.*` and `demo.payments.*` are two families rather than one `demo`), with the legend derived from what is drawn. **The confidence legend is also the filter** (`filterRelations`), one list rather than two of the same three grades: a model rich in name-only `MEDIUM` matches drowns the `HIGH` edges the target's own key actually supports, so each grade is a checkbox carrying its count. It is a *reading* control and touches exactly one thing — which edges are drawn. The layout and the connected/isolated split stay computed over **all** relations, deliberately: toggling a grade must hide lines, not rearrange the diagram under the operator, and "No deduced relation (N)" has to keep meaning *none* rather than "none among the ones you are looking at". The inspector likewise lists every relation of an entity — it is the evidence panel — but **marks** the ones the filter hides, since a relation listed with no line on screen otherwise explains nothing. Both exports follow: the SVG serialises the DOM so it is already filtered, Mermaid is handed the filtered relations so two exports of one screen cannot disagree, the confidence legend drops the grades that are off, and `exportNotes` states how many edges the filter removed — a detached diagram that does not say what it omits reads as the whole model. **A column that reads as a foreign key but yielded no relation is flagged** (`orphanKeyColumns`, a `?` marker on the node and a named callout in the inspector): it was indistinguishable from an ordinary column, so a diagram that looked incomplete never said why. **The judgement is the server's and travels in `DataModelColumn.keyBase`** — the entity word a name points at, `null` when it points at nobody. It was first mirrored in the browser, and the mirror was wrong in a way the server is not: `DataModelService.referencingBase` also rejects a name echoing its *own* topic (`order_id` on an orders topic is identity, not reference — the same rule `deduceRelations` applies before looking for a target), so the browser copy flagged such a column as a broken key. `referencingBase` is now the single rule both the deduction and the marker read; the frontend keeps only "no relation came out of it". That also collapses the explanation to **one** sentence: a target present in the model always yields a relation, so a base with no reference means the topic is simply not in the selection — which was previously a browser-side check with a second sentence for a case that could not occur. A key-like column is ranked with the keys in `displayedColumns`, not just marked: it carried no `references`, so on a nested payload it fell into the `+N more` overflow exactly when the card is crowded and the marker matters most. **An edge states its evidence where the edge is** — hovering *or* focusing one (it is a Tab-reachable `role="button"` with a transparent 14 px hit path, since a 1.5 px line cannot be caught with a mouse) opens a tooltip carrying the relation, its grade and the server's own `reason`; that justification used to be reachable only by opening a node's inspector, and an explanation only the mouse can reach is not an explanation. Message counts are compacted in the fixed-width header (`formatCount`) with the exact value on the node's SVG `<title>` and in its accessible name. **Entities no relation touches are set aside, not drawn** (`drawnEntities`, over `splitByConnectivity`): they dilute the signal, which is the relations, and — the part that costs the most — each one adds a cell to the grid under the graph, so it lowers the fit scale of *everything else*. They live in a **bounded listbox** (`role="listbox"`, capped height, open by default since that is where they now are) headed "No deduced relation (N)" and captioned by `describeSetAside`, which says why they have no edge rather than leaving a bare count to read as a truncation — and **filtered past `SET_ASIDE_FILTER_MIN` (8)** by `filterEntities`, since fifty entities with no relation is an ordinary outcome on a large selection and the list scrolls well before that; below the threshold a filter is noise. It carries the same grammar as the topic filter higher in the same panel (substring, or an anchored pattern as soon as there is a `*`) because two adjacent fields cannot answer the same text differently, and it matches **the table name or the topic**, both being on screen — the row shows the Flink identifier and carries the topic in its tooltip. `describeSetAsideFilter` says what was kept and lets zero read as zero — each one still selectable and inspectable, with an opt-in to draw them anyway, and a `N not drawn` chip beside the coverage line, because an entity missing from the diagram must say so. **And past `SET_ASIDE_GROUP_MIN` (5) it is grouped by topic family** (`groupSetAside`), because the question a long list of set-aside entities raises is not *which ones* but *which ones together* — "the whole `iot` family is outside the model" is a finding, twelve monospace rows are not. The split is the one the header tints already use, and the `topicDomains` map is **passed in rather than recomputed**: it is built over *every* topic of the model, dropping the leading segments they all share, so recomputing it on the set-aside subset alone would name the same families differently — two answers to "what family is this topic in?" on one screen. It groups **what is displayed**, so the header counts describe the screen by construction, where grouping the whole list and rendering the filtered one would put "iot (12)" above three rows. And it returns `null` rather than a single group whenever grouping teaches nothing — below the threshold, with one family (the header would repeat the section title), or when every family holds one entity (each header names only its own row) — which keeps that judgement in one place instead of leaving the page to refuse a group it was handed. A group is a `role="group"` inside the listbox named by `describeSetAsideGroup`, the visible header being `aria-hidden` so the domain and its count are not read twice; ungrouped, the wrapper is presentational and the options stay direct children of the listbox, so there is one row template either way. The rule left the page's ternary for `drawnEntities` because it decides half the available space; it keeps one exception, and only one: when *no* relation was deduced at all the grid **is** the diagram, since setting everything aside would leave a blank canvas after a successful generation. Selecting one yields **no dimming at all** rather than dimming the whole diagram to announce a node that is not in it. A field-highlight box lights the matching column in every entity that carries it (`matchingColumns`, a case-insensitive substring of the full path, so `customer.id` answers to either half) and says what it found — "who else carries this key?" is the question this diagram raises, and the answer is already in the browser, so it costs no request. **A build says what it is doing, and refuses to invent a percentage** (`describeBuildProgress`): `POST /api/data-model` is one request that answers when every topic is inferred, so the browser cannot know which topic is in flight — a progress bar derived from elapsed time would be a fabricated measurement, which is what this page refuses everywhere else. What is true is the topic count and the elapsed time, and those are what the overlay shows. It matters because the canvas was otherwise **blank for minutes** on a first run, and worse on a second: the previous model stayed on screen with nothing saying so, which `describeStaleGraphDuringBuild` now states. The per-topic budget is deliberately not quoted — it is a server constant, and a UI that copies it lies the day it changes. **A minimap appears only when the graph overflows the viewport** (`minimapLayout` / `visibleGraphRect` / `graphFullyVisible`): with everything already on screen it would draw a frame around its own box — an ornament that teaches nothing and costs a corner of the canvas. Clicking it moves the view (`centerOnGraphPoint`, current scale kept), which is the one gesture an overview owes: it situates, and it takes you where you looked. **A subgraph opens as one query** (`buildMultiJoinSql`): `buildJoinSql` answers "open this relation", but re-joining three tables by hand is the real gesture on a star schema, and the diagram already knows every predicate. Entities are added to a join set from the inspector; the query is built from a **breadth-first spanning tree** so every `JOIN` predicate cites a table already introduced — one that names a table further down does not parse. It **refuses rather than inventing a predicate**, the same rule as the binary version and it says which entity is unreachable: a set the deduced relations do not connect has no join, and fabricating one would assert an equality nothing supports. `joinAliasesFor` is the N-ary alias rule, and `joinAliases` now delegates to it — two ways of naming the same tables drift, which is a defect this module's test caught once already. **Named selections are kept by the browser** (`readSavedModels` / `saveModel` / `deleteSavedModel`, `kse:data-model-saved`): the URL is shareable but anonymous, and nothing in it says this is *the* order pipeline. Same shape as `flowChains` — versioned envelope erased rather than guessed at, bounded entries, best-effort writes — with **one deliberate difference: no expiry**. A draft is an accident of navigation and is right to forget after a week; a named save is a deliberate gesture, and dropping it unasked is data loss. Saving under an existing name replaces it in place, since stacking homonyms makes the list unusable. **Finding a table by name doesn't need the mouse**: a "Jump to an entity" combobox (`centerOnEntity`) centres the viewport on a chosen entity at a readable scale — raised to a floor if the graph is currently zoomed out further, left alone otherwise, since re-zooming a table already close enough would undo what the operator just did by hand. Restricted to *drawn* entities — one folded into "No deduced relation" has no position to centre on, and that list already exists to select it. **Comparing two selections has no server-side history to read**: unlike the audit, a data model is never persisted, so "compare" means two independent `POST /api/data-model` calls and a diff computed client-side (`diffModels`) — the same choice Stream Flow's Compare page makes for a trace. Relations carry no stable id across two runs (they're recomputed each time), so the diff pairs them by what they describe — the two columns they connect (`relationKey`) — not by position in the array; the same pair at a different confidence is one changed relation, not a removed one and an added one, because it's the same claim better or worse supported the second time. The result is a list, not two overlapping graphs redrawn on top of each other: past a handful of entities two superimposed diagrams read as noise, where "+2 entities, 1 relation added, 1 confidence changed" reads as an answer. **The diagram exports as a standalone SVG or PNG** (`buildExportSvg`), and the file carries the coverage line, both legends and what is *not* drawn (`exportNotes`) — a diagram pasted into a ticket cannot be interrogated, so one that does not state its bounds reads as a complete model, the same rule as Stream Flow's JSON export. The markup comes from the live DOM rather than being re-emitted: two renderers for one image drift, and the export would stop showing what the screen shows. **But it is serialised at the widest calibre, not the screen's** — the screen's is chosen for *a viewport*, and on a large model it folds columns into `+N more` so the diagram fits; a file has no viewport (an SVG zooms without end, the PNG is rasterised at 2×), so the export was freezing `+14 more columns` for ever, on the one artefact whose reader can zoom. `exportDiagram` therefore forces `COMFORTABLE_NODE_SIZING` across two synchronous `flushSync` commits and restores it in a `finally`: still one renderer and still the live DOM, simply not at the size of the screen, and both commits land in one task so nothing flashes. The layout it measures is recomputed from the same pure functions rather than read from the memo, which still holds the screen's. Mermaid needs none of this and returns before it — it re-emits from the response and has always carried every column. The selection is cleared through `flushSync` first, since exporting it would bake in the dimming and hand back a three-quarters-erased image; the PNG is rasterised at 2× through a canvas and a failure there points at the SVG (which works) instead of vanishing. **Topics are chosen the way Stream Flow chooses them** (`topicSelection.ts`): a name, a list pasted from a runbook or a `kafka-topics --list`, or a pattern `demo.orders.*` expanded over the catalogue `Layout` already polls — the same `parseTopicList` / `expandTopicPatterns`, imported rather than restated, since two list splitters that drift are two behaviours for one gesture. The content lives in `pages/helpContent.ts`, where tests check the examples stay executable (statements the whitelist accepts, table names in their sanitized form, every step being a statement the editor actually runs — the `INSERT INTO` lesson went with Job mode, since a step nobody can open teaches nothing) — a help page rots silently, and a wall of JSX literals cannot be checked
- `ProcessMining` (`/process-mining`) — 4-step pipeline: topic selection → Claude profiling → schema validation → snapshot/live analysis with Mermaid flowchart + anomaly table. Sub-components in `components/processmining/`.
  **The live stream no longer restarts itself.** `EventSource` reconnects on its own, and `GET /api/process-mining/live` mints a *new* session on every GET — a new Kafka consumer, a new group member, a flowchart with no history. So the stream ending started a fresh session behind the operator's back, and since `SseEmitter` was created with a **5-minute total timeout** (not an idle one — the 15 s heartbeat does not extend it), *every* live session died at five minutes and silently respawned; a server that stayed down became an unbounded loop of them. The timeout is now 12 h (`SseEmitterManager.SESSION_TIMEOUT_MS`): long-running monitoring is the feature, and the backstop it provides against a client that vanished without the socket noticing is already covered by the heartbeat within 15 s. `onerror` now closes the stream, the page says monitoring is stopped instead of letting the counters merely stop, and Resume is an explicit gesture. **Stop also tells the server** (`DELETE /api/process-mining/live/{sessionId}`, the id coming from the `CONNECTED` event, fired on unmount too): stopping used to be purely client-side, so a consumer kept polling — and could still spend one more window on the model — until the next heartbeat noticed the emitter was gone. The id is **validated as a UUID before it is used or logged**, and a malformed one is refused rather than sanitised: every session id is server-minted, so nothing else can name a session, and logging a path variable as it arrives is a log-injection sink (CodeQL flagged it) — a `%0A` forges whatever line the caller likes in the file that is meant to be the record of what happened.
  Both LLM calls carry an **axios timeout** (`PROFILING_TIMEOUT_MS`, `SNAPSHOT_TIMEOUT_MS`): axios has no default, so a server that never answered left the spinner turning for ever — the same defect the SQL editor was fixed for. Profiling that returns **no topic at all** is treated as a failure rather than sending the operator to a validation step with nothing to validate. The runtime banner states the endpoint and offers a **Test** button (through `test-llm`, hence through the shared provider); it used to read "Local lightweight open-source inference is active", concluded from the base URL containing `localhost` — a claim about a running model, asserted without ever asking one, on the page whose failures are hardest to attribute.
  **The banner's privacy sentence is now read off the address, not off the provider name.** `ClaudeConfig.isLocalDeployment()` short-circuited on `provider == OLLAMA`, so pointing Ollama at a GPU box — `CLAUDE_BASE_URL=http://gpu-box:11434/v1`, an entirely ordinary setup — kept "It is a loopback address, so no message content leaves this host" on screen while every digest went over the network. It also matched by substring over the whole URL, which said yes to `https://localhost.example.com`. The *host* is parsed and compared now, and a URL that will not parse is not claimed local: the safe answer to "am I sure this stays on this machine" is no. `ClaudeConfigTest` pins both directions.
  **`MermaidRenderer` survives a diagram it cannot draw.** The SVG was written through a ref, so the effect bailed out on a null ref — and after a failed render the ref was null for ever, the error branch having replaced the container: the next window's chart was never drawn and the stale error sat above it until a reload. With a 4B model emitting the Mermaid, one malformed diagram killed the flowchart panel for the rest of a live session. The SVG is state now, and a **generation guard** drops a render that a newer window has superseded — `mermaid.render` is async and a chart arrives per window, so a slow one could otherwise land last and win.
  **The live anomaly feed keys on more than `id`.** `id` is required by the schema and absent on every unconstrained path, and `undefined === undefined` collapsed *every* anomaly onto the first one, leaving a single row eternally "RECURRENT"; `anomalyKey` falls back to topic + type + description. And the cost line shows the **session total** beside the last window's — a live session calls the model on a timer, so the running total is what says whether a configuration is affordable. It is uncapped on purpose: a cap would make the total cover the last N windows while presenting itself as the session's. `totalTokens` (which returns `null` as soon as one call reported nothing, rather than a total that silently omits it) already existed and was unit-tested; nothing had ever asked it a question.
  **`SchemaValidationPanel` can supply a mapping, not only adjust one.** It rendered a role's rows from the proposal alone and returned `null` when there were none — so a topic the model said nothing about had no box to type into, a role it missed entirely was invisible, and a run where it proposed *nothing* replaced the whole editor with a sentence. That is the case where typing the mapping by hand matters most. Rows now come from the profiled topics, undetected roles are shown and badged, each box carries a real `<label>` (it had a placeholder and nothing else, so a screen reader got nothing), the panel is a real `<form>`, and a path that cannot match anything is refused with its reason and focused rather than sailing through to an analysis whose only symptom is an empty correlation. Validation lives in `components/processmining/schemaMapping.ts`, mirrors `PayloadDigestService.normalizePath`, and is **deliberately not stricter than the server** — three rules, all of them paths that can match no leaf; its own test caught the first draft refusing `$['a b'].c`, which the backend accepts. The panel also stopped crediting "Claude" for a proposal that, by default, comes from Ollama.
  **A result now says what it was drawn from** (`CoverageNotice`, over `pages/processMiningCoverage.ts`): what was read against what reached the model, the topics that did not resolve, the ones that held nothing, and the ones the prompt budget left out. Rendered even when everything went in — a banner that only appears on bad news is one people stop reading, and a reduced scope has to be noticeable *against* the ordinary case. It is rendered on a failed analysis too, beside the error: "none of the selected topics held a message" and "the model did not answer" send an operator to opposite places, and the second is what the error alone used to suggest. The wording is entirely in the pure module; the server sends rows, not sentences.
  **And the live session says when the validated mapping was not applied.** The `CONNECTED` event carries `fieldMappingApplied`; the store behind it is bounded and restored best-effort at boot, so a session can legitimately start without the mapping step 3 exists to produce — which changes what "correlated across topics" means for every window it will emit. It used to be said to the log and to nobody else, so the session ran looking exactly like the one that had been configured. `null` until the event says otherwise: an older server does not send the field, and assuming "yes" would assert what was never asked.
  `ProcessMiningResult` / `AnomalyReport` / `RagSource` / `ProcessMiningCoverage` live in `api/types.ts` under `@java` markers, not at the point of call: adding `error` to the Java record is exactly the drift `check-api-types.py` exists to catch.

The live status bar (`components/processmining/LiveStatusBar.tsx`) renders the `WINDOW_STATS` ingestion counters — volume read, distinct payload structures, messages dropped to backpressure, unparsed payloads — so an operator can see that big payloads are being sampled rather than silently lost.

## Metrics — le calque « Neural Float » et le registre React Bits Pro

Le composant **n'est pas dans l'arbre**, et ce fichier existe pour que personne ne conclue à un
oubli. `npx shadcn@latest add @reactbits-starter/neural-float-tw` n'a pas pu être exécuté :
`pro.reactbits.dev` **et** `ui.shadcn.com` sont refusés au CONNECT (403) par la politique réseau
de l'environnement de build, et aucune `REACTBITS_LICENSE_KEY` n'y est définie — le CLI shadcn ne
peut même pas charger son index de registres. Ce qui est posé ici est donc tout ce qui ne dépend
pas du registre, et rien d'autre.

**Ce qui est fait, et pourquoi c'est la moitié qui compte.** La condition d'affichage est la
seule partie qu'un paquet ne fournit jamais, et c'est celle qui se règle de travers en silence.
`hasRunningMetric` (`pages/metricsHealth.ts`) lit « au moins une métrique en marche » comme
`summarizeMetrics(...).reporting > 0` — une valeur produite au dernier passage, sans erreur — et
**dérive** de `summarizeMetrics` au lieu de réécrire la règle. Les deux autres états ne sont pas
des degrés de la même chose : une métrique `failing` expose encore la valeur d'avant, donc elle
*paraît* vivante alors qu'elle ne mesure plus rien, et `pending` n'a jamais rien produit. C'est
aussi pourquoi la condition n'est pas `counts.ok > 0`, qui répond à la question voisine et fausse
ici : une métrique peut être `critical` — au-dessus de son seuil — tout en tournant parfaitement.

**`NeuralFloatBackdrop` rend `null` quand la condition est fausse**, plutôt qu'un calque masqué :
une page qui ne mesure rien encore n'a pas à payer une boucle d'animation, et un `<canvas>`
invisible qui tourne est exactement ce qu'on ne retrouve pas six mois plus tard. Il porte déjà
`aria-hidden`, `pointer-events-none` et `motion-reduce:hidden` — l'ornement est le premier à
disparaître quand l'OS demande moins de mouvement, et cela vaut avant même que le composant
n'arrive.

**Le placement est porteur, et il a coûté un aller-retour.** Le réflexe — racine en
`relative isolate`, calque en `absolute inset-0 -z-10` — **casse le modal « Add metric »**. Le
`isolate` fait de la page un contexte d'empilement ; le modal est `fixed z-50` *à l'intérieur*,
la Sidebar est `fixed z-50` *à l'extérieur* (`components/Layout.tsx` la rend en frère de la
colonne de contenu), et le modal se retrouve donc enfermé sous elle. Mesuré plutôt que raisonné,
avec `docs/screenshots/layout-probe.mjs` déjà debout et `document.elementFromPoint(100, 500)`
en plein dans la Sidebar, modal ouvert : `SIDEBAR ON TOP` avec `isolate`, `modal on top` sans.
Et sans contexte d'empilement, un `-z-10` ne sert à rien non plus — il passerait derrière le
`bg-background` de la coquille, qui est un bloc en flux et peint donc *au-dessus* des descendants
à z négatif.

Ce qui est en place n'a donc ni `isolate` ni z négatif : la racine est `relative` et porte
exactement **deux** enfants positionnés en `z-auto` — le calque d'abord, un conteneur
`relative space-y-6` ensuite qui reprend tout l'ancien contenu. Entre deux éléments positionnés
sans z-index, c'est l'ordre du DOM qui tranche, donc le contenu peint par-dessus le calque sans
qu'aucun contexte d'empilement soit créé, et le modal reste au-dessus de la Sidebar. Le
`space-y-6` a suivi le contenu dans ce conteneur : laissé sur la racine, il aurait donné une
marge haute au calque et décalé son `inset-0`.

**Et le calque est `sticky`, pas `absolute`, pour une deuxième mesure.** Dans un conteneur qui
défile, `absolute inset-0` se résout sur la **fenêtre de défilement** et non sur le contenu :
mesuré sur la page Metrics de la démo en 1440×900, le calque faisait 844 px pour 2 318 px de
contenu, et après défilement jusqu'en bas son sommet se trouvait 1 474 px au-dessus de la zone
visible. L'ornement occupait le premier tiers de la page puis s'en allait — ce qui se lit comme
un défaut, pas comme une intention, sur un fond censé être ambiant. `sticky top-0 h-0` le fait
suivre la fenêtre sans rien prendre au flux ; l'hôte du canvas, en `absolute` dedans, fait
`h-screen` — un dépassement de la hauteur d'en-tête que le conteneur rogne, là où une hauteur
trop courte laisserait une bande nue en bas. Re-mesuré après coup : la zone visible est couverte
en haut **comme en bas**, et sur 1 184 px de large pour 1 184 px de racine.

**Le débord horizontal est porté par l'ancre (`-mx-6`), pas par l'hôte, et ça a coûté un job CI
rouge.** Écrit d'abord en `-left-6 -right-6` sur l'hôte, celui-ci devenait plus large que l'ancre
qui le contient : `layout-probe --check` comptait alors l'ancre comme un conteneur qui rogne son
contenu sans moyen d'atteindre le reste, `metrics` passait de 0 à 1 `unreachable` **aux deux
largeurs**, et le job screenshots échouait. La tentation était d'apprendre à la sonde à ignorer
les calques décoratifs — elle exclut déjà `sr-only` et les couches internes de Monaco pour des
raisons de cette famille. C'était le mauvais réflexe : la géométrie était réellement fautive, pas
la mesure. Porté par l'ancre, le débord annule exactement le `p-6` de la racine — l'ancre fait la
largeur de la *boîte de padding* de la racine, l'hôte fait `inset-x-0` donc la largeur de
l'ancre — et plus rien ne dépasse de son parent à aucun des trois niveaux (vérifié : `anchor`,
`root` et `host` rapportent tous `scrollWidth <= clientWidth`). `metrics` est revenu à ses
chiffres d'avant le changement, `clipped=10 unreachable=0`. Le cas unitaire pinne le sens du
débord, puisque c'est lui qui a cassé.

Le `sticky` forme un contexte d'empilement, contrairement à `absolute` — sans conséquence ici,
parce qu'il naît sur *le calque* et non sur la page : le modal vit dans le conteneur frère, donc
il n'y est pas enfermé. Le contrôle Chromium du paragraphe précédent a été refait après ce
changement et rend toujours `modal on top`. jsdom ne disposant rien, ce que le test unitaire
pinne est le *contrat de classes* (`sticky`, `h-0`, pas d'`absolute inset-0`, les trois marges
négatives) : la géométrie a été mesurée une fois, la décision est gardée pour toujours.

**`docs/check-alias-parity.py` garde l'alias `@/`.** Il est déclaré trois fois — `paths` dans
`tsconfig.json` (que lit `tsc`), `resolve.alias` dans `vite.config.ts` (que lisent Vite *et*
Vitest), `aliases` dans `components.json` (que lit le CLI shadcn) — et aucune des trois ne lit
les autres. Aucune n'est fausse isolément ; elles ne peuvent l'être que *les unes par rapport aux
autres*, ce que seule une vérification qui lit les trois peut voir. Chaque sens de la panne est
silencieux : sans l'entrée Vite, `tsc` passe et le build ne résout plus ; sans l'entrée tsconfig,
l'application se construit et tourne pendant que le typecheck tombe ; avec un `components.json`
qui vise ailleurs, `shadcn add` écrit le fichier dans un dossier que ni le compilateur ni le
bundler ne voient — le composant est sur le disque, l'import est rouge, et rien ne nomme l'alias
comme cause. Il vérifie en plus qu'`aliases.utils` résout vers un fichier qui existe, puisque
c'est de là que tout composant généré importe `cn`, et que la cible tsconfig reste relative
(`./src/*`), `baseUrl` étant déprécié par le TypeScript de ce dépôt. Les quatre pannes ont été
provoquées une à une pour vérifier qu'il les attrape, et qu'il sort bien en 1 — la boucle
`for check in docs/check-*.py` de `ci.yml` le ramasse sans modification du workflow.

**Le registre est configuré dans `components.json`** (`@reactbits` et `@reactbits-starter`, en-tête
`Authorization: Bearer ${REACTBITS_LICENSE_KEY}`). Deux choix y sont délibérés. `cssVariables` est
à **`false`** : ce projet définit `background`, `foreground`, `card`, `muted`, `border`, `primary`
comme couleurs Tailwind littérales (le bloc « Alias (compat shadcn-style) » de
`tailwind.config.js`), pas comme variables CSS — avec `true`, les composants générés émettraient
des classes attendant `hsl(var(--background))` que rien ici ne définit. Et `aliases.utils` pointe
`@/components/ui/cn`, qui est déjà exactement le `cn` de shadcn (clsx + tailwind-merge), donc un
composant installé se branche sans adaptateur.

**L'alias `@/` est neuf**, ajouté parce que les composants d'un registre shadcn s'importent ainsi.
Il est décrit à **trois** endroits qui doivent bouger ensemble — `paths` dans `tsconfig.json` (que
lit `tsc`), `resolve.alias` dans `vite.config.ts` (que lisent Vite et Vitest), et `aliases` dans
`components.json` (que lit le CLI) — et les imports relatifs existants restent valables : rien n'a
été réécrit. `paths` est en `./src/*` sans `baseUrl`, ce dernier étant déprécié par le TypeScript
de ce dépôt (TS5101).

**Pour finir l'installation**, sur une machine qui atteint le registre : exporter
`REACTBITS_LICENSE_KEY`, lancer la commande `shadcn add` ci-dessus depuis `src/main/webapp`, puis
décommenter l'import et la balise dans `NeuralFloatBackdrop.tsx` en ajustant le nom exporté et les
props au composant réellement livré. Rien d'autre dans l'application n'a à changer — la page monte
déjà le calque et lui passe sa condition. Les gabarits d'URL des deux registres sont reconstruits
sur la forme shadcn standard (`{name}`) et **n'ont pas pu être vérifiés** contre
<https://pro.reactbits.dev/docs/installation>, injoignable d'ici : c'est le premier point à
confronter à la doc si le `add` répond 404.
