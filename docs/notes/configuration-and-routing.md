# Configuration reference and SPA routing — design notes

Extracted from `CLAUDE.md`. `src/main/resources/application.yml` is the source of truth
for every default; this says what each knob is *for* and why its default is what it is.
The routing half carries four rules that a controller can break silently — read it before
adding a mapping.

## Configuration

`src/main/resources/application.yml` controls:
- LLM (`claude.*`, `ClaudeConfig` — the prefix is historical, the provider is a choice): `claude.provider` (`ANTHROPIC` / `OPENAI_COMPATIBLE` / `OLLAMA` / `OPENROUTER` / `SPECTRA`, **default `OPENROUTER`**), `claude.model` (default `openai/gpt-4o-mini`, an OpenRouter slug — that provider names its models *vendor/model*), `claude.base-url` (default `https://openrouter.ai/api/v1`; blank falls back to the provider's own default, `http://localhost:11434/v1` for Ollama), `claude.api-key` (env vars `OPENROUTER_API_KEY` then `ANTHROPIC_API_KEY` — one setting under two historical names, and `CLAUDE_API_KEY` outranks both — required for `ANTHROPIC` and for `OPENROUTER`, whose gateway answers 401 to an anonymous request, hence `isApiKeyRequired()` covering both), `claude.max-tokens` (4096 — it caps the whole JSON answer, anomalies included, so a truncated answer is a parse failure and the error says so), `claude.request-timeout-seconds` (60), `claude.snapshot-window-size` (100), `claude.snapshot-window-timeout-seconds` (30), `claude.structured-output` (`AUTO` / `ON` / `OFF`, default `AUTO`), `claude.openrouter-data-collection` (`ALLOW` / `DENY`, **default `DENY`**), `claude.openrouter-require-parameters` (**false**) and `claude.openrouter-max-price-usd-per-million` (**0**, no ceiling) for `OPENROUTER` only — see the routing note above — plus `claude.use-rag` / `claude.collection` for `SPECTRA` only
- Kafka bootstrap servers (default `localhost:9092`)
- Kafka connection mode: `PLAIN` (default), `SSL`, or `CONFLUENT_CLOUD` — each mode has its own set of required properties (keystore/truststore for SSL, API key/secret for Confluent Cloud)
- Process Mining ingestion (`process-mining.*`, `ProcessMiningConfig`): consumer fetch sizing (`max-poll-records`, `max-partition-fetch-bytes` — **must exceed the largest record**, 1 MB payloads at the 1 MB default would fetch one per round trip — `fetch-max-bytes`), payload digestion (`max-payload-bytes`, `max-depth`, `max-parse-events`, `array-sample-size`, `max-shape-paths`, `max-sample-fields`, `max-value-chars`, `preview-chars`, `shape-cache-size`, `max-window-digest-bytes`) prompt budgeting (`max-shape-paths-in-prompt`, `max-messages-per-topic-in-prompt`, `max-sample-fields-in-prompt` — what is inlined *per message*, as opposed to what the digest carries — `prompt-char-budget`) and the measured process (`max-trace-cases-in-prompt`, `max-variants-in-prompt`, `max-edges-in-prompt`, `max-status-activities`)
- Query timeout (default 10s), schema inference timeout (2s), audit run budget (`explorer.audit-max-duration-ms`, 30 min), audit consumer-group snapshot TTL (`explorer.audit-group-snapshot-ttl-ms`, 60 s — how long the cluster's groups, read once and shared across topics, stay usable before being re-read; 0 takes the snapshot once for the whole run)
- Topic search budgets: `explorer.search-max-hits` (100), `search-max-scan` (20 000), `search-timeout-ms` (10s), `search-max-value-chars` (8 000 — values are truncated in search results and samples, the original size travels in `valueBytes`), `record-max-value-chars` (1 000 000 — the cap for one record read by its coordinates, which is meant to be read whole)
- Cleanup of the app's own leftover groups: `explorer.cleanup-own-groups` (**false**) + `explorer.cleanup-own-groups-max` (500 per pass) — `ExplorerGroupCleanupService`, on `ApplicationReadyEvent`. The **only write this application makes to a cluster**, hence off by default: older builds committed offsets under a random group id on every metadata read, so a long-running deployment can carry thousands of empty groups that nothing removes. A group is deleted only if it carries one of our *readers'* names (`isOwnReaderGroup`, historical schemes included — never the `flink_table_*` id of generated DDL, which may belong to a Flink job the user runs) **and** the broker reports it EMPTY or DEAD — a live Process Mining session holds members and is therefore never a candidate, and a group that is not ours is never touched whatever its state. Bounded per pass, every deleted id logged, and a failure is a WARN rather than a refusal to start: housekeeping on someone else's cluster must not be able to keep the app down. **It runs on an interval, not once** (`explorer.cleanup-own-groups-interval-ms`, one hour; `0` restores the startup-only behaviour): every bundled stack runs the app with `restart: unless-stopped`, so a deployment that stays up for months tidied up once, months ago — while the groups it removes keep being produced, a live Process Mining session leaving an empty group behind each time one ends. A pass costs one `ListGroups` and normally no deletion at all, and a failed pass must not cancel the schedule (`scheduleWithFixedDelay` ends on the first exception its task lets out, which is how this would silently become a startup-only job again). **The cap cuts by relevance**: the naming schemes that predate the prefix go first, being the backlog no build running today can recreate, where the old cut was alphabetical over ids that are UUIDs — a random cut dressed up as an order.
- Internal topic naming: `explorer.internal-topic-prefix` (`EXPLORER_INTERNAL_TOPIC_PREFIX`, **empty**) — a prefix for the three topics this application writes to the user's cluster for its own state (`internal.audit.history`, `internal.metrics.config`, `internal.field.mappings`). Empty changes nothing, which is the point: it is opt-in, for a deployment that shares a cluster with other tenants or whose naming convention reserves a namespace per application — the same need `consumer-group-prefix` answers for groups, and it follows the same rules. It renames **only** what this application writes for itself, never a topic of the user's pipelines. A value Kafka could not accept in a topic name is refused with a WARN naming the property and the run continues unprefixed (a prefix that cannot be created is not a stricter policy, it is three stores failing to write with nothing saying why), and a value with no trailing separator gets one — `acme` yields `acme.internal.audit.history`. It is applied inside `ExplorerConfig`'s three getters, so every caller gets it from one place, and `isInternalTopic()` — the "is this one of ours?" test the KPI suggestions filter on — follows it, where a literal `"internal."` stopped being the marker the moment a prefix could be set. **The browser asks the same question and now gets the same answer**: the data model's select-all, the SQL editor's starter queries and its sink-table pick each answered it with a literal `'internal.'` written on the spot — four of them — which was right while the prefix was a constant and silently wrong the day it became a setting, a deployment that set one being re-offered its own topics as if they belonged to the cluster under exploration. `internalTopics.ts` holds the two predicates (a topic name, and the Flink table name where `toTableName` turned the dots into underscores — the prefix goes through the same transformation, or `acme.` would yield `acme.internal_` and match nothing), and **takes the prefix as a parameter defaulting to `''`** rather than reading a module-level mutable: the callers are pure, tested modules, and a mutable would make them impure and their tests order-dependent. The value travels on `DashboardResponse` and lands in `catalogStore` beside the topics it qualifies — that is the response every page already receives through `Layout`'s poll, so nothing extra is requested, and a second carrier (`/api/query/init` also has a catalogue) would be a second copy of one setting, which is how two answers to one question begin. **Deliberately not retroactive**: changing it points the application at different topics, it does not move what the previous setting wrote, and an operator who sets it on a live deployment starts a fresh audit history. That is where it differs from the consumer-group prefix, which keeps recognising its default so a rename does not orphan what came before — a topic can only be read or not read, never recognised.
- Provisioning of those same three topics: `explorer.internal-topic-provisioning` (`EXPLORER_INTERNAL_TOPIC_PROVISIONING`, **true**), `explorer.internal-topic-reconcile` (**false**) and `explorer.audit-history-retention-ms` (30 days; `0` leaves the broker's own retention alone, `-1` keeps reports for ever) — `InternalTopicProvisioner`, on `ApplicationReadyEvent`. Nothing here had ever *created* these topics: they were auto-created by the broker on the first write, and therefore with its defaults, which is wrong for all three. `internal.metrics.config` and `internal.field.mappings` are **keyed stores** — replayed by key at startup, only the last record per key mattering, which is the definition of a compacted topic — and both got `cleanup.policy=delete` with whatever `retention.ms` the broker had, so a metric configured eight days earlier was deleted by the broker and the next restart came up without it, in silence. `FieldMappingStore` said so in its own warning ("The topic is meant to be compacted — check that it is"): the requirement was documented and enforced nowhere. `internal.audit.history` is append-only and nothing ever trimmed it, so what bounded it was whichever retention the broker happened to apply — unbounded on one cluster, a "Past runs" list that stops a week back on another, and `audit-history-max-records` bounds only what one *listing* reads. It also removes the dependency on `auto.create.topics.enable`, which the bundled stacks set to `true` with a comment naming these very topics and which most production brokers turn off — there the three writes simply failed. Four rules, the same ones `ExplorerGroupCleanupService` states for the other write this application makes to a cluster: **only ours** (the names come from the getters above, so the prefix is followed and no topic of the user's can be named); **create, don't alter** — an existing topic whose policy differs is reported with the value found, the value wanted and the `kafka-configs.sh` line that fixes it, since it may have been configured deliberately, and `internal-topic-reconcile` is the opt-in an upgraded deployment turns on once; **the broker sizes the topic**, partitions and replication left to its defaults, a hard-coded replication factor being wrong on every cluster but the one it was written on; and **never fatal, never in front of readiness** — the stores fall back to auto-creation exactly as before. `cleanup.policy` is compared as the *list* it is, so a topic set to `compact,delete` is not a finding, and a configuration that could not be read is not a finding about the topic either.
- Internal consumer group naming: `explorer.consumer-group-prefix` (`EXPLORER_CONSUMER_GROUP_PREFIX`, default `kafka-explorer-`) — the prefix for the groups **this application creates for its own reads**, and for nothing else. See `ExplorerConsumerGroups` below.
- Consumer lag: `explorer.consumer-group-max-groups` (200 groups whose committed offsets are read for one topic — each costs a coordinator lookup, and the response says when the cap truncated it); `explorer.lag-metrics-topics` (empty by default — topics whose lag is exported to Prometheus, named rather than discovered), `explorer.lag-metrics-max-series` (500) and `explorer.lag-metrics-time` (**false** — also export the backlog in time for those topics; the only lag gauge that reads a record rather than metadata)
- Dashboard activity sparkline: `explorer.activity-max-topics` (100 — topics one `GET /api/dashboard/activity` may measure), `explorer.activity-max-lookups` (20 000 — partitions × bucket boundaries for one call, the real unit of work), `explorer.activity-default-window-ms` (86 400 000) and `explorer.activity-buckets` (24) for a request that names neither. The buckets are clamped to [4, 60] and the window to [1 min, 30 days] server-side: fewer than four points is not a curve, and a request past those is a mistake, not a policy.
- Data model: `explorer.data-model-max-topics` (100) — the ceiling on one `POST /api/data-model` run. The request carries its own, lower, per-run budget (30 by default, a field on the page); this is what bounds it.
- Stream-flow budgets: `explorer.stream-flow-timeout-ms` (60s wall clock for one trace — a whole-cluster trace could otherwise pin the HTTP thread for minutes) and `explorer.stream-flow-max-topics` (250 topics scanned when the request names none — the 250 **most recently active**, see `StreamFlowService` above). Each topic's scan reuses the topic-search budgets (`explorer.search-timeout-ms`, clamped to the remaining trace budget)
- Header label: `explorer.cluster-name` (`EXPLORER_CLUSTER_NAME`, default `Kafka cluster`) — a display name for the environment, nothing more; see the connection-pill note under **App shell**
- Consumer pool: `explorer.consumer-pool-size` (**0**, disabled) — how many byte-array consumers the per-topic record readers keep between reads. See `KafkaConsumerPool` for why the default is off
- Cache TTL: `explorer.cache-expire-seconds` (default 30s) — applied by the custom `CacheManager` bean in `WebConfig`; a `spring.cache.caffeine.spec` in YAML would be silently ignored
- Startup state restores: `explorer.startup-restore-timeout-ms` (3000) — how long each of the two `@PostConstruct` topic reads may wait for the broker's first answer, shared through `StartupRestore` so the second does not re-pay for the first one's verdict
- Keeping what was typed: `explorer.settings-persistence` (**true**) governs both stores below — it is one question about one deployment. `explorer.settings-store-path` (`data/settings.json`) holds what the Settings page changes, `explorer.flink-table-store-path` (`data/flink-tables.json`) the `CREATE TABLE` statements written in the SQL editor. `explorer.settings-store-secrets` (**true**) decides whether the credentials go into the first of those — see `SettingsStore` above for why a file rather than a topic, why the environment still outranks it, and why turning secrets off has to *name* what it left out

- Log level: application package defaults to INFO (`logging.level`); per-query engine logs are DEBUG. `org.apache.kafka.clients.admin.internals.AdminMetadataManager` is pinned to **WARN** — measured at 98.2 % of a boot's log volume when the broker does not answer — and `logging.logback.rollingpolicy.total-size-cap` is set to 200MB, Spring Boot's default being no cap at all
- Default result rows (50)
- Audit topic name (`internal.audit.history`) and history read cap (`explorer.audit-history-max-records`, 200)
- Field-mapping topic (`explorer.field-mapping-topic`, `internal.field.mappings`) — where a validated Process Mining mapping is kept, keyed by its id so the topic can be compacted
- Prometheus: `management.endpoints.web.exposure.include: health,info,prometheus` — exposes `/actuator/prometheus` for scraping

## SPA routing

`SpaController` forwards to `index.html` everything that is not a static asset and not under `/api/`, enabling client-side routing. The frontend router (`App.tsx`) then handles the route. When adding new frontend pages, no backend changes are needed. The `/api/` half of that sentence is a mapping (`unmappedApi`), not a property of the catch-all — see the third rule below.

**`SpaRoutingTest` is what enforces the three rules below**, and it was written after the piecemeal guard let two of them through. It boots the real web layer and walks the router of `App.tsx`: a forward to `/index.html` proves both halves at once — the SPA serves the route, and nothing intercepted it. What guarded it before was a 404 assertion inside three different controller tests, in standalone MockMvc, which says only that *that* controller does not map the path; `/audit`, `/lineage`, `/cluster` and `/compare` were guarded by nothing, and `SpaController` had no test. It found three live defects: `CompareController` still mapped `GET /compare` returning the view name `"compare"`, `HelpController` was an entire controller whose only mapping was `GET /help` doing the same (both deleted or reduced to their API), and **`/topic/<a dotted name>` answered 404** — see below.

**A Kafka topic name contains dots, and `SpaController`'s patterns excluded them.** `{path:[^\.]*}` is right in general: it is what lets `/assets/index-a1b2c3.js` fall through to the resource handler. It is wrong for the one client route whose parameter is a topic name — every topic of the demo cluster is `demo.orders.1.received` — so a shared link to a topic, or F5 on the Topic Explorer, fell through and answered **404**. `/topic/**` is mapped explicitly rather than by loosening the dot rule, which would take the asset paths with it; nothing static lives under `/topic/`.

**And the catch-all does not exempt `/api/**` by itself — a mapping does.** `/**/{path:[^\.]*}` matches any dotless path, `/api/` included, so it only ever lost to a *mapped* endpoint on specificity: `GET /api/topics` — the plural of the real `/api/topic`, i.e. a renamed endpoint or one letter of a typo — matched nothing under `/api/` and was answered **200, as HTML**, with `index.html`. That reaches axios and dies inside `JSON.parse` on `<!doctype`, naming neither the route nor the mistake. `SpaController.unmappedApi` maps `/api/**` and throws a 404: measured against `PathPatternParser`, that pattern is strictly more specific than the catch-all and strictly *less* specific than every mapping under `/api/` in the package — literal and path-variable alike — so it shadows none of them and collects only what would have fallen through to the SPA. The guard for it had to change too: asserting on `/api/metrics` proves only that a mapped endpoint outranks the catch-all, which was never in doubt; the rule is asserted on an **unmapped** path.

**Never map a controller onto a client-side route.** There is no template engine, so a `@GetMapping("/stream-flow")` returning the view name `"stream-flow"` shadows `SpaController` and answers a page refresh with a circular-view-path 500. `StreamFlowController` carried exactly that mapping (removed; it is now `@RestController` under `/api/stream-flow`), `ConfigController` carried it too — `GET /config` returning the view name `"config"`, so refreshing the Settings page answered 500 (removed with the form-encoded `POST /config`; the SPA posts JSON to `/api/config`). `TableController` was the third and the worst of them: a whole `@Controller` whose only mapping was `GET /table/{name}`, returning the view name `"table-detail"` — a template that exists nowhere. Nothing linked to it, no SPA route matched it, and no test named it, so it sat there taking `/table/*` away from `SpaController` (its mapping being the more specific of the two) while running `"SELECT * FROM " + name` — a path variable concatenated into a statement and submitted to the query engine on an unauthenticated GET — and discarding the rows into a `Model` nothing rendered. Deleted; `QueryControllerTest.thereIsNoServerSideTablePage` pins its absence beside the live `DELETE /api/query/table/{name}`. The same rule is why there is no `GET /audit`. Domain controllers belong under `/api/**`.

**An endpoint nobody calls is an entry point nobody guards.** That is the other half of what `TableController` was, and `POST /api/metrics/preview` was the same shape one controller over: it took raw SQL from the body of an unauthenticated request and handed it to `flinkSqlService.executeSql`, while having **no caller anywhere** — not in the SPA, which previews through `/preview-template`, not in a test, not in the rest of the tree. A second path into the query engine that nothing exercises is how two paths to one behaviour start to diverge, and the four `Map.of("error", …)` branches inside it carried the trap `ddl-preview` had already been fixed for (`Map.of` refuses a null value and `e.getMessage()` is null on an NPE, so the error path answered 500 with no body). Deleted; `MetricControllerTest.theUncalledSqlPreviewEndpointIsGone` pins its absence, asserting **405 rather than 404** — measured, not assumed: `DELETE /{id}` matches that path with `id = "preview"`, so Spring answers "method not supported", and restoring the endpoint would make the call succeed and the test fail. Its sibling `save` keeps its refusal but serves it as `ApiError`, whose `of(Throwable)` goes through `SqlErrorClassifier.explain` for the same reason — the wire shape is unchanged, `extractApiErrorMessage` reads `error` either way.

**Repointing the cluster is refused while work runs against it.** `POST /api/config` answers **409** when a change touches `bootstrapServers` or `mode` and an audit, a Flink job or a live Process Mining session is still running — naming what, in `message` and `inFlight`. Nothing is stopped: that work is bounded and cancellable from its own screens, and killing it from a settings save would be a worse surprise than refusing the save. `force: true` proceeds anyway (the Settings page turns the 409 into a confirm dialog carrying the server's own words), and what was already running keeps reading the previous cluster. LLM settings are not guarded — they touch nothing an audit reads.
